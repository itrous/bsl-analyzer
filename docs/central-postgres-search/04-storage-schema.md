# Схема хранения

Этот документ фиксирует схему PostgreSQL на уровне основных сущностей —
**реально используемые таблицы**.

## Реально используемые таблицы

### `snapshots`

Хранит snapshot'ы корпусов; их видимое содержимое после публикации не меняется.

Ключевые поля:

- `id`
- `corpus`
- `fingerprint`
- `parent_snapshot_id`
- `branch`
- `commit_sha`
- `created_at`

Внешний ключ `snapshots_parent_fk`: `parent_snapshot_id REFERENCES snapshots(id)
ON DELETE RESTRICT` — snapshot, на который ссылается потомок, удалить нельзя. На
существующих схемах миграция добавляет его `NOT VALID`: уже висящая строка
миграцию не валит, а новые висячие ссылки и удаление родителя живого потомка ключ
отказывает. Версия схемы при этом остаётся `3`.

Snapshot бывает **дельтой** (родитель есть, видимый набор собирается по цепочке)
или **самостоятельным** (`parent_snapshot_id IS NULL`, все видимые файлы — его
собственные строки). Компактация (`admin prune`) делает самостоятельным
сохраняемый snapshot, чей родитель удаляется; его видимое содержимое не меняется.

### `snapshot_heads`

Текущий snapshot каждой ветки: `(corpus, branch) → snapshot_id`.

- по ней резолвится ветка (при отсутствии строки — последний snapshot ветки по
  `created_at`); head двигается только вперёд по `created_at`;
- ссылается на `snapshots` с `ON DELETE CASCADE`: удаление snapshot снимает и его
  строку head;
- компактация её не меняет и не удаляет ни один snapshot, на который она указывает.

### `snapshot_files`

Связывает логический путь внутри snapshot с file object. У дельты — только
изменившиеся относительно родителя файлы, у самостоятельного snapshot — весь его
видимый набор.

Ключевые поля:

- `snapshot_id`
- `collection`
- `root_id`
- `path`
- `file_fingerprint`
- `document_count`
- `file_object_id`

Тождество файла — тройка `(collection, root_id, path)`. Расширение повторяет
раскладку конфигурации, поэтому один относительный путь под двумя корнями
называет два РАЗНЫХ файла; ключ без корня слил бы их в одну строку. Корень
конфигурации — пустая строка, поэтому строки, записанные до появления корней,
сохраняют смысл под составным ключом без переписывания.

### `file_objects`

Хранит дедуплицированное файловое содержимое на уровне объекта файла.

Ключевые поля:

- `id`
- `collection`
- `file_fingerprint`
- `document_count`

### `file_object_items`

Хранит структурированные item'ы одного file object.

Ключевые поля:

- `file_object_id`
- `ordinal`
- `symbol_name`
- `kind`
- `line_start`
- `line_end`
- `content_hash`

### `content_objects`

Дедуплицированное текстовое содержимое item/chunk.

Ключевые поля:

- `content_hash`
- `text`

### `semantic_embeddings`

Общее хранилище эмбеддингов.

Ключевые поля:

- `embedding_key`
- `model_id`
- `dimension`
- `embedding`

### `snapshot_deletions`

Фиксирует удаления путей относительно parent snapshot.

Ключевые поля:

- `snapshot_id`
- `collection`
- `root_id`
- `path`

Корень входит в ключ по той же причине, что и в `snapshot_files`, и здесь она
дороже: удаление, записанное без корня, погасило бы живой файл другого корня.

Эта таблица важна для корректного восстановления resolved view по цепочке delta
snapshot'ов. У самостоятельного snapshot удаления остаются как были: снаружи они
ничего не гасят, а собственный файл с тем же ключом гасят по-прежнему.

### `serving_lexical` и `serving_semantic`

Развёрнутые для чтения проекции snapshot'а: лексическая держит текст и `tsvector`,
семантическая — вектор эмбеддинга.

Ключевые поля `serving_lexical`:

- `snapshot_id`
- `collection`
- `root_id`
- `path`
- `ordinal`

Ключевые поля `serving_semantic` — те же плюс `model_id`, потому что одна и та же
строка живёт в схеме по одному разу на модель эмбеддинга.

Корень входит в ключ обеих по той же причине, что и в `snapshot_files`. У
семантической он закрывает вторую, менее очевидную беду: строки готовятся по
списку видимых ФАЙЛОВ, а не по объектам файлов, — `file_object_id` вычисляется из
содержимого и перестаёт быть однозначным, едва два корня держат одинаковые байты
по одному относительному пути. Такая пара делит один эмбеддинг намеренно (вектор
описывает содержимое) и получает две строки.

**Обязательность различается.** `serving_lexical` обязательна; `serving_semantic`
создаётся только там, где есть расширение `vector`, и база без него полностью
пригодна для всего остального. Поэтому отсутствие семантической таблицы —
не ошибка, а её существование с неверным ключом — ошибка: раз таблица есть, ею
пользуются. Проверка готовности спрашивает существование отдельным вопросом, а не
выводит его из пустого состава ключа: пустой состав даёт и таблица, у которой
первичного ключа нет вовсе, — состояние, в котором миграция умерла между
`DROP CONSTRAINT` и `ADD PRIMARY KEY`.

### Версия схемы

Строка `schema_version` в `_schema_metadata_`; текущая — `3`. Миграция идёт
только вперёд и внутри одной транзакции, под advisory-блокировкой по имени схемы.

Барьер связывает лишь те сборки, которые эту блокировку берут, то есть знающие
свою версию и более поздние. Сборка, выпущенная раньше барьера, поставит свою
версию поверх и разблокирует сама себя, и средствами новой сборки до неё не
дотянуться. Отсюда правило эксплуатации: **две сборки разных версий не должны
делить одну схему** — барьер упорядочивает подъём, но не переживает спуск.

## Характеристики текущей схемы

Схема уже сейчас оптимизирована под:

- immutable publication;
- reuse file objects;
- reuse текстовых payload'ов;
- reuse embeddings между snapshot'ами.
