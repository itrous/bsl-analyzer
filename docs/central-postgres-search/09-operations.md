# Эксплуатация

## Базовая модель эксплуатации

Для shared search ожидается такой production-контур:

- один PostgreSQL instance или cluster для shared search;
- CI публикует snapshot'ы;
- разработчики читают baseline через ограниченные runtime credentials;
- retention и GC обслуживаются как отдельные штатные операции.

## Что нужно контролировать

Минимальный operational baseline:

- доступность PostgreSQL;
- latency lexical и semantic запросов;
- рост таблиц snapshot/file/embedding;
- reuse vs create статистику на publish;
- количество снимков к удалению в `admin prune` и кандидатов в `admin gc`;
- состояние branch support policy.

## Retention, компактация и освобождение места

### Почему предков нельзя удалять по возрасту

Инкрементальная публикация записывает в snapshot только изменившиеся файлы и
удаления относительно родителя (`parent_snapshot_id`), а видимый набор файлов
собирается по всей цепочке предков. Поэтому каждый head зависит от всей своей
истории: удалить старый snapshot «по возрасту» значит сломать всех его потомков.
Внешний ключ `snapshots_parent_fk` (`ON DELETE RESTRICT`) такое удаление
запрещает.

Компактация делает удаление возможным в два шага:

1. сохраняемый snapshot, чей родитель удаляется (граница), становится
   **самостоятельным**: в его `snapshot_files` копируется вся его видимая карта,
   `parent_snapshot_id` становится `NULL`. Id, fingerprint, `created_at`,
   `serving_*`, маркеры полноты семантики и `snapshot_heads` не меняются, видимое
   содержимое и результаты поиска — тоже;
2. затем удаляются просроченные snapshot'ы, от потомков к предкам; каскад снимает
   их строки в `snapshot_files`, `snapshot_deletions`, `serving_lexical`,
   `serving_semantic`.

Что удаляется: снимки `workspace-code` с веткой, которые `inspect retention`
относит к `expired-candidate`, кроме защищённых `minimum-preservation` и снимков,
на которые указывает `snapshot_heads`. Последний снимок каждой ветки, снимки окна
`developRetentionDays`, `vendorKeepHeads` последних снимков `vendor`, корпус
`reference` и снимки без ветки не удаляются никогда.

### Порядок

1. Проверить план:

   ```bash
   bsl-analyzer search baseline inspect retention -s ./my-project
   bsl-analyzer search baseline admin prune -s ./my-project
   ```

   `admin prune` без флага ничего не меняет: печатает политику, сохраняемые
   снимки по причинам, снимки, которые станут самостоятельными (и сколько строк
   `snapshot_files` каждый получит), снимки к удалению в порядке удаления и
   оценку освобождаемого места по `serving_lexical`, `serving_semantic`,
   `snapshot_files`, `snapshot_deletions` (доля строк удаляемых снимков ×
   `pg_total_relation_size`). Перед первым `--execute` схема должна пройти
   `admin migrate` этой сборкой — иначе dry-run печатает предупреждение, а
   `--execute` отказывает с `parent_link_not_enforced`.
2. Выполнить компактацию сразу за dry-run, вне окна публикаций:

   ```bash
   bsl-analyzer search baseline admin prune -s ./my-project --execute
   ```

   Команда строит план заново (каталог и текущее время читаются ею самой — снимок,
   переступивший край окна между dry-run и `--execute`, в план попадёт), печатает
   его до первого шага, затем строку на каждый зафиксированный шаг и итог.
   Повторный dry-run после успешного запуска показывает `To make standalone: 0`
   и `To delete: 0`. Первый запуск на существующей длинной цепочке и есть её
   починка: самостоятельной становится граница, переиндексация не нужна.
3. Собрать осиротевшие объекты — сначала dry-run, затем удаление:

   ```bash
   bsl-analyzer search baseline admin gc -s ./my-project
   bsl-analyzer search baseline admin gc -s ./my-project --execute
   ```

   `gc` удаляет file objects без `snapshot_files`, их items, content objects без
   items и эмбеддинги вне активных ключей.
4. `VACUUM (ANALYZE)` для `serving_lexical`, `serving_semantic` (если таблица
   есть), `snapshot_files`, `snapshot_deletions`, `file_objects`,
   `file_object_items`, `file_object_parts` (если таблица есть), `content_objects`,
   `semantic_embeddings`:

   ```sql
   VACUUM (ANALYZE) <schema>.serving_lexical;
   ```

   `serving_semantic` создаётся только при расширении `vector`, `file_object_parts`
   — только у схемы с заявленной раскладкой токенов; есть ли таблица, показывает
   `SELECT to_regclass('<schema>.<таблица>')` (не `NULL` — есть). После `VACUUM`
   освобождённое место пригодно для новых публикаций, но размер файлов таблиц не
   уменьшается. Чтение и публикацию `VACUUM` не блокирует.
5. Вернуть место операционной системе, если оно нужно, — `VACUUM FULL
   <schema>.<таблица>`, начиная с `serving_lexical` и `serving_semantic` (если
   таблица есть). `VACUUM FULL` берёт блокировку, несовместимую с чтением, поэтому
   выполняется в окне обслуживания без публикаций и при недоступном на это время
   поиске по baseline; ему нужно свободное место под новую копию оставшихся строк
   таблицы. Альтернатива без долгой блокировки — расширение `pg_repack`; его
   ставит администратор БД, продукт его не использует.
6. Проверить размеры:

   ```sql
   SELECT pg_size_pretty(pg_total_relation_size('<schema>.<таблица>'));
   ```

### Права

`VACUUM` и `VACUUM FULL` выполняет владелец таблиц (роль, которой выполнялся
`admin migrate`) или роль с правом `MAINTAIN`. Роль без прав получает
предупреждение `permission denied … skipping it`, а не ошибку, — поэтому после
`VACUUM` проверять предупреждения и размеры. `admin prune` и `admin gc` работают
под ролью migrator и в dry-run, и с `--execute`.

### Объём WAL

Удаление пишет WAL порядка объёма удаляемых данных — следить за местом под WAL и
его архив. Удаление идёт по снимку на транзакцию, так что объём одной транзакции
ограничен одним снимком.

### Конкурентная работа и прерывание

- Каждый шаг — своя транзакция; сначала все снимки становятся самостоятельными,
  затем идут удаления. Прерывание посреди шага откатывает его транзакцию;
  состояние между шагами согласовано, висячих ссылок на родителя нет. Повторный
  запуск строит план заново и доделывает оставшееся.
- Читатель сохранённого снимка в любой момент видит прежнюю карту: она читается
  одним SQL-оператором. Читатель удаляемого (просроченного) снимка после удаления
  получает «not found».
- Публикация потомка удаляемого снимка (явный `--parent-snapshot-id` или
  републикация, где родителем выбран второй снимок ветки) сериализуется внешним
  ключом: либо удаление получает `snapshot_still_referenced` и запуск
  останавливается (данные целы, повторный `prune` доделает), либо публикация —
  `parent_snapshot_missing`, и её повторяют; при одновременных транзакциях вторая
  ждёт первую.
- Републикация снимка-границы или удаляемого снимка сериализуется блокировкой его
  строки; изменение снимка во время его материализации даёт
  `snapshot_changed_while_compacting`, ничего не меняя.
- Семантическая публикация потомка границы, спланированная до её материализации,
  получает `snapshot_republished_while_publishing` и не ставит маркер полноты;
  её повторяют. Поэтому компактацию запускают вне окна публикаций; корректность от
  этого не зависит.
- Снимок, ставший head после построения плана, не удаляется (`skipped …: became a
  branch head`); если его родитель тоже в плане, удаление родителя упирается во
  внешний ключ и запуск останавливается с `snapshot_still_referenced` — повторный
  `prune` сделает такой снимок самостоятельным и удалит предка.
- `admin gc --execute` не запускать одновременно с `publish`: публикация
  переиспользует найденные эмбеддинги, и удалённый в этом окне эмбеддинг оставит
  снимок без маркера полноты семантики.

### Расписание

Регулярно вне окна публикаций, например еженедельно. Это рекомендация, а не
лимит: длина живой цепочки после `prune` не превышает числа сохраняемых снимков.

## Безопасность

Нормальная operational модель:

- разработчики получают read-only или близкие к тому права;
- публикация и очистка доступны только контролируемым pipeline/операторам;
- секреты для PostgreSQL и embedder'ов хранятся вне репозитория.
