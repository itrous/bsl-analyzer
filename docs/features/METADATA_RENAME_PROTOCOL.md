# Протокол переименования метаданных

Клиент показывает предварительный просмотр и отправляет отдельный commit после
подтверждения эксклюзивной сессии. Сервер применяет план сам, с журналом исходных
байтов. Ответ preview предназначен только для просмотра: его нельзя передавать
в `workspace/applyEdit` или преобразовывать в обычный `WorkspaceEdit`.

Это описание серверного кандидата. Приёмка нового клиента в настоящем VS Code
Extension Host ещё обязательна. В общем workspace сервер приостанавливает
чтение диска всеми участвующими LSP/MCP-моделями, отменяет и дожидается уже
допущенных читателей. После завершения журнала общий владелец синхронно собирает
и публикует одну конечную модель; затем сервер открывает чтение и повторяет
уведомление подписчикам той же generation. Во время записи запросы получают
ограниченный по времени отказ или явный ответ о загрузке, без промежуточных
результатов из частично изменённого дерева.

## Согласование поддержки

Клиент передаёт при initialize:

```json
{
  "capabilities": {
    "experimental": {
      "metadataRename": {
        "protocolVersion": 1,
        "buffersOwnReloads": true
      }
    }
  }
}
```

Сервер объявляет `experimental.metadataRename.protocolVersion=1`,
`exclusiveSession=true`, `requiresOwnReloadBuffering=true` и имена трёх методов.
Отсутствие любого обязательного клиентского признака запрещает все три метода.
Обычные `textDocument/prepareRename` и `textDocument/rename` для BSL-символов
сохраняют прежнее поведение.

## Открытые документы

Каждый preview и commit содержит `documents`: полный список открытых входов всех
участвующих корней, включая XML, и точных `contextInputs` даже вне корней.
Первый preview, до получения границ, может содержать метаданные всех открытых
локальных документов: сервер сам отбирает участвующие входы. Для следующего
preview и commit клиент использует полный список по возвращённым границам.
Клиент передаёт для каждого документа:

```json
{
  "uri": "file:///project/cf/Catalogs/Partners.xml",
  "version": 7,
  "textSha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "dirty": false
}
```

`textSha256` — SHA-256 UTF-8 представления текста редактора; это отдельный
отпечаток, а не хеш исходных байтов с BOM. Для сопоставления с редактором сервер
исключает ровно один начальный U+FEFF; исходный BOM остаётся в файловых байтах и
в `beforeText`/`afterText`. Клиент также исключает один начальный U+FEFF из этих
двух полей при сравнении с `TextDocument.getText()`. Версия и текст BSL сверяются также с
синхронизированным серверным документом. Несохранённый документ, несовпадение с
диском, пропущенный открытый BSL или изменённая версия запрещают commit.

## Предварительный просмотр

Метод `bsl/metadataRenamePreview`:

```json
{
  "textDocument": {"uri": "file:///project/cf/Catalogs/Partners.xml"},
  "position": {"line": 4, "character": 10},
  "newName": "Customers",
  "documents": []
}
```

Позиция использует согласованную при initialize кодировку LSP. Цель разрешается
по BSL, SDBL или XML-диапазону общей семантической моделью. Новое имя и коллизии
проверяет общий построитель плана.

Ответ для обычного плана:

```json
{
  "operation": "rename",
  "roots": [{
    "sourceUri": "file:///project/cf",
    "canonicalUri": "file:///project/cf",
    "caseSensitive": true
  }],
  "contextInputs": [{
    "uri": "file:///project/bsl-analyzer.toml",
    "canonicalUri": "file:///project/bsl-analyzer.toml",
    "caseSensitive": true
  }],
  "sessionId": "server-session-token",
  "expiresInSeconds": 300,
  "canApply": true,
  "problems": [],
  "files": [{
    "uri": "file:///project/cf/Catalogs/Partners.xml",
    "beforeText": "...",
    "afterText": "..."
  }],
  "resources": [{
    "oldUri": "file:///project/cf/Catalogs/Partners.xml",
    "newUri": "file:///project/cf/Catalogs/Customers.xml"
  }],
  "documents": []
}
```

При `canApply=false` сервер возвращает причины и `sessionId=null`; применить
такой результат нельзя. Snapshot охватывает все прочитанные файлы, исходные
диапазоны/байты, состав каталогов и контекст корней. В ответ входят только
изменяемые текстовые файлы и операции с ресурсами, без полного прочитанного
снимка. Сервер хранит не более четырёх планов, каждый пять минут. Снимок ограничен
10 000 файлов, 64 MiB на файл и 128 MiB в сумме; JSON preview — 8 MiB. Превышение
запрещает применение и не превращается в частичный план.

`roots` задаёт полные границы участвующих входов, включая зависимости и файлы
без правок. Клиент проверяет принадлежность документа по компонентам пути, а
не по строковому префиксу; учитывает `caseSensitive` и оба URI корня. Для alias
использует настоящий путь файла, а для нового файла — настоящий путь ближайшего
существующего родителя и оставшиеся компоненты. Границы нельзя выводить только
из изменяемых `files`.

`contextInputs` содержит уже прочитанные настройки проекта, цепочку `extends`
и `.env`, в том числе за пределами source roots. Здесь действует точное
совпадение пути/alias с учётом `caseSensitive`, а не принадлежность каталогу.
Для ожидаемого отсутствующего файла `canonicalUri=null`; его создание тоже
делает план устаревшим. Открытые context inputs обязательно входят в `documents`.
Их несохранённый текст или изменённая версия запрещают commit. Содержимое `.env`
сервер не передаёт в preview или журналы протокола: только URI и состояние
документа с отпечатком. `files[].beforeText/afterText` предназначены для правок
переименования.

## Применение

Метод `bsl/metadataRenameCommit`:

```json
{
  "sessionId": "server-session-token",
  "exclusiveSession": true,
  "documents": []
}
```

`exclusiveSession=true` подтверждает выбранное пользователем условие: все
участвующие буферы сохранены, нет параллельного ввода/сохранения и других writers.
Это условие пользователя и участвующего клиента; собственные locks не блокируют
сторонние расширения или процессы.

Клиент повторно получает полный manifest непосредственно перед commit. Сервер
повторно проверяет файлы, версии, все каталоги и контекст уже под своими locks.
До создания сессии сервер сравнивает выбранный проект со свежей загрузкой тех же
настроек; shared загрузка сохраняет согласованные CLI source overrides. Изменение
настроек до принятия watcher-события тоже запрещает preview. Привязки и байты
настроек повторно читаются после получения locks и непосредственно перед первой
записью исходников.
Токен расходуется при начале commit. Повторный commit с тем же токеном запрещён;
неопределённый результат нельзя автоматически повторять. После разрыва связи
клиент начинает новый preview, чтобы обнаружить журнал и фактическое состояние.

Во время commit клиент откладывает только доказанные собственные disk reloads:
текст должен совпадать с `afterText` просмотренного файла, с учётом переименования
пути. Ввод пользователя и любое другое изменение сразу отправляются серверу и
считаются нарушением эксклюзивности. Нельзя скрывать произвольный `didChange`
под видом собственного reload. После конечного ответа клиент обновляет открытые
документы с диска, отправляет отложенные изменения/открытия/закрытия и проверяет
полный manifest. Несовпадение требует повторного анализа, а не нового commit
старого токена. Эту часть необходимо подтвердить настоящим Extension Host.

XML и другие входы вне BSL `documentSelector` клиент отслеживает собственными
событиями VS Code. Во всех согласованных v1-клиентах, включая клиента без
собственной rename-сессии, пользовательская правка отправляет отдельный запрос:

```json
{
  "sessionId": "",
  "violation": true,
  "documentUri": "file:///project/cf/Catalogs/Partners.xml",
  "dirty": true,
  "eventKind": "change"
}
```

Метод — `bsl/metadataRenameAbort`. Допустимые `eventKind`: `change`, `open`,
`close`, `save`, `create`, `delete`, `rename`. Ответ содержит `aborted` для локальной
сессии и `violationReported` для общего writer. Сервер проверяет canonical/source
границы текущего writer и точные context inputs; посторонний URI не нарушает
сессию. Отправителю не требуется знать preview другого клиента. Этот путь
передаёт URI и dirty/eventkind без текста и повторного хеширования всех буферов.

Чистый `change` с `dirty=false` не считается пользовательским вводом: это позволяет
второму клиенту принять XML disk reload, даже если у него нет origin preview.
Синхронизированный BSL `didChange` допускается только при точном совпадении с
ожидаемым editor-хешем текущего writer. Пользовательский ввод всегда дополнительно
сообщается как dirty ingress, даже если текст случайно совпал с ожидаемым результатом.
`open`/`close`/`save` и операции с файлами сообщаются как самостоятельные события;
ожидаемые собственные reload события origin-клиента буферизуются по правилам выше.
XML не добавляется в BSL `MemDocs`. При will-save/file operation клиент дожидается
ответа на ingress до продолжения операции.

Клиент с собственной сессией также может немедленно отправить
`{"sessionId":"server-session-token","violation":true}`. Это нарушение отличается
от обычной отмены: после первой записи сервер сохраняет версии и возвращает
`recovery_required`. Общий writer учитывает наблюдаемые сигналы всех участвующих
клиентов. Чужие несогласованные процессы по-прежнему ограничиваются проверкой
известных файловых версий и условием эксклюзивной сессии.

Конечный ответ содержит `transaction`, `status`, `reason` и `changedUris`.
Статус `committed` означает завершённый набор операций; `rolled_back` означает
восстановление исходных файлов. `recovery_required` означает сохранённые версии
и журнал для разбирательства: чужие байты не перезаписываются ради отката.
Путь журнала — общий пользовательский cache `bsl-analyzer/metadata-rename`.
Числовые коды LSP-ошибок не разрешают повтор записи.

## Восстановление после обрыва

Preview не восстанавливает исходники сам. Если есть незавершённый журнал, он
возвращает `operation="recover"`. При совпадении разрешённых корней и контекста
ответ содержит отдельный `sessionId`; обычный rename-план пока не выдаётся.
Клиент показывает пользователю, что сначала требуется восстановление, и только
после подтверждения эксклюзивной сессии отправляет commit этого токена.

Сервер сравнивает текущее состояние с известными версиями журнала и выполняет
обратные операции. После полного восстановления ответ содержит
`status="recovered"`, `rebuildPreview=true` и `receipts`; клиент перестраивает
обычный preview. При чужой версии или неизвестной привязке корней возвращается
`recovery_required`; новые применения остаются запрещены. Форсировать исходные
байты поверх чужой версии нельзя.

В recovery preview `files[].afterText` содержит исходный текст из журнала для
восстанавливаемого пути. Клиент использует его для распознавания собственного
reload тем же способом, что при обычном rename. Если файлы уже были полностью
применены, но не была опубликована общая модель, recovery session повторяет
только конечную сверку/публикацию и затем разрешает новый preview.
Признак незавершённой публикации сохраняется в журнале ещё до изменения
исходников и удаляется после проверки конечных байтов, публикации модели и
последней проверки сигналов участников под общей блокировкой допуска чтения.
Поэтому сбой или позднее нарушение между durable terminal журнала и публикацией
видно после перезапуска. Уже завершённый commit в такой recovery session не
откатывается: сервер сверяет его конечные версии и публикует модель. Отмена,
полученная после durable terminal, также не превращается в принудительный undo.

## Отмена

Метод `bsl/metadataRenameAbort` получает `{"sessionId":"server-session-token"}`.
Он удаляет сохранённый preview или просит прервать текущий commit. Ответ
`{"aborted":true}` подтверждает получение запроса; конечный статус выполняющегося
commit приходит ответом на исходный commit. Клиент ждёт его перед продолжением.
`$/cancelRequest` также передаёт отмену worker. В эксклюзивной сессии отмена после
первой записи выполняет журнал отката. Поздняя отмена после durable terminal не
отменяет уже завершённую транзакцию. При shutdown сервер дожидается результата
worker; обрыв процесса оставляет журнал для следующей явной recovery session.
