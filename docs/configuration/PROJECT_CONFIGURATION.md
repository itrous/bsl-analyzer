# Конфигурация проекта

Этот документ описывает общую структуру `bsl-analyzer.toml`: где лежит файл,
какие верхнеуровневые секции поддерживаются и как проверять конфигурацию.

Параметры конкретных диагностик вынесены отдельно в
`docs/configuration/DIAGNOSTICS.md`.

## Какие форматы поддерживаются

При автоматической загрузке конфигурации используется такой приоритет:

1. `bsl-analyzer.toml`
2. `.bsl-analyzer.json`
3. `.bsl-language-server.json`

Важно:

- если `bsl-analyzer.toml` найден, но не парсится, fallback на JSON не
  выполняется;
- legacy JSON поддерживается только как слой совместимости со старым tooling;
- для новых проектов основным форматом считается `bsl-analyzer.toml`.

## Где должен лежать файл

Обычно конфигурация лежит в корне проекта:

```text
my-project/
├─ bsl-analyzer.toml
├─ src/
└─ ...
```

Для CLI можно передать явный путь:

```bash
bsl-analyzer analyze -s ./my-project -c ./configs/bsl-analyzer.toml
```

## Минимальный пример

```toml
# Необязательно: целевая версия платформы 1С.
target_platform_version = "8.3.27.1644"

[source]
root = "src/cf"

[diagnostics]
ordinaryAppSupport = false
dataflowMaxIterations = 10000

[diagnostics.parameters]
CommentedCode = false

[formatting]
use_tabs = true
indent_size = 1
```

## Верхнеуровневая структура `bsl-analyzer.toml`

### `target_platform_version`

Необязательная целевая версия платформы 1С для versioned семантических
каталогов:

```toml
target_platform_version = "8.3.27.1644"
```

Допустимы три или четыре числовых компонента (`8.3.27` или `8.3.27.1644`).
Каталог глобальных имён аттестован для всей release-линии из первых трёх
компонентов. Если ключ не задан, используется версия встроенного каталога —
сейчас `8.3.27`. В legacy JSON тот же ключ записывается как
`targetPlatformVersion` (также принимается `target_platform_version`).

Если значение некорректно либо указывает на другую release-линию, анализатор
не считает промах в платформенном каталоге доказательством отсутствия: правила
наподобие `UnresolvedName` молчат, а host записывает предупреждение об
unsupported target. Это безопасная деградация, а не переключение каталога на
ближайшую версию.

### `[platform_help]`

Источник справки платформы (синтаксис-помощника): типы, методы, свойства,
конструкторы и их описания, которые питают hover, completion, разрешение
имён и платформенные проверки.

```toml
[platform_help]
source = "external"
path = "platform-help/platform_data.json"
```

| `source` | Что загружается |
|---|---|
| `auto` | Сохранённый для `auto` снимок, затем установленная платформа, затем закреплённый корпус из репозитория `itrous/bsl-platform-help`, затем встроенные факты интерфейса. **Умолчание.** |
| `external` | Ровно один из `path` — каталог пакета с `manifest.json`, сам `manifest.json` или прежний `platform_data.json` — либо `url` манифеста пакета. |
| `installed` | HBK установленной платформы: `path`, затем `BSL_PLATFORM_PATH`, затем стандартные каталоги установки. |
| `none` | Справка отключена: без поиска, распаковки и сети. |
| `bundled` | Только встроенные факты интерфейса: имена, сигнатуры, параметры, типы, версии, контексты — без описаний. Без поиска, распаковки и сети. |

`installed` и `auto` читают HBK собственным кодом анализатора, без 7z и других
внешних программ, и не изменяют файлы установки. Извлечённый корпус кэшируется
в каталоге пользователя (`~/.cache/bsl-analyzer/platform-help/`, переопределяется
`BSL_PLATFORM_HELP_CACHE_DIR`) и переиспользуется, пока не изменились пути и
содержимое обоих HBK. Из нескольких найденных установок выбирается наибольшая
числовая версия каталога; выбранный путь пишется в журнал. Версия справки берётся
из имени каталога установки (`8.3.27.2214`), если оно — номер версии.

`auto` хранит собственный снимок: при доступной установке использует или
обновляет его, после исчезновения установки читает сохранённый; снимки других
источников он не использует.

Если ни снимка, ни установки нет, `auto` скачивает закреплённый корпус —
файл release-asset `https://github.com/itrous/bsl-platform-help/releases/download/corpus-3c759994/platform_data.json`. Его SHA-256 вкомпилирован в анализатор:
файл с другим содержимым отвергается. Проверенный корпус сохраняется в
`<кэш>/pinned/…` вместе с `NOTICE.md`, и следующие запуски берут его оттуда без
сети. Если скачать не удалось и копии нет — справки нет, в журнале причина.
Переменная `BSL_PLATFORM_HELP_PINNED_URL` задаёт своё зеркало вместо этого
адреса; пустое значение отключает скачивание. Файл зеркала по SHA-256 не
сверяется — за его содержимое отвечает тот, кто зеркало задал; проверяется лишь,
что это корпус справки. Копия зеркала кэшируется отдельно для каждого адреса. Явно заданные источники (`installed`, `external`,
`none`) к закреплённому корпусу и к встроенным фактам никогда не переходят.

`external` с `url` указывает на `manifest.json` опубликованного пакета: анализатор
скачивает манифест и корпус, сверяет SHA-256 и формат и только после этого
заменяет свою копию для этого URL (`<кэш>/external/…`). Если URL недоступен или
отдаёт негодный пакет, используется последний валидный пакет **этого же** URL с
предупреждением; если его нет — справки нет. Пакеты других URL, `installed` и
`auto` не подставляются. В сеть ходят только `external` с явно заданным `url`
и `auto` за закреплённым корпусом.

Относительный `path` отсчитывается от каталога файла конфигурации. Неизвестное
значение `source`, лишнее поле или пустой путь — ошибка конфигурации. Явно
заданный источник никогда не подменяется другим: если он не загрузился,
справки нет, в журнале — предупреждение с причиной, а анализатор продолжает
работу. Собственные реестры анализатора, каталог глобальных имён EDT и
статическая справка по ключевым словам от источника справки не зависят.

Без `[platform_help]` действует `auto`; на машине без установленной 1С, без
сохранённого снимка и без доступа к закреплённому корпусу (и его копии в кэше)
`auto` отдаёт встроенные факты интерфейса: типы, методы, свойства, конструкторы
и глобальные функции платформы 8.3.27.2214 с сигнатурами, параметрами, версиями
и контекстами, но без описаний. Hover и completion по платформенным типам
работают, тексты описаний пусты; в журнале — причина, по которой полный корпус
не загрузился. Встроенные факты не содержат текстов 1С
(`crates/bsl-platform/data/PROVENANCE.md`). Чтобы получить описания, укажите
установку или пакет.

Источник выбирается один раз при запуске процесса (LSP, `analyze`, MCP).
После изменения `[platform_help]` работающий сервер продолжает отвечать по
прежней справке и предупреждает, что для смены источника нужен перезапуск.

Статус справки для `target_platform_version` пишется в журнал при запуске:
`available` (версия корпуса известна и совпадает с release-линией цели),
`unverified` (версия неизвестна — так у JSON без манифеста),
`unsupported_target` (другая release-линия) или `missing` (только при `none`
или отказе явно заданного источника). Статус справки не участвует в
доказательстве отсутствия глобальных имён: это делает только каталог EDT.

В legacy JSON та же настройка записывается как `platformHelp` (принимается и
`platform_help`).

### `min_platform_version`

Необязательная МИНИМАЛЬНАЯ версия платформы, на которой код проекта обязан
компилироваться, — для проектов, которые разрабатываются на новой
платформе, а в рабочей базе работают на старой:

```toml
min_platform_version = "8.3.17"
```

Пока ключ не задан, диагностика `PlatformMemberNewerThanMinVersion` полностью
молчит. С ключом она сообщает каждое использование элемента платформы (глобальной
функции или свойства, типа в `Новый`, метода или свойства значения типа
платформы, объявления `Асинх` / оператора `Ждать`), который по каталогу доступен
только с более поздней версии: на минимальной платформе такой модуль не
скомпилируется (глобальная функция, `Асинх`) или упадёт при выполнении (метод или
свойство значения). Режим совместимости 8.3.x этого не меняет — новые элементы он не
скрывает (проверено на 8.3.17 и 8.3.27); то, что он всё-таки скрывает (30 глобальных
имён), проверяет отдельное правило — см. `compatibility_mode` ниже.

Допустимы два-четыре числовых компонента (`8.3`, `8.3.17`, `8.3.17.1549`);
сравниваются major.minor.patch, номер сборки не учитывается. Нечисловое значение
выключает проверку (host пишет предупреждение). На `target_platform_version` ключ
не влияет: каталог по-прежнему один. В legacy JSON — `minPlatformVersion` (также
принимается `min_platform_version`). CLI `analyze` читает ключ из того же файла
конфигурации, что и остальные настройки, — найденного в корне `-s` или
переданного через `-c`.

### `compatibility_mode`

Необязательный режим совместимости, в котором компилируется код проекта:

```toml
compatibility_mode = "8.3.15"   # или "Version8_3_15", "DontUse"
```

Откуда берётся режим, по старшинству:

1. эта настройка;
2. `<CompatibilityMode>` в `Configuration.xml` ОСНОВНОЙ конфигурации проекта
   (`Version8_2_13`, `Version8_3_17`, `DontUse`);
3. ни того ни другого — режим неизвестен.

Режим один на проект: модули расширений работают в режиме расширяемой
конфигурации, а внешние обработки и отчёты компилируются в режиме той базы, в
которой их открыли (проверено живьём на 8.3.17 и 8.3.27), — поэтому для внешних
обработок проекта действует режим его конфигурации. Настройка нужна, когда выгрузка
`src` не отражает базу заказчика: например, выгрузка говорит 8.2.13, а у заказчика
8.3.15 — тогда в настройке указывают режим ЗАКАЗЧИКА.

По режиму работает диагностика `PlatformMemberHiddenByCompatibilityMode`: 30
глобальных имён (`СтрНайти`, `СтрРазделить`, побитовые функции, функции регулярных
выражений, `КопииБазыДанных` …) и свойство `Запрос.ТребуемаяАктуальностьДанных`,
которые режим ниже своего порога скрывает. Режим `DontUse` и неизвестный режим
ничего не скрывают; значение, которое не является режимом, выключает проверку (host
пишет предупреждение). Принимаются `8.2.13`, `Version8_2_13`, `Версия8_2_13`,
`DontUse`, `НеИспользовать`. В legacy JSON — `compatibilityMode` (также
принимается `compatibility_mode`). На `min_platform_version` и
`target_platform_version` режим не влияет.

### `[source]`

Определяет корень основной конфигурации 1С и расширений:

```toml
[source]
root = "src/cf"
extensions = [
  "src/cfe/BMS_RU_UT",
  "src/cfe/YAxUnit",
]
```

`root` — локальный корень основной конфигурации, то есть та, что лежит внутри репозитория. Это полноправный и наиболее частый способ задать базу. Если же базовая конфигурация хранится вне проекта, в общем на машину хранилище выгрузок, вместо `root` используйте read-only зависимость:

```toml
[source]
extensions = ["Расширения/MyExtension"]

[source.configuration]
id = "UT11"
version = "11.5.22.129"
```

`project-model` разрешает её как `${ONEC_CONFIGURATIONS_ROOT}/UT11/11.5.22.129`. `ONEC_CONFIGURATIONS_ROOT` берётся сначала из process environment, затем из `.env` рядом с выбранным `bsl-analyzer.toml`; поиск `.env` вверх по каталогам не выполняется. `id` и `version` должны быть безопасными именами одного каталога без `/`, `\` и `..`. `root` и `[source.configuration]` одновременно задавать нельзя. Если базовая конфигурация проекту не нужна, не задавайте ни `root`, ни `[source.configuration]`: extension-only проект является корректным.

Если ни один вариант не задан, `project-model` пытается найти основную конфигурацию сам: поиском `Configuration.xml` в пределах двух уровней и по конвенционным каталогам `src/cf` и `Configuration`. Каталоги, определённые как расширения по `ConfigurationExtensionPurpose`, за базовую конфигурацию не принимаются.

`extensions` — список расширений конфигурации (CFE). При отсутствии явного списка расширения ищутся автообнаружением в конвенционных контейнерах `src/cfe/`, `cfe/` и `Расширения/` — первый существующий выигрывает. Каждый элемент — либо
строка-путь относительно корня проекта (в последнем сегменте допустим глоб
`*`), либо структурированная запись со стабильным именем:

```toml
[source]
root = "src/cf"
extensions = [
  "src/cfe/BMS_RU_UT",                                              # строка-путь
  { name = "yaxunit", path = "vendor/yaxunit" },                    # именованная запись
  { name = "TESTS", path = "src/cfe/TESTS", dependsOn = ["yaxunit"] },
]
```

Каждый путь должен указывать на каталог с `Configuration.xml`. Метаданные
расширений видны автокомплиту и диагностике наравне с основной конфигурацией.

Отличия двух форм:

- **Строка-путь** ведёт себя как раньше: имя выводится из имени каталога,
  отсутствующий путь или каталог без `Configuration.xml` пропускается
  с предупреждением, текстовые варианты одного пути схлопываются.
- **Структурированная запись** строгая: отсутствующий путь, каталог без
  `Configuration.xml`, глоб в `path`, дубль имени или пути — ошибка загрузки
  проекта, а не предупреждение. `dependsOn` принимает имена других расширений
  (допустима и snake_case-форма `depends_on`).

`dependsOn` объявляет направленную зависимость между расширениями
(`A dependsOn B` — «A использует API B»). Граф валидируется при загрузке:
неизвестные имена, самоссылки, дубли рёбер и циклы (с полным путём цикла)
отклоняются до начала анализа.

Видимость по зависимостям: файл расширения `E` видит базовую конфигурацию,
транзитивные зависимости `E` (в стабильном топологическом порядке) и само
`E` — последним. Обратной видимости нет (`B` не видит `A`), независимые
расширения не видят друг друга, файл базовой конфигурации не видит ни одного
расширения. При поиске имени приоритет у самого расширения, затем у ближайшей
зависимости, затем у базы; оверлеи метаданных накладываются в прямом порядке
(база → зависимости → своё расширение), так что унаследованные реквизиты
сохраняются.

Команда `bsl-analyzer-app check-config bsl-analyzer.toml` печатает секцию
`Extension topology` — разобранные узлы, рёбра, детерминированный порядок
и отпечаток топологии.

Изменение топологии применяется вживую, без перезапуска. Отпечаток топологии
входит в идентичность всех производных состояний: LSP пересканирует воркспейс
и добавляет новые корни расширений в наблюдение; персистентный граф MCP и
резидентная база диагностик считают снапшот устаревшим и перестраиваются
(даже если ни один `.bsl`/`.xml` не менялся — например, правка только
`dependsOn`); кэшированный граф с другой топологией не переиспользуется;
поисковый индекс перерендеривает графовый контекст документов; а брокер MCP
разводит клиентов с разными топологиями по разным демонам (старый демон
доживает по idle-TTL).

`externals` — внешние обработки и отчёты (выгрузки EPF/ERF), анализируемые
против основной конфигурации проекта. Ключ трёхзначен, как `extensions`:
не задан — автообнаружение раскладок `src/epf/*` и `src/erf/*` (запасные
варианты — `epf/*` и `erf/*` в корне проекта; обе семьи сканируются, вид
объекта берётся из корневого тега выгрузки, а не из имени контейнера);
`externals = []` — явный отказ; непустой список — ровно он, обнаружение
выключено. Только именованная форма:

```toml
[source]
root = "src/cf"
externals = [
  { name = "АРМПроизводство", path = "src/epf/АРМПроизводство" },
  { name = "Отчет", path = "src/erf/Отчет", dependsOn = ["ЯxUnit"] },
]
```

Выгрузка опознаётся по `<Имя>.xml` с элементом `ExternalDataProcessor` или
`ExternalReport` под `MetaDataObject`. Обнаруженный каталог, который такой
выгрузкой не является, пропускается с предупреждением, а не роняет проект; то же
для пустого имени каталога, двух обнаруженных выгрузок одного объекта и имени
каталога, совпадающего с именем расширения или другой выгрузки (остаётся первый
по порядку путей). Имя обнаруженной выгрузки — имя её каталога.

Автообнаружение не спускается в дополнительные контейнеры вроде `managed`.
Для вложенной раскладки укажите каждую выгрузку явно:

```toml
[source]
root = "src/cf"
externals = [
  { name = "АРМ", path = "src/epf/managed/АРМ" },
  { name = "Сводка", path = "src/erf/managed/Сводка" },
]
```

CLI `analyze` и MCP `diagnostics` проверяют доступный текстовый BSL модуля
объекта, управляемой и обычной формы. Бинарный EPF/ERF сначала нужно выгрузить:
отсутствие текстового модуля не означает, что он проверен без ошибок. Для MCP
пустой список диагностик считается результатом только после готовности
резидента, без `stale` и ошибки `not_in_workspace`. `ParseError` относится к
синтаксису; разрешение имён требует семантического контекста, а полноценная
проверка платформой выполняется отдельно в 1С.

У объявленной записи `path` указывает на каталог выгрузки: в нём лежит ровно один
`<Имя>.xml`, чей первый элемент под `MetaDataObject` — `ExternalDataProcessor` или
`ExternalReport`, и рядом каталог `<Имя>/` с формами и модулями. Всё остальное —
ошибка загрузки проекта, а не предупреждение: каталог с `Configuration.xml`
(это конфигурация или расширение, объявленные не тем ключом), выгрузка
внутренней обработки (`<DataProcessor>`), `MetaDataObject` без элемента (выгрузка
оборвана), несколько выгрузок в одном каталоге, отсутствующий путь, две выгрузки
одного объекта под разными `name` (имя объекта
берётся из `<Имя>.xml` без учёта регистра и является его идентичностью в графе
и словаре имён MCP — один проект держит одну выгрузку на имя объекта).

Видимость: без `dependsOn` модуль внешней обработки видит базовую конфигурацию
и **все** расширения проекта в топологическом порядке — обработка исполняется в
той информационной базе, которую описывает проект, с подключёнными расширениями.
`dependsOn` сужает вид до транзитивного замыкания перечисленных именованных
расширений; `dependsOn = []` — только база. Её саму не видит никто: ни база, ни
расширения, ни другие внешние обработки, поэтому внешняя обработка не бывает
целью `dependsOn` — такое ребро отклоняется при загрузке. Режим видимости входит
в отпечаток топологии. Имя обработки живёт в одном реестре с именами расширений:
у объявленной записи совпадение — ошибка дубля.

Без базовой конфигурации (`root` / `[source.configuration]` не заданы) модули
внешних обработок анализируются против одной платформы, а обращения к
конфигурации помечаются `UnresolvedMethodCall`; CLI, LSP и статус MCP при этом
предупреждают, что владеющая конфигурация не задана.

Корни внешних обработок входят в отпечаток топологии наравне с расширениями и
регистрируются в поисковом индексе MCP со своим `root_id`, так что одноимённая
внутренняя обработка конфигурации и её внешняя выгрузка — два разных объекта.
В базовой линии диагностик внешняя обработка образует собственный раздел
`external:<имя>`; у проектов без внешних обработок отпечаток области не меняется.

#### `exclude`

`exclude` — список каталогов, которые исключаются из проекта целиком:

```toml
[source]
root = "src/cf"
exclude = [".tmp", ".v8vscedit/import-temp"]
```

- Пути задаются относительно каталога, где лежит `bsl-analyzer.toml` (при
  `--config` — каталога указанного файла), а не относительно `[source].root` и
  не относительно текущего каталога процесса. `.` означает сам этот каталог.
- Значения — буквальные относительные пути каталогов. Глобы и маски не
  поддерживаются, абсолютный путь или пустая строка — ошибка конфигурации.
  Сравнение идёт по компонентам пути: исключение `.tmp` не задевает `.tmp2`.
- Отсутствие ключа и `exclude = []` ничего не меняют.
- Каталог может ещё не существовать: исключение действует и для каталога,
  созданного после старта.
- Исключение побеждает любой корень: если оно совпадает с `root`, каталогом
  расширения или внешней обработки либо содержит его, этот корень выпадает из
  проекта и никаким объявлением не возвращается. Проект, у которого так исключены
  все корни, анализирует пустой набор исходников — это не ошибка.
- Исключённое поддерево не обходится при сканировании проекта, не попадает в
  VFS и индекс, не ставится под наблюдение файловой системы (в том числе каталоги,
  созданные в рантайме) и не читается загрузчиками метаданных. Это действует
  одинаково в LSP, CLI (`analyze`, сборка поисковой базы) и MCP. Файл из
  исключённого каталога, открытый в редакторе, не анализируется.
- Изменение `exclude` применяется при штатной перезагрузке конфигурации. Если
  конфиг лежит в исключённом каталоге — например, `exclude = ["."]` при
  `bsl-analyzer.toml` в корне проекта, — наблюдение за самим конфигом тоже
  снимается: новое значение подхватится по сохранению файла в редакторе
  (didSave) или после перезапуска сервера.

> Все ключи должны быть внутри секции `[source]`. Если `extensions` окажется
> выше `[source]`, парсер отклонит конфиг с ошибкой — это намеренно, чтобы
> исключить тихое присваивание в «не ту» таблицу TOML.

> Существующий, но синтаксически некорректный `bsl-analyzer.toml` — ошибка
> загрузки проекта (CLI завершится с ошибкой, LSP покажет сообщение и не
> поднимет воркспейс). Отката к конфигурации по умолчанию при битом файле
> больше нет: молчаливый откат означал бы анализ «не того» проекта.

## Задание состава исходников без файла конфигурации

Тот же состав — корень основной конфигурации и расширения — задаётся флагами
`analyze` и `check-config`. Это нужно, когда файл конфигурации в дерево проекта
класть нельзя: без указания основной конфигурации расширение анализируется в
одиночку, не видит её метаданных и экспортных общих модулей, и валидные
обращения помечаются `UnresolvedMethodCall`.

```
--configuration-root <PATH>              корень основной конфигурации
--extension <NAME=PATH | PATH>           повторяемый
--extension-depends-on <NAME=DEP[,DEP…]> повторяемый
--no-extensions                          анализировать без расширений
--external <NAME=PATH>                   внешняя обработка/отчёт, повторяемый
--external-depends-on <NAME=DEP[,DEP…]>  повторяемый; NAME= — только база
--no-externals                           анализировать без внешних обработок
```

Пример:

```bash
bsl-analyzer-app analyze -s /проект \
  --configuration-root src/cf \
  --extension yaxunit=vendor/yaxunit \
  --extension TESTS=src/cfe/TESTS \
  --extension-depends-on TESTS=yaxunit
```

Флаги замещают поля секции `[source]` **независимо**: заданный `--extension` не
трогает корень из файла, и наоборот. Не заданное флагом поле остаётся таким,
каким его объявил файл.

`--no-extensions` — явный отказ от расширений, тот же, что `extensions = []` в
файле. Без него «не задано» означает наследование: список из файла либо
автодискавери `src/cfe/*`.

`--external NAME=PATH` замещает список `externals` из файла целиком. Только
именованная форма: голого пути здесь не существует. `--no-externals` — явный
отказ, тот же, что `externals = []` в файле; без него «не задано» означает
наследование: список из файла либо автодискавери `src/epf/*`, `src/erf/*`.
Один каталог, названный и через `--extension`, и через `--external`, — ошибка
запуска.

`--external-depends-on NAME=DEP[,DEP…]` сужает вид внешней обработки `NAME` до
расширений `DEP`; `NAME=` с пустой правой частью — только база. Владелец обязан
быть объявлен через `--external NAME=PATH`, каждая цель — через
`--extension NAME=PATH`; повторы для одного владельца накапливаются.

Две формы `--extension` соответствуют двум формам записи в файле:

- `NAME=PATH` — строгая именованная запись. Отсутствующий каталог, каталог без
  `Configuration.xml`, глоб в пути, дубль имени или пути — ошибка запуска.
  Только на такие записи можно вешать зависимости.
- `PATH` — мягкая строковая запись: имя выводится из имени каталога, глоб в
  последнем сегменте допустим, ненайденный путь пропускается с предупреждением.

`--extension-depends-on NAME=DEP[,DEP…]` объявляет, что расширение `NAME`
использует API расширений `DEP`. Обе стороны обязаны быть объявлены через
`--extension NAME=PATH`; имена сравниваются без учёта регистра. Повторы для
одного владельца накапливаются, то есть `--extension-depends-on T=A,B` и
`--extension-depends-on T=A --extension-depends-on T=B` описывают одни и те же
рёбра.

### Чем флаги строже файла

Строка, набранная в командной строке, — ошибка этого запуска, а не чужая
устаревшая запись в файле, поэтому:

- `--configuration-root` на каталог без `Configuration.xml` — ошибка запуска.
  Одноимённый ключ файла в этом случае лишь предупреждает и уходит в автопоиск;
  для флага это недопустимо, иначе команда молча проанализирует другую
  конфигурацию.
- Один и тот же каталог, названный дважды литеральными формами `--extension`, —
  ошибка запуска в любом порядке. Сравниваются канонические пути, поэтому
  разные написания и симлинки на один каталог тоже считаются дублем.
  Пересечение глоба с литералом ошибкой не является: глоб задаёт множество.

### База относительных путей

Относительные пути во флагах разрешаются от корня проекта **той команды,
которая их получила**:

- у `analyze` — от `-s/--source-dir`;
- у `check-config` — от каталога файла, переданного в `-c/--config`.

То есть `analyze -s /ws --configuration-root base` даёт `/ws/base`, а
`check-config -c /cfg/bsl-analyzer.toml --configuration-root base` — `/cfg/base`.
Абсолютный путь работает в обеих командах.

ОГРАНИЧЕНИЕ: каталог, в имени которого есть `=`, в голой форме задать нельзя —
значение всегда делится по первому `=` на имя и путь. Если при этом оба чтения
указывают на существующее расширение (есть и каталог `wanted=real`, и каталог
`real`), команда отказывается работать и называет обе трактовки: выбирать за
пользователя означало бы проанализировать не тот каталог. Разрешается это
явным именем — `--extension NAME=wanted=real`: деление идёт по первому `=`,
поэтому остаток целиком становится путём. Абсолютный путь не помогает, `=` в
нём остаётся.

### Откуда взят состав

`check-config` печатает источник отдельно для корня и для списка расширений —
они решаются независимо:

```
  Source root: src/cf [from: cli]
  Extensions:  yaxunit (vendor/yaxunit)
  Extensions from: bsl-analyzer.toml
```

Значения: `cli`, имя файла конфигурации, `auto-discovery`. Объявленный в файле
корень без `Configuration.xml` показывается как проигнорированный — решение в
этом случае принимает автопоиск, а не файл.

### `[analysis]`

Ограничение области анализа: диагностики выдаются только по файлам и строкам,
отличающимся от эталонного git-ref (обычно ветка `vendor` с выгрузкой
поставщика). Индексация и вывод типов при этом по-прежнему покрывают всю
конфигурацию — фильтр действует только на замечания.

```toml
[analysis]
diff_base = "vendor"
ignored_authors = ["Фирма 1С"]
```

- `diff_base` — git-ref, относительно которого считается diff
  (`merge-base(diff_base, HEAD)` против рабочей копии, включая
  незакоммиченные и untracked-файлы). Не задан — анализируется всё.
- В CLI `analyze` область можно задать и флагами (приоритет сверху вниз):
  `--diff-filter report.json` (готовый JSON в формате rtools `diff-report`),
  `--incremental --git-diff <ref>`, `--incremental --changed-files a.bsl,b.bsl`;
  без флагов берётся `diff_base` из конфига. `--git-diff` и `--changed-files`
  взаимоисключающие: два конкурирующих явных источника — ошибка ввода.
- Недоступный репозиторий или несуществующий ref при заданной области — жёсткая
  ошибка запуска `analyze` (молчаливый полный анализ в CI хуже отказа).
- В JSON-конфигах ключ пишется как `analysis.diffBase`.

`ignored_authors` — фильтр по авторам через git blame, для конфигураций без
vendor-ветки: замечание подавляется, если **все** строки его диапазона в
последний раз менял автор из списка; любая «своя» строка сохраняет замечание.

- Сопоставление — точное совпадение с именем **или** email автора коммита
  (с учётом `.mailmap`). Точную строку имени подскажет
  `git log --format='%aN <%aE>'` (заглавные `N`/`E` — уже с учётом mailmap,
  как сравнивает и анализатор).
- Незакоммиченные правки и untracked-файлы никогда не фильтруются; целиком
  переименованный файл сохраняет авторство исходных строк.
- Поверхности: CLI `analyze` (флаг `--ignored-author <имя>` повторяемый,
  список из флагов **заменяет** список из конфига) и MCP `diagnostics`
  (счётчики `findings_ignored_by_author`). LSP-диагностики фильтр пока НЕ
  применяют — сервер однократно предупреждает об этом клиента.
- Shallow-клон делает атрибуцию недостоверной: CLI завершается ошибкой
  (`git fetch --unshallow`), MCP отключает фильтр с предупреждением в логе.
- Назначение — конфигурации **без** vendor-ветки: на ERP полный прогон с
  фильтром снимает ~95% замечаний (52 мин против ~4 мин без него — blame
  дорог). При настроенном `diff_base` фильтр авторов избыточен: изменённые
  относительно vendor строки и так принадлежат команде.
- В JSON-конфигах ключ пишется как `analysis.ignoredAuthors`.

### `[diagnostics]` и `[diagnostics.parameters]`

В этой секции задаются общие флаги диагностики и параметры конкретных правил.

Базовый вид:

```toml
[diagnostics]

[diagnostics.parameters]
LineLength = { maxLineLength = 140 }
BadWords = true

```

Полный список поддерживаемых ключей и параметров — в
`docs/configuration/DIAGNOSTICS.md`.

### `[code_lens]`

Поддерживаются два булевых флага:

```toml
[code_lens]
show_cognitive_complexity = true
show_cyclomatic_complexity = true
```

В JSON-совместимом формате им соответствуют camelCase-ключи
`showCognitiveComplexity` и `showCyclomaticComplexity`.

### `[formatting]`

Настройки форматтера:

```toml
[formatting]
use_tabs = true
indent_size = 1
```

Поддерживаемые поля:

- `use_tabs` — использовать табы;
- `indent_size` — размер одного уровня отступа.

### `[output]`

Управляет языком пользовательских сообщений анализатора — имён примитивных
типов в диагностиках (`'Число'` vs `'Number'`), hover-карточек и
completion-detail.

```toml
[output]
display_language = "ru"   # или "en"
```

Поддерживаемые значения для `display_language`:

- русский: `"ru"`, `"ru-RU"`, `"ru_RU"`, `"russian"`;
- английский: `"en"`, `"en-US"`, `"en_US"`, `"en-GB"`, `"en_GB"`, `"english"`.

Сравнение регистронезависимое, пробелы по краям обрезаются. Неизвестное
значение логируется как `tracing::warn!` и игнорируется — анализатор
переходит к следующему сигналу локали (см. ниже), а не падает на загрузке
проекта.

Поддерживается также camelCase-алиас `displayLanguage` для совместимости с
JSON-форматом.

#### Приоритет источников локали

Эффективная локаль определяется по убыванию приоритета:

1. `[output] display_language` в `bsl-analyzer.toml` — фиксирует язык на
   уровне проекта (команда видит одинаковый язык независимо от настроек
   IDE у конкретного разработчика).
2. `InitializeParams.locale` от LSP-клиента (RFC 4646: `"ru-RU"`,
   `"en-US"`, …). Учитывается только primary-subtag: `"ru-RU"` → `ru`,
   `"de-DE"` → `en` (всё, что не русский, считается английским).
3. Дефолт анализатора — `ru`. BSL — русскоязычный язык-первого-класса:
   при отсутствии всех сигналов выводятся русские имена типов.

При CLI-запуске LSP-сигнала нет, поэтому работают только `[output]
display_language` и дефолт.

> Локализуются только **имена типов**, подставляемые в сообщения. Каркасы
> диагностик (текст «Несоответствие типов: ожидалось …, получено …»)
> сейчас захардкожены русскими — это сознательное ограничение текущего
> уровня i18n.

### `[diagnostics.baseline]`

```toml
[diagnostics.baseline]
path = ".bsl-analyzer-diagnostics-baseline.json"
```

`path` разрешается относительно фактического файла конфигурации и должен
оставаться внутри канонического корня проекта. Цель не может быть символической
ссылкой. Область файла фиксирует корень основной конфигурации и упорядоченную
топологию расширений, поэтому изменение имени, пути или `dependsOn` требует
осознанного пересоздания либо обновления базовой линии.

Для больших проектов рекомендуется независимый набор файлов:

```toml
[diagnostics.baseline]
directory = ".bsl-analyzer/diagnostics-baselines"
include = ["main", "group:vendor"]

[[diagnostics.baseline.groups]]
name = "vendor"
extensions = ["VendorCore", "VendorReports"]
```

Анализ по-прежнему выполняется один раз по полной топологии. `directory` лишь
разделяет записи между `main`, каждым расширением вне группы и явно заданными
группами. `path` и `directory` взаимоисключающие; прежний `path` полностью
совместим и остаётся форматом одного файла версии 1.
Вычисленный идентификатор раздела (`main`, `extension:<имя>` или `group:<имя>`)
не может превышать 64 байта UTF-8.

`include` — необязательный allowlist логических идентификаторов разделов. Только они
получают policy `baseline`; остальные владельцы остаются в полном анализе с policy
`unsuppressed`, поэтому их замечания видимы, а их baseline objects не читаются и не
наблюдаются. Удаление `include` возвращает режим полного набора.

Это не `analysis.diff_base`: diff ограничивает анализ текущими изменениями и даёт
частичный результат, а базовая линия диагностик сопоставляет известные замечания
только после полного анализа. Это также не `[search.baseline]`, который управляет
централизованным индексом поиска и не влияет на диагностики.

### `[search.baseline]`

Секция описывает настройки централизованного baseline для поиска.

Минимальный пример для PostgreSQL backend:

```toml
[search.baseline]
backend = "postgres"

[search.baseline.postgres]
schema = "bsl_search"
url_env = "BSL_SEARCH_BASELINE_PG_URL"

[search.baseline.workspace_code.policy]
publish_branches = ["vendor", "develop"]
```

### Префиксы входа эмбеддера

Для модели, различающей вопрос и документ, задайте литеральные префиксы:

```toml
[search.baseline.embedding]
queryPrefix = "search_query: "
documentPrefix = "search_document: "
```

MCP и CLI публикации разрешают каждый префикс независимо: явно заданное поле
проекта → `EMBEDDING_QUERY_PREFIX` / `EMBEDDING_DOCUMENT_PREFIX` → пустая строка.
Явное `documentPrefix = ""` отключает префикс документа даже при непустом
значении окружения. Пробелы и переводы строк сохраняются буквально. Вопрос
получает префикс вопроса, background и interactive batches — префикс документа;
lexical-поиск продолжает использовать исходный текст вопроса.

Без новых настроек HTTP-вход и идентификатор модели в legacy cache сохраняются.
При непустом префиксе storage identity учитывает оба префикса и wire model alias;
изменение любого префикса требует совместимого индекса. Используйте отдельный
cache для пилота. Непустой cache неизвестного или чужого профиля не очищается
автоматически и не принимается как источник новых векторов.

Имя модели, отправляемое HTTP-сервису, должно закреплять checkpoint, tokenizer,
pooling, dtype, нормализацию и token policy. При изменении этих условий задавайте
новый alias. Префиксы готовит клиент: server default prompt должен быть отключён.
Существующий порядок разрешения model/URL этим дополнением не меняется.

### Ограничение code embedding по токенам

Полностью заданная тройка включает разбиение кода с сохранением исходных байтов:

```toml
[search.baseline.embedding]
maxInputTokens = 8192
tokenizerFile = "artifacts/tokenizer.json"
tokenizerSha256 = "80d0433a2cfc55a4561b0e98b6f822decc48c9d457db498837223f9385ef3aff"
```

Каждое поле разрешается независимо: значение проекта → `EMBEDDING_MAX_INPUT_TOKENS`,
`EMBEDDING_TOKENIZER_FILE`, `EMBEDDING_TOKENIZER_SHA256` → отсутствие. Путь проекта
относится к каталогу TOML, путь окружения — к source workspace. Отсутствие всей
тройки сохраняет прежнее поведение. Частичная тройка, пустое значение, неверный лимит,
отсутствующий файл или несовпадение SHA256 дают `embedding_invalid_config` до HTTP.
Файл загружается локально, без скачивания; tokenizer и транспортные лимиты
фиксируются на время процесса. Truncation и padding выключены, special tokens
учитываются вместе с префиксом, заголовком и graph context.

Большие методы делятся на адресуемые UTF-8 части без обрезки исходного текста.
Query не разбивается: превышение лимита возвращает `embedding_input_too_large`,
сохраняя lexical fallback. Документация платформы не сегментируется.
Профиль включает tokenizer hash, лимит, алгоритм и byte envelope в storage identity.
Используйте отдельные cache и PostgreSQL schema; чужой непустой layout отвергается
до записи данных. Возврат к профилю без token policy требует прежнего отдельного cache.

## Проверка конфигурации

### Быстрая проверка через `check-config`

Команда `check-config` умеет читать и TOML, и legacy JSON:

```bash
bsl-analyzer check-config --config ./bsl-analyzer.toml
```

```bash
bsl-analyzer check-config --config ./.bsl-analyzer.json
```

В сводке можно увидеть:

- `source.root` и подключённые extensions;
- сводку по diagnostics;
- отключённые, явно включённые и параметризованные правила;
- code lens;
- formatting;
- workspace/reference baseline selection.

### Проверка в реальном запуске

Для end-to-end проверки можно запустить анализ с явным конфигом:

```bash
bsl-analyzer analyze -s ./my-project -c ./bsl-analyzer.toml
```

## Совместимость с legacy JSON

Legacy-формат всё ещё поддерживается. В нём встречаются camelCase-ключи:

```json
{
  "configurationRoot": "src/cf",
  "diagnostics": {
    "ordinaryAppSupport": false,
    "dataflowMaxIterations": 10000,
    "parameters": {
      "LineLength": { "maxLineLength": 120 }
    }
  }
}
```

Это нужно только для совместимости со старой экосистемой. Для новых проектов
рекомендуется `bsl-analyzer.toml`.
