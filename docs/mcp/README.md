# MCP-сервер: установка и профили

Этот документ отвечает на два вопроса:

- какой MCP-профиль нужен в вашем сценарии;
- как установить его в AI-клиент без ручного редактирования конфигов.

Описание самих инструментов и подключение к базе 1С вынесены в
`docs/mcp/TOOLS_AND_EXTENSION.md`.

## Как устроены профили

`bsl-analyzer` публикует два отдельных MCP-профиля.

| Профиль | Для чего нужен | Что обычно требуется |
|--------|----------------|----------------------|
| `reference` | справка платформы, поиск по документации, `syntax_help`, `its_help` | при необходимости `EMBEDDING_URL` и `NAPARNIK_TOKEN` |
| `workspace` | поиск по коду проекта, metadata, SDBL, выполнение BSL-кода, debug | `--source-dir`; для live-инструментов ещё `--onec-url` и учётные данные |

Для нескольких ИБ используйте один `workspace`: скопируйте
`docs/mcp/onec-connections.example.json` за пределы репозитория, заполните и
передайте путь через `BSL_ONEC_CONNECTIONS_FILE`; живые инструменты выбирают
профиль параметром `connection`. Пароли задаются только переменными окружения,
указанными в реестре.

Расширение VS Code запускает языковой сервер отдельным процессом
`bsl-analyzer-app --stdio`. MCP-профиль `workspace` использует локальный
посредник и Unix-сокет, поэтому порты и сеансы с языковым сервером не делит.
Несколько MCP-клиентов одного проекта, напротив, переиспользуют один тяжёлый
сервер посредника.

Практическое правило:

- ставьте `reference`, если AI должен знать платформу и ИТС;
- ставьте `workspace`, если AI должен работать с конкретным репозиторием;
- чаще всего нужен комплект из обоих профилей.

> `reference` не использует `--source-dir` и не принимает параметры подключения
> к 1С. Live-доступ к базе относится только к `workspace`.

## Рекомендуемая установка

Самый удобный сценарий — установить оба профиля сразу:

```bash
bsl-analyzer mcp install \
  --target all \
  --preset recommended \
  --source-dir ./my-project
```

Этот preset делает следующее:

- `reference` ставится как user-scoped конфигурация;
- `workspace` ставится как project-scoped конфигурация для текущего репозитория.

Если нужны дополнительные возможности, добавьте переменные окружения и
параметры подключения:

```bash
bsl-analyzer mcp install \
  --target all \
  --preset recommended \
  --source-dir ./my-project \
  --env NAPARNIK_TOKEN=your_token \
  --env EMBEDDING_URL=http://localhost:8000/v1/embeddings \
  --env EMBEDDING_API_KEY=your_api_key \
  --onec-url http://localhost/base/hs/bsl-analyzer \
  --onec-user admin
```

## Установка по отдельности

Только глобальный профиль справки:

```bash
bsl-analyzer mcp install \
  --target all \
  --preset reference \
  --scope user \
  --env NAPARNIK_TOKEN=your_token \
  --env EMBEDDING_URL=http://localhost:8000/v1/embeddings \
  --env EMBEDDING_API_KEY=your_api_key
```

Только проектный профиль рабочего каталога:

```bash
bsl-analyzer mcp install \
  --target all \
  --preset workspace \
  --scope project \
  --source-dir ./my-project
```

Поддерживаемые scope'ы по целевым клиентам:

| Target | Поддерживаемые scope'ы | Как применяется |
|--------|-------------------------|-----------------|
| `codex` | `user`, `project` | user через CLI `codex mcp add`, project через `.codex/config.toml` |
| `gemini` | `user`, `project` | через CLI `gemini mcp add` |
| `claude` | `user`, `project`, `local` | через CLI `claude mcp add` |
| `cursor` | `user`, `project` | через merge в `mcp.json` |

## Полезные флаги `mcp install`

- `--dry-run` — показать итоговую команду или конфиг без записи на диск;
- `--force` — обновить существующую MCP-запись с тем же именем;
- `--name custom-bsl` — изменить базовое имя сервера;
- `--env KEY=value` — передать переменные окружения для MCP-процесса;
- `--onec-password` — сохранить пароль в конфиге целевого клиента.

Если пароль передаётся через `--onec-password`, он попадает в аргументы
запуска MCP-сервера. Для небезопасных контуров лучше использовать отдельные
тестовые учётные данные.

## Ручной запуск серверов

Если нужно сначала проверить профиль локально, можно запустить его вручную.
Для профиля `workspace` брокер включён по умолчанию на всех платформах, включая
Windows: транспорт — named pipe с security descriptor, ограниченным текущим
пользователем, с проверкой личности backend'а (защита от подмены имени pipe).
Принудительно вернуться на прямой `stdio` можно переменной `BSL_MCP_BROKER=0`.

Глобальный профиль справки:

```bash
bsl-analyzer mcp serve --profile reference
```

Профиль проекта:

```bash
bsl-analyzer mcp serve --profile workspace --source-dir ./my-project
```

### Опт-ин инструменты: `--enable-tool`

Часть инструментов сборка умеет, но по умолчанию не отдаёт. Пока запуск их не
назвал, такого инструмента нет в `tools/list`, а вызов по имени получает ту же
ошибку, что вызов несуществующего: сборка не сообщает клиенту, что могла бы его
обслужить.

**В текущей сборке опт-ин один — `references`** в профиле `workspace`: полный
список ссылок на символ (см. `docs/mcp/TOOLS_AND_EXTENSION.md`). Полный список
ссылок на популярное имя — большой ответ, и профиль, отдающий его без спроса,
тратил бы контекст агента на вопрос, которого тот не задавал. Действующий
список всегда брать из `opt_in_tools` декларации, а не отсюда: здесь он
устареет, там — нет.

```bash
bsl-analyzer mcp serve --profile workspace --source-dir ./my-project \
  --enable-tool references
```

Ключ повторяемый. Имена берутся из `opt_in_tools` декларации, а **не** из
`tools/list`: опт-ин инструмента в списке как раз нет, пока запуск его не
назвал. Имя, которого профиль не объявляет, останавливает старт и печатает
список допустимых; молча отброшенного ключа не бывает. Назвать инструмент,
который профиль и так отдаёт, разрешено и ничего не меняет — благодаря этому
конфиг с ключом продолжит работать в релизе, где инструмент станет умолчанием.

Что сборка **умеет** и что она отдаёт **по умолчанию** — две разные величины, и
обе объявлены в декларации контракта (`docs/mcp/CONTRACT.md`): умеет —
объединение `tools` и `opt_in_tools`, по умолчанию — `tools`.

Прописать ключ сразу в конфиг клиента:

```bash
bsl-analyzer mcp install --target claude --preset workspace --enable-tool <имя>
```

Имя сверяется с профилем пресета прямо при установке, поэтому записанный конфиг
не может оказаться таким, который откажется стартовать.

`--preset recommended` опт-ин инструменты не включает никогда и отвергает ключ,
а не отбрасывает его: включение — осознанное действие того, кто ставит.

Состав входит в идентичность брокерского бэкенда наравне с проектом, каталогом
кеша и профилем. Два запуска с разными наборами — разные демоны; запуск, назвавший
инструмент, который и так обслуживается, к разведению демонов не приводит. В режиме
`--mode broker-required` расхождение состава между супервизором и клиентом означает
разные ключи, то есть прокси не найдёт сокет и откажет — это верный исход:
подключиться к демону с чужой поверхностью хуже, чем не подключиться.

### Каталог кеша workspace

Граф вызовов, поисковый индекс, векторы и lease по умолчанию хранятся вне
исходников, в системном каталоге кеша. Каждый workspace и состав источников
получает отдельный каталог `<base>/workspaces/v1/<digest>/`:

| Платформа | База `<base>` по умолчанию |
|---|---|
| Linux | `${XDG_CACHE_HOME:-$HOME/.cache}/bsl-analyzer` |
| macOS | `~/Library/Caches/bsl-analyzer` |
| Windows | `%LOCALAPPDATA%/bsl-analyzer` |

Базу можно изменить флагом или переменной окружения:

```bash
bsl-analyzer mcp serve \
  --profile workspace \
  --source-dir ./my-project \
  --cache-dir ../.bsl-analyzer-cache
```

`--cache-dir` доступен только профилю `workspace` и задаёт **базу**, а не
точный каталог DB. Приоритет: флаг → `BSL_CACHE_DIR` → системная база.
Пустое выбранное значение — ошибка; непустой флаг имеет приоритет даже над
пустой переменной окружения. Относительный путь вычисляется от cwd процесса.
В broker-режимах daemon получает абсолютную базу и проверяет тот же состав;
namespace добавляется один раз. Профиль `reference` не использует `BSL_CACHE_DIR`.

Например, `--cache-dir /data/bsl-cache` размещает граф в
`/data/bsl-cache/workspaces/v1/<digest>/bsl-graph.db`. Там же находятся
`bsl-search.db`, SQLite WAL/SHM, vector sidecars, `writer.lease` и
`writer.lease.lock`, временный граф, его locks/stall report и opt-in daemon log.
State-журнал векторов, reference cache и broker runtime endpoints сохраняют
свои отдельные системные каталоги.

Digest зависит от канонического workspace, состава и порядка расширений,
их связей/видимости, физических source roots и пользовательских исключений.
Эквивалентные TOML/CLI declarations используют один кеш; разные составы
могут одновременно владеть отдельными кешами в одной базе. Изменение тела
BSL, mtime, версии бинарника, модели embedding или набора инструментов не
меняет каталог. Проверки актуальности содержимого остаются действующими.
Одинаковый состав использует прежнюю координацию писателей и takeover/version
arbitration внутри своего каталога.

Системная база не должна помещать namespace внутри workspace или любого
source root, в том числе через symlink. Такой запуск отклоняется до записи и
предлагает внешний override. Явный CLI/env override разрешает кеш внутри
исходников; `--cache-dir <source-dir>` тоже допустим, если семейство
`workspaces/v1` не содержит source root. Семейство исключается из
graph/search/watch целиком, включая соседние составы; остальные файлы базы
продолжают читаться. Source root внутри этого семейства запрещён.
Забытый `<source-dir>/.build` сохраняет прежнее исключение из обхода и не создаётся.

Недоступный явный кеш останавливает запуск. Отказ создания системного кеша
оставляет операции, которым запись не нужна, доступными и сообщает degraded
состояние; search/vector не пишут без подтверждённого владения lease.
Запасного кеша в исходниках нет. Если автоматический state-журнал или reference
cache пересекается с исходниками, соответствующий optional owner отключается
с диагностикой. Пересечение обязательного HTTP process record или broker
endpoint с source roots останавливает запуск до записи.

При изменении состава источников или невалидном конфиге сессия останавливает
писателей и закрывает MCP transport с сообщением
`workspace source composition changed; restart/reconnect MCP`.
Клиенту stdio/HTTP нужен перезапуск; новое broker-подключение вычисляет новый
состав и подключается к его backend. Обычные изменения BSL/XML, не меняющие
состав, обновляются в текущей сессии.

Первый запуск после переноса строит новый кеш холодно. Старые плоские DB в
`.build` или прежнем `--cache-dir` не читаются, не импортируются и не удаляются.
Даже `--cache-dir <source-dir>/.build` создаёт namespace под `.build`, сохраняя
старые файлы. Для rollback остановите новые процессы и верните прежний
бинарник и конфиг: старый бинарник использует прежние пути. Одновременный
запуск старого и нового layout не обеспечивает общую lease-координацию.

Профиль проекта с live-доступом к базе 1С:

```bash
bsl-analyzer mcp serve \
  --profile workspace \
  --source-dir ./my-project \
  --onec-url http://localhost/base/hs/bsl-analyzer \
  --onec-user admin \
  --onec-password secret
```

### Запуск по HTTP

Чтобы запустить профиль `workspace` по HTTP с доступом из локальной сети:

```bash
bsl-analyzer mcp serve \
  --profile workspace \
  --source-dir ./my-project \
  --mode http \
  --host 0.0.0.0 \
  --port 8021 \
  --allowed_hosts localhost 127.0.0.1 ::1 mcp-server.local
```

Вместо `--host`, `--port` и массива `--allowed_hosts` можно передать
`--config` с TOML-файлом:

```toml
host = "0.0.0.0"
port = 8021
allowed_hosts = ["localhost", "127.0.0.1", "::1", "10.9.9.10", "mcp-server", "mcp-server.local"]
```

```bash
bsl-analyzer mcp serve \
  --profile workspace \
  --source-dir ./my-project \
  --mode http \
  --config ./mcp-http.toml
```

- `--mode http` включает транспорт Streamable HTTP;
- `--port` задаёт обязательный порт от `1` до `65535`;
- `--host 0.0.0.0` открывает все сетевые интерфейсы; без параметра сервер
  доступен только на `127.0.0.1`;
- `--allowed_hosts` принимает массив имён и адресов сервера, по которым
  подключаются клиенты. Для нелокального `--host` массив не может быть пустым.
  Пустое значение не считается разрешённым именем и отвергается: иначе сервер
  запустился бы и отказывал всем. Заданный список заменяет встроенные локальные
  адреса целиком, поэтому для доступа с самой машины перечислите `localhost`,
  `127.0.0.1` и `::1` явно. Адрес привязки `0.0.0.0` (или `::`) сюда не годится:
  клиент шлёт в `Host` тот адрес, по которому подключался, а не адрес
  прослушивания, поэтому такая запись не разрешает почти ничего — при старте
  о ней предупреждает лог.
- `--config` принимает те же три настройки в полях `host`, `port` и массиве
  `allowed_hosts`. Обязателен только `port`: опущенный `host` привязывает
  `127.0.0.1`, опущенный `allowed_hosts` оставляет встроенные локальные имена —
  как и у отдельных флагов. Неизвестное поле отвергается, чтобы опечатка в имени
  ключа не подняла сервер не там, где написано. `--config` нельзя сочетать с
  отдельными HTTP-параметрами;
- оба варианта используются только с `--mode http`.

В примере MCP доступен по адресу `http://mcp-server.local:8021/mcp`. Одинаковые
HTTP-процессы одновременно не запускаются. Без `--mode http` поведение команды
не меняется.

HTTP-сервер забирает у демона того же состава и базы владение производными
кэшами — графом вызовов и поисковым индексом. Демон дослуживает своих
клиентов, перестаёт писать кэши и выходит по простою, поэтому держать оба режима
на одном проекте одновременно незачем.

Если нужна ручная интеграция в конкретный AI-клиент, обычно проще не писать
конфиг с нуля, а сначала выполнить `mcp install --dry-run` и использовать
показанную команду или сгенерированный фрагмент как образец.

## Эмбеддинги и семантический поиск

Семантическая составляющая поиска требует `EMBEDDING_URL`:

- `search(action=search_docs)` в профилях `reference` и `workspace`;
- семантическая ветвь `search(action=search_code)` в профиле `workspace`
  (лексическая ветвь `search_code` работает и без неё).

Если embedding-провайдер требует Bearer-авторизацию
(например, OpenRouter, OpenAI или совместимый сервис), дополнительно задайте
`EMBEDDING_API_KEY`.

Для задач семантического поиска по коду и документации разумно явно задавать
`EMBEDDING_MODEL`. Практический ориентир:

- `Qwen/Qwen3-Embedding-0.6B` — минимальная рекомендуемая модель и текущий
  дефолт в `bsl-analyzer`;
- `Qwen/Qwen3-Embedding-4B` — усиленный компромиссный вариант;
- `Qwen/Qwen3-Embedding-8B` — предпочтительный вариант, если позволяет ресурс.

Пример:

```bash
EMBEDDING_URL=https://openrouter.ai/api \
EMBEDDING_API_KEY=your_api_key \
EMBEDDING_MODEL=Qwen/Qwen3-Embedding-0.6B \
  bsl-analyzer mcp serve --profile reference
```

Если `EMBEDDING_URL` не задан, остаётся полнотекстовый `find_docs` в `reference`, а
`search_code` в `workspace` возвращает лексические результаты с пометкой
`-- semantic skipped: … --`.

Сейчас `bsl-analyzer` для embedding API поддерживает стандартный заголовок
`Authorization: Bearer ...` через `EMBEDDING_API_KEY`. Если конкретный
провайдер требует дополнительные нестандартные заголовки, это нужно учитывать
отдельно.

Если используется централизованный baseline в PostgreSQL, семантический поиск
комбинирует локальный runtime и shared baseline. Подробности — в
`docs/central-postgres-search/README.md`.

### Размер embedding-запросов и повторные попытки

`EMBEDDING_MAX_REQUEST_BYTES` задаёт максимальный размер одного HTTP JSON body
в байтах. По умолчанию это **1 048 576 байт (1 MiB)**; положительное целое из
окружения заменяет дефолт одинаково в MCP и CLI. При включённой семантике ноль,
нечисловое значение или переполнение дают `embedding_invalid_config` до сетевого
запроса, без вывода исходного значения. Настройка не добавляет секцию TOML;
библиотечный клиент задаёт `EmbedderConfig.max_request_bytes` напрямую.

`EMBEDDING_DIM` необязателен: не задан — поле `dimensions` не отправляется
вовсе, и запрос принимает эндпоинт, не поддерживающий параметр; ширину
объявляет сама модель. Индекс при этом строится на **1024** — модели другой
ширины требуют явного `EMBEDDING_DIM` (и эндпоинта, принимающего `dimensions`).
Заданное, но негодное значение (ноль, мусор) даёт `embedding_invalid_config` до
сетевого запроса.

Сборка и публикация разбивают работу одновременно по действующему лимиту числа
документов и точному размеру сериализованного запроса: учитываются UTF-8,
JSON-экранирование, модель, dimensions и provider routing. Равенство лимиту
допустимо. Один слишком большой документ даёт `embedding_input_too_large`:
содержимое не обрезается, не делится и не пропускается как успешно обработанное.
Пустой допустимый набор не отправляет запрос. Лимит ответа остаётся **10 MiB**;
лимит запроса не гарантирует, что ответ в него уложится.

`Embedder::batch_ranges(texts, max_items)` возвращает последовательные диапазоны
для существующих исполнителей. Прямые `embed_batch` и `embed_batch_interactive`
готовят ровно один запрос: слишком большой набор завершается локально с
`embedding_request_too_large`, без скрытого разбиения на несколько вызовов.
Индексы входов и соответствие векторам сохраняются; некорректные индексы или
размерность ответа дают `embedding_invalid_response`.

Пакетный путь делает максимум **10 попыток одного подготовленного запроса**,
таймаут каждой — **120 секунд**; интерактивный — **одну попытку, 12 секунд**.
Локальные ошибки настройки/размера и окончательные HTTP-отказы (4xx, включая 413,
кроме 408, 425 и 429) не повторяются; успешно завершённые
диапазоны не пересылаются из-за ошибки следующего. Разбиение может увеличить число
физических запросов, время сборки и стоимость. Общего нового таймаута сборки нет:
сохраняются действующие отмена, concurrency и бюджеты публикации.

Уже зафиксированные векторы сохраняются при последующем отказе, но незавершённая
попытка не публикует семантическую готовность. Коды отказа и доступность лексического
поиска описаны в [контракте `semantic_failure`](TOOLS_AND_EXTENSION.md#ошибки-эмбеддингов).
После смены значения перезапустите процесс с нужным окружением. Удаление override
возвращает дефолт 1 MiB. Откат на предыдущий бинарник и его конфигурацию не требует
миграции данных, но возвращает прежнее разбиение только по числу документов и не
решает проблему превышения payload.

## Совместимость indexing

Текущий machine contract — `3.3`: live metadata object использует schema `2` с полнотой и усечением;
успешные ответы поиска и graph lifecycle/loading
несут структурированный `indexing`, ответы поиска — необязательный `semantic_failure`.
Search hits/not-ready имеют schema `8` для `search_code` и `6` для docs-действий,
search status — `4`, graph descriptor — `35`; list_platform остаётся `1`.
Готовность lexical, semantic, graph и reference читается отдельно; unknown не
означает завершение. Точный формат, null/terminal правила и примеры описаны в
[TOOLS_AND_EXTENSION.md](TOOLS_AND_EXTENSION.md#структурированный-прогресс-индексации).

Бюджетируемые ответы поиска резервируют обязательный конверт; слишком маленький
`max_output_tokens` возвращает `budget_too_small` с `minimum_output_tokens`.
Статусы поиска и graph status/schema/resolve сохраняют исключения из бюджета.
Перед обновлением strict consumer проверяет новый contract и `tools/list`;
откат использует предыдущий binary вместе с его contract, без конвертации индекса.
