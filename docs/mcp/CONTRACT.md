# Декларация контракта: feature-detection вместо грепа `--help`

Потребителю нужно знать, что умеет конкретная сборка, до того как он её вызовет.
Без декларации единственная наблюдаемая поверхность — текст `--help` и проза в
описаниях инструментов, поэтому чужой CI начинает проверять контракт поиском
подстрок: переформулировали строку справки — CI сломался, переименовали параметр
— не заметил.

`bsl-analyzer` отдаёт обе свои поверхности машиночитаемо.

## Как получить

Из CLI — обе поверхности сразу, без MCP-хендшейка:

```bash
bsl-analyzer contract
```

Из MCP-сессии — стандартными `resources/list` + `resources/read`:

```
uri: bsl-analyzer://contract
```

Это ресурс, а не инструмент: декларация нужна потребителю для проверки
совместимости, а не агенту для работы, и 13-й инструмент тратил бы токены
описания в каждой сессии.

## Что внутри

```jsonc
{
  "contract_version": "4.0",
  "build_version": "0.2.80",
  "mcp": {
    "profiles": {
      "workspace": {
        "tools": [
          {
            "name": "diagnostics",
            "actions": [
              { "name": "catalog", "required": [] },
              { "name": "file", "required": ["path"] }
            ],
            "params": [
              { "name": "action", "type": "string", "required": true },
              { "name": "path", "type": "string", "required": false }
            ]
          }
        ],
        "opt_in_tools": [
          {
            "name": "references",
            "actions": [],
            "output_schema_version": "1",
            "params": [{ "name": "symbol", "type": "string", "required": false }]
          }
        ]
      },
      "reference": { "tools": [], "opt_in_tools": [] }
    }
  },
  "transports": {
    "workspace": {
      "broker-required": {
        "backend_pid_required": true,
        "backend_pid_source": "supervisor launching bsl-analyzer-app directly",
        "auto_launch": false,
        "stdio_fallback": false,
        "peer_identity": "supervised-pid+platform-trust",
        "platforms": ["android", "freebsd", "fuchsia", "linux", "netbsd", "openbsd", "redox", "windows"]
      }
    }
  },
  "cli": {
    "name": "bsl-analyzer",
    "args": [],
    "commands": [
      {
        "name": "analyze",
        "args": [
          {
            "name": "source-dir",
            "short": "s",
            "aliases": ["srcDir", "src", "project"],
            "required": false,
            "takes_value": true,
            "default": ["."]
          },
          {
            "name": "format",
            "required": false,
            "takes_value": true,
            "values": ["console", "jsonl"],
            "default": ["console"]
          }
        ]
      }
    ]
  }

```

Пояснения к полям:

- В контракте `3.2` `metadata` сохраняет прежние поля live object, добавляет `completeness` и `truncated`
  в `schema_version="2"`; live `tree` и `object` учитывают `max_output_tokens` для `content` и
  `structuredContent` вместе.
- В контракте `3.3` `search` публикует `output_schema_version="9"` в workspace и `"7"` в reference,
  `syntax_help` — `"2"`, `symbol_info` — `"1"`. `syntax_help` и справочные
  действия `search(action=find_docs|search_docs|list_platform|status)` доступны
  не только в `reference`, но и в `workspace`; отдельный профиль `reference`
  остаётся совместимым, но больше не обязателен для справки платформы.
- Контракт `4.0` меняет смысл `execute(action=check)`: он использует нативный профиль
  выбранного именованного подключения и возвращает структурированный `schema_version="1"`.
  `compiler.compatibility` — сериализованный токен режима из XML применённой конфигурации;
  на платформе 8.3.27.1989 runtime-значение `НеИспользовать` представлено токеном
  `Version8_3_27`, а не отдельным режимом runtime.
  Без профиля результат `unsupported`; прежний HTTP `/check-syntax` не вызывается.
  `run`/`eval` сохраняют прежние HTTP DTO и разрешения. `execute` намеренно не публикует
  единый `outputSchema`, поскольку эти действия возвращают разные формы.

- `tools` — то, что сервер отдаёт в `tools/list` при обычном запуске;
  `opt_in_tools` — то, что эта же сборка умеет, но отдаёт только по явному
  `mcp serve --enable-tool <имя>`. Читать их так: «сборка умеет» — объединение
  двух массивов, «получу без ключа» — `tools`, «нужен ключ» — принадлежность к
  `opt_in_tools`. Записи в обоих массивах одинаковой формы, поэтому потребитель
  разбирает их одним кодом. Опт-ин инструмент невидим в `tools/list` и при
  вызове неотличим от несуществующего — feature-detect делается по декларации,
  а не пробным вызовом.
- `required` у действия — параметры, обязательные именно для него; `required` у
  параметра — обязательность на уровне схемы, то есть для любого действия.
- `note` появляется там, где требование не выражается схемой: например
  «`metadata tree` в режиме infobase требует `meta_type`» или «`symbol_info`
  требует либо `symbol`, либо `path`+`line`».
- `params` подняты прямо из JSON-схемы, которую сервер публикует в `tools/list`,
  поэтому имена, типы и обязательность не могут разойтись с тем, что сервер
  действительно принимает.
- `nullable: true` — параметр принимает не только отсутствие, но и явный `null`;
  `required: false` сам по себе говорит только о первом.
- `output_schema_version` означает, что инструмент публикует стандартный
  `outputSchema` в `tools/list`. `structuredContent` несёт `schema_version`
  соответствующего варианта ответа: у `search` это `8` (`search_code`) и `6`
  (справка) для hits/`not_ready`, `4` для `status` и `1` для `list_platform`. Поле отсутствует у инструментов
  без стабильной структурированной формы ответа.
- Описания инструментов и параметров в декларацию **не входят**: это проза для
  агентов, она есть в `tools/list`, и её присутствие здесь означало бы, что
  каждая переформулировка выглядит как изменение контракта — ровно та беда, ради
  которой декларация и заводилась.
- `global: true` у флага означает, что он принимается и подкомандами; такие
  флаги перечислены один раз на корне, а не продублированы под каждой командой.
- `multiple: true` — флаг принимает повторение: многозначным диапазоном,
  накоплением списка (в том числе через `value_delimiter`) или счётчиком
  (`-vvv`).
- `aliases` / `short_aliases` включают и скрытые псевдонимы: скрытость влияет на
  `--help`, но не на то, что сборка принимает. В `values` попадают и псевдонимы
  значений перечисления.
- `index` есть у позиционных аргументов: список аргументов отсортирован по имени,
  и порядок позиционных восстанавливается только по нему.
- `conflicts_with` перечисляет флаги, которые нельзя указывать вместе, и всегда
  симметричен: clap отвечает только со стороны того аргумента, где ограничение
  объявлено, а отвергает пару в любом порядке — декларация описывает поведение
  парсера, а не место написания атрибута.
- `transports.workspace.broker-required` объявляет контролируемый режим, в
  котором proxy требует PID уже запущенного daemon, не запускает его сам и не
  возвращается к прямому stdio.
- `platforms` у этого режима — не список текущей сборки, а вся поддерживаемая
  область: привязка к процессу опирается на PID пира в учётных данных сокета.
  На macOS и DragonFly BSD его там нет, поэтому режим отвергается при старте, а
  не отказывает на каждом соединении. Публикуется тот же список, по которому
  CLI пускает режим, поэтому разойтись они не могут.
- `backend_pid_source` называет, откуда берётся значение для `--backend-pid`:
  его знает супервизор, потому что сам запустил бэкенд. Запускать для этого
  нужно `bsl-analyzer-app`, а **не** установленный `bsl-analyzer`: последний —
  лаунчер, он запускает анализатор ребёнком и ждёт его, поэтому сокетом владеет
  не тот процесс, чей PID виден супервизору.
  Значение остаётся внешним по построению: пин имеет смысл ровно потому, что
  приходит от того, кто запускал, а не из артефакта, доступного на запись
  любому процессу того же пользователя.
  Что пин доказывает: сокету отвечает процесс, держащий этот номер **сейчас**,
  запущенный тем же пользователем и с того же образа. Чего не доказывает:
  тождества с изначально запущенным процессом после его смерти — номер PID не
  несёт ни поколения, ни времени старта, и ОС выдаёт его заново. Супервизору,
  которому этого мало, следует не переиспользовать PID умершего демона.
  Если демон супервизора завершился сразу после старта, значит бэкенд для этого
  воркспейса уже был запущен и демон проиграл ему привязку сокета: proxy в этом
  случае называет PID действительного владельца, а не просто отказывает.
- Для инструмента с версионированным `structuredContent`
  `output_schema_fingerprint` фиксирует точную опубликованную `outputSchema`;
  потребитель проверяет и версию, и отпечаток, не разбирая текстовое описание.

### Чего в декларации нет

Взаимные требования флагов. Ограничение вида «`--changed-files` требует
`--incremental`» не объявлено: clap отдаёт публичным геттером только конфликты
(`Command::get_arg_conflicts_with`), а для `requires` геттера нет — переписывание
руками вернуло бы ровно то расхождение, ради устранения которого декларация и
сделана. Отсутствие ограничения читается как «не объявлено», а не как «любая
комбинация допустима».

## Версия контракта

`contract_version` намеренно отделена от `build_version`: патч-релиз анализатора
не должен выглядеть как изменение контракта, а переименование параметра —
должен.

- **major** — инструмент, действие или параметр удалён либо переименован,
  параметр стал обязательным, изменился смысл существующего поля;
- **minor** — добавлен инструмент, действие, параметр, допустимое значение или
  структурированная форма ответа.

Поле, переставшее утверждать ложное, смысла не меняет: `freshness.stale` графа, который
с `2.3` отвечает `true`, пока за воркспейсом никто не следит (`drift_watch` `starting` /
`unobserved`), а раньше мог назвать себя свежим, — исправление, и версия поднята как minor
вместе с появлением `drift_watch` (`docs/mcp/LOCATION_CONTRACT.md`).

Потребителю разумно требовать точный major и минимальный minor:

```python
major, minor = contract["contract_version"].split(".")
assert major == "4" and int(minor) >= 0
```

`build_version` остаётся в документе, но для feature-detection он не нужен —
именно ради этого и введена отдельная версия.

Контракт `3.3` ввёл текущие на тот момент схемы `search`; контракт `4.0` сохраняет их
без изменений и отдельно меняет `execute(action=check)`. Инструмент `search` публикует
`outputSchema` версии `9` в workspace и `7` в reference:
hits и `not_ready` используют `schema_version="8"` для `search_code` и `"6"` для справки, `status` обоих профилей —
`"4"`, `list_platform` сохраняет `"1"`. Добавлены необязательное поле статуса `embedding_profile`
и необязательный закрытый объект
`semantic_failure` с кодом embedding-ошибки; отсутствие поля не доказывает
готовность семантики. Версия и `output_schema_fingerprint` доступны через CLI и
ресурс `bsl-analyzer://contract`; точная форма проверяется через `tools/list`.
При ошибке `search_docs` этот объект находится в RPC `error.data`, которое
проверяется отдельно от успешной `outputSchema`. Формы и примеры —
[«Ошибки эмбеддингов»](TOOLS_AND_EXTENSION.md#ошибки-эмбеддингов).

## Что заменяет проверку по `--help`

Было (проверка текста справки):

```python
("bsl-analyzer analyze source-dir/jsonl", "bsl-analyzer",
 ["analyze", "--help"], ["--source-dir", "--format", "jsonl"]),
```

Стало (проверка контракта):

```python
contract = json.loads(subprocess.check_output(["bsl-analyzer", "contract"]))
analyze = next(c for c in contract["cli"]["commands"] if c["name"] == "analyze")
args = {a["name"]: a for a in analyze["args"]}
assert "source-dir" in args
assert "jsonl" in args["format"]["values"]
```

## Как это не протухает

Со стороны репозитория декларация удерживается тестами:

- CLI-поверхность целиком выводится интроспекцией живого clap-дерева, поэтому
  переименованный флаг или исчезнувшее значение перечисления попадают в
  декларацию автоматически;
- параметры MCP-инструментов поднимаются из схем самого роутера, а тест
  проверяет, что каждый параметр, объявленный обязательным для действия,
  действительно существует у инструмента;
- сообщения `Unknown action '…'. Expected: …` генерируются из тех же таблиц, что
  и декларация, поэтому список действий, который видит агент, и список, который
  читает потребитель, — одна и та же строка по построению;
- поскольку из этих же таблиц берутся и сообщения об ошибках, сверка одних строк
  с другими ничего не доказала бы: отдельный тест поднимает настоящий сервер и
  для каждого объявленного обязательного параметра вызывает инструмент без него,
  требуя отказа именно по этому параметру. Так расхождение таблицы с кодом
  диспетчера ловится поведением, а не текстом;
- снапшот-тесты (`cargo test -p mcp-server contract`,
  `cargo test -p bsl-analyzer contract_surface`) показывают любое изменение
  поверхности в диффе того коммита, который его вносит, рядом с
  `contract_version` — это и есть напоминание её поднять.

## Отношение к действию `schema`

`schema` у `query`, `graph` и `diagnostics` описывает **форму ответа** и остаётся
на месте: это другой вопрос, чем «что сборка принимает». Декларация контракта
отвечает на второй вопрос и не требует достраивать `schema` до всех инструментов.

Третья ось — версия самого объекта места (`schema_version` внутри `location`). Она
общая для всех инструментов и потому не может версионироваться номером одного из них;
описание — `docs/mcp/LOCATION_CONTRACT.md`.
