# Свойства метаданных из HTTP-сервиса

Ответ `/metadata-structure` сохраняет прежние `name`, `full_name`, `synonym` и
коллекции реквизитов. Дополнительно `read_properties` содержит прочитанные факты,
а `enum_values` — все значения выбранного перечисления с именами и синонимами.
Отсутствующее поле у старого producer означает неизвестный состав;
`enum_values: []` означает подтверждённо пустое перечисление.

Пример справочника:

```json
{"read_properties":{"synonym":{"ru":"Товары"},"synonym_complete":false,"hierarchical":true,"hierarchy_type":"HierarchyFoldersAndItems","code_type":"String","code_length":9,"code_allowed_length":"Fixed","members":[{"path":["Attribute","Article"],"synonym":{"ru":""},"synonym_complete":false,"use_mode":"ForFolderAndItem"}]}}
```

Ключ карты синонимов — фактический код текущего языка сеанса. HTTP API возвращает
только доступный перевод; `synonym_complete: false` сохраняется у объекта,
реквизита, табличной части, её реквизита и значения перечисления. `{"ru":""}`
подтверждает пустой русский перевод и не подтверждает отсутствие остальных
переводов. Если язык не удалось определить, карта не выдаётся. Прежний строковый
`synonym` остаётся доступен старым клиентам.

`members[].path` чередует вид XML-элемента и техническое имя:
`["TabularSection","Rows","Attribute","Quantity"]`. Используются виды
`StandardAttribute`, `Attribute`, `Dimension`, `Resource`, `TabularSection`,
`EnumValue`. `use_mode` сравнивается с конкретными значениями системного
перечисления и возвращается техническим именем, например `ForItem`, `ForFolder`
или `ForFolderAndItem`. Локализованное представление не преобразуется в token.
Так же возвращаются `hierarchy_type`, `code_type`, `code_allowed_length`,
`periodicity` и `write_mode`; примеры последних — `Nonperiodical` и `Independent`.
Неподдержанное значение остаётся неизвестным.

`fill_value` сохраняет XML-тип, лексическое значение и признак отсутствия:

```json
{"type_name":"{http://www.w3.org/2001/XMLSchema}string","value":"","nil":false,"fields":[]}
```

Это типизированная пустая строка. Подтверждённо незаданное заполнение имеет
`type_name: null`, `value: ""`, `nil: true`, `fields: []`. Ошибка чтения свойства
или отсутствие поддержанной XML-сериализации оставляет `fill_value` неизвестным;
представление значения не выдаётся за XML-значение. Стандартные поля читаются из
действительной коллекции платформы, без добавления предполагаемых полей
независимому регистру или неиерархическому справочнику.

Для непустой ссылки справочника `fill_value` может дополнительно содержать
`runtime_predefined_identity`:

```json
{"metadata_type":"Catalog","metadata_name":"OwnCountries","predefined_name":"OwnCountry","runtime_ref_uuid":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa"}
```

Это отдельное native-свидетельство: producer проверяет уже инициализированную
область, техническое имя предопределённых данных и обратное полное имя ссылки.
UUID относится к ссылке ИБ, а не к ItemID source XML. Поля `type_name`, `value`,
`nil`, `fields` не меняются. Поддержан только проверенный `CatalogRef`;
примитивы, перечисления и пустые ссылки не получают такого свидетельства.
Если оно недоступно для непустого `CatalogRef`, MCP сохраняет исходное значение
и отмечает `runtime_predefined_identity_unavailable`. Несогласованные тип,
имя или UUID сохраняются с `invalid_runtime_predefined_identity` и `partial`.
Отсутствующее свидетельство не доказывает равенство `DesignTimeRef` и runtime
ссылки. Producer не создаёт предопределённые записи ради получения имени.

Для плана счетов `/metadata-structure` дополнительно возвращает
`predefined_accounts` и `predefined_unread`. Отсутствующий массив означает
недоступный состав старого producer или непрочитанные данные; `[]` подтверждает
пустой набор. Элементы адресуются техническим `name` и содержат `code`,
`description`, техническое XML-значение `account_type`, `off_balance`, `order`,
`accounting_flags` и упорядоченные `ext_dimension_types`.

`runtime_reference.uuid` — UUID ссылки ИБ, а не ItemID из source `Predefined.xml`.
`runtime_reference.parent_known_empty: true` с `parent_uuid: null` подтверждает
корневой счёт; `false` требует UUID родителя, а `null` оставляет родителя
неизвестным. Пустой, некорректный или нулевой UUID и противоречивое состояние
родителя сохраняются в ответе, но дают `partial` с `invalid_runtime_identity`.
Эта же проверка применяется к UUID вида субконто.

В строках субконто сохраняются `runtime_ref_uuid`, доступный `predefined_name`,
`turnover`, `predefined` и признаки учёта `{name, enabled}`. Успешно прочитанная
пустая строка имени сохраняется как `""`; ошибка чтения остаётся `null`.
Данные читаются только в уже инициализированной области: producer не вызывает
`InitializePredefinedData` или методы изменения этого состояния.
MCP `metadata.object` с `predefined_code` выбирает точный код и отклоняет
неоднозначный; неполный набор не доказывает отсутствие запрошенного кода.
В source-режиме `root_id: ""` выбирает базовую конфигурацию, а имя расширения
выбирает его вместе с видимыми ему зависимостями. Без `root_id` сохраняется
поиск по всему workspace. В `source_origins` счёта указаны дескрипторы
планов счетов с именами корней, из которых получено его эффективное определение.
Source-ответ показывает значения из выгрузки конфигурации с учётом расширений.
В режиме `infobase` producer читает значения, записанные в ИБ. Прикладные
обработчики и учётная политика могут изменить признаки учёта, порядок и
состав субконто после инициализации предопределённых данных.

MCP сохраняет эти факты в карточке и явно отмечает неполноту языков,
недоступных свойств и усечение общего ответа. Примеры совместимости находятся в
`crates/bsl-analyzer/tests/fixtures/live_metadata_read_properties.json`.
Проверка API на существующей ИБ подтверждает отдельные операции чтения;
приёмка обновлённого producer требует отдельного применения расширения и
сравнения HTTP/MCP с исходниками той же конфигурации.
