# Нативная проверка BSL отдельным исполнителем

`bsl-native-check` принимает один JSON-запрос через stdin до EOF и возвращает
один ответ в stdout. MCP запускает его как обычный дочерний процесс без shell.
Формат запроса, ответа и caller-профиля описан в
[контракте версии 1](check-contract/README.md).

Исполнитель собирается отдельно:

```sh
cargo build --locked -p bsl-check-executor --bin bsl-native-check
cargo test --locked -p bsl-check-executor
```

Для сборки и unit-тестов установленная 1С не требуется. Для нативного вызова
нужны Designer и соседний `ibcmd` одной подтверждённой сборки, Python 3 и права
чтения применённой конфигурации источника. На Linux для запуска без рабочего
стола можно указать `xvfb_run_path`; Windows работает без Xvfb.

## Установка бинарника

После включения исполнителя в релиз Linux и Windows получают отдельные файлы
`bsl-native-check-linux-amd64` и `bsl-native-check-windows-amd64.exe`.
Они входят в общий `checksums.txt` и attestation релиза. Исполнитель не
устанавливается автоматически вместе с launcher анализатора; macOS в первую
целевую матрицу не входит.

Проверьте SHA-256 скачанного файла по `checksums.txt`, сохраните его в локальном
каталоге программ и на Linux разрешите исполнение. Укажите абсолютный путь в
`check_executor.program` caller-профиля. Для проверки запуска без 1С используйте
`bsl-native-check --help`; для компиляции дополнительно нужны локальный registry
и инструменты платформы, описанные ниже. При обновлении заменяйте бинарник
после завершения активных проверок.

## Локальный registry исполнителя

Caller передаёт фиксированные аргументы `--config <file> --profile demo`.
Имя `connection` в wire-запросе должно точно совпадать с выбранным профилем.
Registry исполнителя имеет собственный корень `profiles`:

```json
{
  "profiles": {
    "demo": {
      "designer_path": "/opt/1cv8/x86_64/8.3.27.1989/1cv8",
      "python_path": "/usr/bin/python3.12",
      "xvfb_run_path": "/usr/bin/xvfb-run",
      "expected_build": "8.3.27.1989",
      "work_root": "/var/lib/bsl-check-executor/demo",
      "source_kind": "server",
      "source_connection_env": "BSL_NATIVE_SOURCE",
      "runtime_url_env": "BSL_NATIVE_RUNTIME_URL",
      "user_env": "BSL_NATIVE_USER",
      "password_env": "BSL_NATIVE_PASSWORD"
    }
  }
}
```

Пути должны указывать на существующие локальные инструменты и собственный
рабочий каталог. На Windows задайте пути к `1cv8.exe`, `python.exe` и рабочему
каталогу; `ibcmd.exe` должен находиться рядом с Designer. Поле
`xvfb_run_path` пропустите. Linux work root принадлежит запускающему
пользователю и имеет режим `0700`.

Registry содержит имена переменных окружения. Значения подключения и
учётные данные получает только локальный процесс из разрешённого источника
секретов. Храните registry и источник секретов с ограниченным доступом;
не помещайте значения в примеры, shell history или отчёты. Для файлового
источника задайте `source_kind: "file"` и передайте через
`source_connection_env` путь к собственной тестовой файловой ИБ.

`runtime_url_env` требуется серверному источнику даже при отсутствии HTTP URL
в caller-профиле. Исполнитель читает через существующий сервис фиксированный
trusted паспорт. Проверяемый текст в этот HTTP-вызов не попадает. Установка
или ремонт сервиса источника в проверку не входят.

Каждый вызов получает пять обязательных wire limits. Эффективные лимиты
задаёт caller; `reap_timeout_ms` остаётся его локальной настройкой.
Неподдержанный набор bounds отвергается до создания compiler job.

## Границы проверки и восстановление

Designer проверяет одноразовую копию применённых метаданных без бизнес-данных.
Для толстого клиента управляемого приложения исполнитель использует
`/CheckConfig -ThickClientManagedApplication`; остальные поддержанные
контексты проверяет через `/CheckModules`. Перед проверкой входа ошибочный
контрольный модуль подтверждает, что каждый выбранный контекст проверяется.
Входной BSL не исполняется. Передавайте тип модуля и точный metadata
owner/origin либо явно выбранный synthetic context. Успешная компиляция
не доказывает существование обработчиков событий формы, работу интерфейса
или фактические права пользователя.

Рабочий каталог содержит приватные ownership manifests. При недоказанной
очистке исполнитель сохраняет manifest, возвращает `cleanup_failed` и
блокирует новую компиляцию в загрязнённом root. Следующий запуск выполняет
адресное recovery только доказанно собственных объектов. Не удаляйте
manifests или глобальные X11-файлы для обхода этого отказа.

SIGKILL исполнителя, авария ОС и задержки ядра могут отложить очистку.
Ограниченное окно остановки не обещает мгновенного исчезновения процессов
в таком состоянии. Для rollback отключите `check_executor` в caller-профиле;
перед удалением его work root подтвердите отсутствие собственных активных jobs.

Первая целевая матрица — Linux x86_64 и Windows x86_64. Нативная приёмка требует
Designer на каждой ОС, обоих режимов совместимости и расширений, сравнения
исходных координат, серии не менее 20 проверок и проверки отмены, таймаута и
восстановления. Сборка для Windows и fake-executor тесты отдельно эту приёмку
не заменяют.
