# MCP: инструменты и подключение к 1С

Этот документ описывает сами MCP-инструменты и их зависимости. Установка
профилей в AI-клиенты вынесена в `docs/mcp/README.md`.

## Матрица инструментов

Набор доступных tools зависит от профиля сервера.

Ответы инструментов `search` (`search_code`), `symbol_info`, `diagnostics`, `graph`,
`outline` и `references` несут единый объект места и единый конверт свежести — см.
`docs/mcp/LOCATION_CONTRACT.md`.

Клиенту, объявившему расширение `io.modelcontextprotocol/tasks`, чтения резидентной
базы могут отвечать долговечным хэндлом вместо конверта «индекс строится» — см.
`docs/mcp/TASKS.md`. Ветка выключена по умолчанию; клиент, расширение не объявивший,
изменений не видит.

| Профиль | Tool | Что делает | Что нужно дополнительно |
|--------|------|------------|-------------------------|
| `reference` | `search(action=find_docs\|search_docs\|list_platform\|status)` | поиск и перечисление встроенного каталога платформы | `EMBEDDING_URL` только для `search_docs` |
| `reference` | `syntax_help` | точечная справка по типу, методу, свойству или глобальной функции | ничего |
| `reference` | `its_help` | вопросы к ИТС / 1С:Напарник | `NAPARNIK_TOKEN` |
| `workspace` | `metadata` | обзор объектов конфигурации, реквизитов, форм и дерева метаданных: `info`, `tree`, `object`, `form`, `status` (готовность резидентной базы) | `--source-dir` |
| `workspace` | `search(action=search_code\|find_docs\|search_docs\|list_platform\|status)` | поиск по коду проекта и тот же встроенный каталог платформы, что в `reference` | `EMBEDDING_URL` включает семантику `search_code`/`search_docs`; без него работают лексика и `find_docs` |
| `workspace` | `syntax_help` | точная карточка платформенного типа или члена по legacy `name`/`type_name` либо по `reference_id` из `list_platform` | `--source-dir`; подключение к 1С не требуется |
| `workspace` | `symbol_info` | консолидированная семантическая карточка одного символа по квалифицированному имени (`ОбщийМодуль.Метод`, `Документ.ЗаказКлиента.Реквизит`, имя объекта метаданных): вид, контейнер, сигнатура, doc-комментарий, тип возврата, место определения, состав объекта, сводка использований и `graph_id`. Неточное имя даёт список кандидатов из общего словаря имён (см. «Словарь имён»), а не ошибку и не пустоту. Вход `path` (+ `root_id`, как в хитах `search`) + `line` + `column` (0-based) — запасной, для локальных переменных и параметров, у которых нет глобального имени. Граница с `graph`: `symbol_info` отвечает про один символ, `graph` — про его связи | `--source-dir` |
| `workspace` | `references` (опт-ин) | все вхождения одного символа с видом каждого (`declaration` \| `call` \| `write` \| `read`) и пофайловой гистограммой. Вход — `symbol` (квалифицированное имя или короткое уникальное) либо `path` (+ `root_id`) с `line_content` — текстом строки, который сверяется с файлом, — и/или `line` + `column` для локальной переменной и параметра. Отдаётся только когда запуск назвал его: `--enable-tool references` | `--source-dir` |
| `workspace` | `graph` | граф вызовов: `overview`, `schema`, `status`, `node`, `source`, `neighbors`, `callers`, `callees`, `resolve`; `resolve` — общий словарь имён, а не проекция узлов графа: отвечает и на несобранном графе и называет каждый источник, который спросить не удалось (см. «Словарь имён»); виды рёбер включают строковую диспетчеризацию `notify_ref` (`ОписаниеОповещения`), `idle_handler` (`ПодключитьОбработчикОжидания`) и `event_subscription` (`ПодпискаНаСобытие` → обработчик) с провенансом `string_resolved`, а также `register_movement` (`Движения.<Регистр>.<метод>()` → регистр) для анализа влияния на регистр перед удалением/переименованием | `--source-dir` |
| `workspace` | `diagnostics` | диагностики кода: `catalog`/`schema` (без базы), `status` (готовность резидентной базы), `file` (находки по файлу), `workspace` (агрегаты по конфигурации) | `--source-dir` |
| `workspace` | `outline` | карта одного `.bsl`-файла: дерево `#Область`, процедуры, функции и модульные переменные с экспортом, директивами компиляции, параметрами (`Знач`, умолчания) и диапазонами. Тел методов не отдаёт никогда. Вход — `path` (+ `root_id`, как в хитах `search`), `mode` (`full` \| `regions` — только скелет областей для большого модуля). Отвечает от одного разбора файла: ничего не строит, `loading` не возвращает, ответ одинаков на непрогретой и прогретой рабочей области | `--source-dir` |
| `workspace` | `query` | `schema` (контракт без базы), `validate` для SDBL, а также `execute` для `SELECT` | `--onec-url` нужен для live-валидации через платформу и для `execute` |
| `workspace` | `execute` | нативная проверка BSL (`check`), выполнение скрипта (`run`) и вычисление выражения (`eval`) | `--onec-url` нужен для `run` и `eval`; `check` требует `native_check` у выбранного подключения |
| `workspace` | `event_log` | чтение журнала регистрации 1С с фильтрами (`date_from`, `date_to`, `level`, `user`, `event`, `metadata`, `contains`, `limit`); свежие записи первыми. `contains` — пост-фильтр по уже усечённому окну из `limit` записей (не по всему журналу); неизвестный `metadata` даёт ошибку, а не тихое расширение выборки | `--onec-url` + право `EventLog` у пользователя сервиса |
| `workspace` | `debug` | attach, breakpoints, step, stack trace, locals, eval | `--onec-url` и доступ к отладочному контуру |

**«Выключен» и «деградирован» — разные состояния, и путать их нельзя.**
Столбец «что нужно дополнительно» описывает деградацию: инструмент виден в
`tools/list` всегда, а отсутствие соединения с 1С, `EMBEDDING_URL` или
`NAPARNIK_TOKEN` проявляется при вызове — ошибкой либо ответом с пометкой
`degraded` и причиной в `freshness`. Опт-ин инструмент ведёт себя ровно наоборот:
пока запуск не назвал его в `--enable-tool`, его нет в `tools/list` вовсе, а вызов
по имени неотличим от вызова несуществующего инструмента. В таблице выше опт-ин
помечен прямо в строке; действующий список публикуется отдельным массивом
`opt_in_tools` в декларации контракта, и брать его следует оттуда.

`graph` и `diagnostics` — два семантических примитива, которые недоступны через grep:
граф отвечает «кто кого вызывает», диагностики — «где недостижимый код / несоответствие
типа / неразрешённый вызов / неиспользуемая переменная». Они связаны: каждая находка
`diagnostics file` несёт `graph_id` метода, который можно передать в `graph callers` для
анализа влияния.

### Версии и lifecycle справочной поверхности

При opt-in `maxInputTokens`/`tokenizerFile`/`tokenizerSha256` результат `search_code`
показывает исходный `symbol` и необязательный `source_span`: `byte_start`, `byte_end`,
`parent_byte_start`, `parent_byte_end`, `part_index`, `part_count`. Байтовые диапазоны
относятся к полному исходному файлу, начинаются с нуля и не включают конец;
номер части начинается с единицы. Части одного метода остаются отдельными hits.
Без token policy `source_span` отсутствует. Версия `8` описывает эту форму code hit;
веса и порядок fusion не меняются.

`search` публикует tool-wide `outputSchema` версии `9` в workspace и `7` в reference: `search_code` (включая `not_ready`) — версии `8`,
`find_docs` и `search_docs` (включая `not_ready`) — версии `6`; варианты различаются по
`action` и `schema_version`. Номера действий независимы: `search_code` ранее получил версию `5` из-за
`freshness.drift_watch`. Контракт `3.0` добавил indexing и повысил версии
`search_code` до `6`, справочных действий до `5`; контракт `3.1` добавляет необязательную
диагностику `semantic_failure` и повышает их до `7` и `6`;
`list_platform` имеет версию `1`; `status` обоих профилей имеет версию `4` и форму
`{action:"status",schema_version:"4",profile,state,indexing}` с необязательными
`semantic_failure` и `embedding_profile`; профиль содержит `wire_model`, `storage_identity`
и `dimension`. `state` — `ready|loading|busy|failed`. Машинный контракт имеет версию `3.3`. `metadata` live object возвращает `schema_version="2"`
с `completeness` и `truncated`; live `tree` и `object` учитывают общий `max_output_tokens`.
`syntax_help` имеет версию `2`, а все успешные варианты
`symbol_info`, включая transient `status="loading"`, — версию `1`.

Справочный индекс проходит состояния `Uninitialized → Loading → Ready` либо `Failed`.
Во время загрузки поиск возвращает структурированный `not_ready`, terminal `Failed` —
MCP error с `reasonCode`; `list_platform` и `syntax_help` читают встроенный каталог и от
индекса документации не зависят. Если настроен внешний baseline, его ошибка не включает
скрытый локальный fallback: stale baseline rows/manifest очищаются, engine не публикуется,
а состояние остаётся fail-closed до успешной повторной инициализации.

Провенанс рёбер. Полностью литеральный вызов метода модуля менеджера
(`Документы.X.Метод()`, метод найден и экспортирован) имеет провенанс `resolved` — модуль
менеджера определяется однозначно, доверие как у квалифицированного `Модуль.Метод()`.
Провенанс `inferred` означает, что ребро указывает на узел метаданных (платформенный метод
менеджера вроде `СоздатьЭлемент` или голая ссылка `Справочники.X`), а не на узел кода. Ответы
`neighbors`/`callers`/`callees` несут поле `confidence` (`resolved_only` |
`contains_inferred`) — свёртка гистограммы провенанса показанных рёбер (`resolved_only`,
если все рёбра `resolved`; иначе `contains_inferred` при любом inferred/string-ребре).
Неразрешённые вызовы в граф не попадают, поэтому поле оценивает доверие к показанным рёбрам,
а не полноту. Это позволяет анализу влияния перед переименованием/удалением одним взглядом
видеть, доверять ли результату или дополнить его `search_code`. У `Новый ОписаниеОповещения` моделируются оба обработчика —
основной (`ИмяПроцедуры`, `Модуль`) и обработчик ошибки (`ИмяПроцедурыОбработкиОшибки`,
`МодульОбработкиОшибки`).

## Ссылки на символ

`references` отвечает на «кто использует X» полным списком вхождений, а не выборкой.
Инструмент опт-ин: `--enable-tool references`.

**Ответ всегда называет, чем он является, — поле `outcome`, закрытый словарь
`resolved` | `ambiguous` | `not_found` | `unsupported_symbol` | `anchor_stale`:**

- `resolved` — якорь один, список вхождений И ЕСТЬ ответ; пустой список означает ровно
  ноль ссылок — но только при `total_is_lower_bound: false` и полном `completeness`:
  перебор, упёршийся в `max_files`, даёт нижнюю оценку, а нечитаемый файл резидента
  (`unreadable_files`) означает, что вхождение могло остаться в непрочитанном;
- `ambiguous` — имени отвечает несколько объявлений, ссылки не считаются вовсе. Ответ
  несёт `declarations` (места объявлений) либо `lookup.candidates` (кандидаты словаря
  имён с квалифицированными именами), а `resolution_hint` называет ту ось, которая
  разделяет ИМЕННО ЭТИ объявления: `anchor_root_id` для одноимённых модулей в разных
  корнях, якорь по цитате — пара `root_id` + `path` нужного объявления вместе с
  `line_content` — там, где объявления делят корень, квалифицированное имя кандидата
  (`lookup.candidates[].address.symbol`) обратно в `symbol` — там, где неоднозначность
  пришла от словаря имён;
- `not_found` — ничего не совпало точно;
- `unsupported_symbol` — имя разрешено точно, но перебора ссылок для него не существует:
  объект метаданных, платформенный член, модуль целиком, поле неизвестной области ссылок;
- `anchor_stale` — присланная цитата строки этот файл больше не описывает.

Последний исход — причина, по которой инструмент вообще заведён: сегодня такой запрос
неотличим от «ссылок нет», а клиент по этому нулю принимает решение о переименовании.
Чем именно оказалось имя, говорит `unsupported.category` — закрытый словарь
`common_module` | `metadata_object` | `metadata_member` | `form` |
`platform_member` | `unknown_scope`. Коды те же, что у категорий словаря имён: до какой
ступени дошёл якорь, клиента не касается, а род сущности — касается. Значение
`unknown_scope` стоит особняком: это не род сущности, а род незнания — символ разрешён, но
где искать ссылки, не знает никто.

Разрешённый ответ. `limit` режет показ, а не счёт: `total` считает все вхождения, и
пофайловая гистограмма покрывает их все — по ней и обходят остаток вместо курсора.

**Якорь называет себя в каждом ответе.** Блок `anchor` несёт `mode` — закрытый словарь
`symbol` | `position` | `line_content`, — и `line`, строку, на которой якорь в итоге встал,
когда он вообще где-то встал: у `position` всегда, у `line_content` — когда цитата выделила
один символ. Ответы `ambiguous` и `anchor_stale` по цитате `line` не несут: якорь не встал
никуда, и ровно это они и сообщают. Отдельного `verified` рядом нет намеренно: у якоря по имени
проверять нечего, и `verified: false` учил бы клиента, что его запрос чем-то ущербен.

**Цитата строки — самопроверяемый якорь.** `path` + `line_content` — подстрока строки, на
которой стоит вхождение, несущая хотя бы одно ИМЯ целиком: имена сравниваются целиком, и
цитата, разрезающая идентификатор посередине, не удостоверяет ничего и отвергается кодом
`no_name_in_quoted_text`. `line` при этом необязателен, а будучи задан — ничего не выбирает. Цитата сверяется с файлом ДО того, как что-либо посчитано, и это закрывает режим
молчаливо неверного ответа: клиент, приславший прежние `line`/`column` после чужой правки,
сегодня получает уверенный список ссылок на ДРУГОЙ символ. Разрешение идёт по строкам,
содержащим цитату, затем по именам, чей текст в цитату входит, и сводится по САМОМУ
символу: одно имя на пяти подходящих строках — один ответ, выбирать нечего. Нашлась цитата
не на той строке, что прислана, — ответ по-прежнему `resolved`, но говорит об этом в
`anchor.relocated_from_line`. Присланный `line` при этом ничего не закрепляет: пока цитата в
файле одна, координата всё равно ничего не решает, а когда цитат несколько — «ваша строка
всё ещё несёт текст» это совпадение, а не свидетельство свежести, и закрепление по нему
вернуло бы уверенный ответ о другом символе. Поэтому несколько совпавших строк с разными
символами дают `ambiguous`, и место, на которое указывал присланный `line`, помечено
`pointed_by_line: true` — выбор виден и подтверждается одним следующим вызовом. Повторить
тот же запрос с `line` бесполезно: разводит только более узкая цитата либо переход на
позиционный якорь по `location` нужного места — координаты в нём той же ревизии, что и
ответ, и `resolution_hint` называет именно эти две оси. Разошлись картины — `anchor_stale`, и `anchor_stale.reason`
называет, как именно: закрытый словарь `not_in_file` | `column_outside_quoted_text` |
`no_name_in_quoted_text` | `name_not_resolved`. Рядом идут `line_content_matches` — сколько
строк файла ещё несут цитату, — и `actual_line`, то, что стоит по присланному номеру
сейчас; если эта строка была урезана капом или в ней замаскирован литерал, сказано
`actual_line_truncated` и `actual_line_redacted`, иначе сверка с собственным буфером
показала бы расхождение, которого в файле нет. Отказ двусмыслен по построению: вперёд мог уйти файл, а мог отстать резидент, —
поэтому конверт свежести называет ревизию, с которой клиент разошёлся, и такой ответ
стоит одного форсированного пересбора с повтором. Позиционный вход `path` + `line` без
цитаты работает ровно как прежде и объявляет себя `mode: "position"` — то есть
непроверенным. Цитата, дающая больше одного РАЗЛИЧНОГО символа, — это `ambiguous` с
перечнем `anchor_sites`: место, строка-свидетельство и квалифицированное имя там, где оно
у символа есть.

**Вид вхождения — закрытый словарь `declaration` | `call` | `write` | `read`.** Обработчика
событий среди них нет намеренно: имя связывается с событием в XML формы и в подписках, а
не в тексте BSL, поэтому синтаксический разбор вхождения такого факта не выводит. Он
придёт от `graph` отдельной осью со своей свежестью, а объявленное, но никогда не
выдаваемое значение учило бы клиента неверной модели.

**Превью — декорация, а не часть ответа.** `include_preview: true` добавляет к каждому
вхождению `snippet` — одну строку исходника, — и `snippet_start_character`, UTF-16-колонку,
с которой этот срез начинается: она и позволяет проиндексировать имя внутри среза колонками
`location.range`. Длинная строка показывается окном ВОКРУГ вхождения, а не с головы
(`snippet_truncated: true`): превью, в котором нет символа, о котором ответ, — ровно тот
класс правдоподобного и неверного, ради которого инструмент заведён. К строке применяется
та же маскировка секретов, что у `search`, и видит она ВЕСЬ ОПЕРАТОР, а не показываемую
строку: маркер, который её взводит (`Пароль`, `token`), стоит перед своим литералом в том же
операторе, а BSL переносит длинные присваивания свободно — фильтр, которому дали одну
физическую строку, такого маркера не увидел бы и выпустил секрет открытым. По той же причине
маскировкой накрыт и многострочный `|`-литерал целиком: литерал открыт до закрывающей
кавычки. Границей служит объемлющий метод — оператор её не пересекает. Сработала маскировка —
`snippet_redacted: true`: колонки `range` такой срез больше не индексируют, и остаётся
единственное обещание — вхождение в срезе есть. Флаг говорит про САМУ строку: секрет двумя
строками выше её не помечает. Превью
навешиваются ПОСЛЕДНИМИ, из остатка бюджета: `outcome`, `total`, состав `references` и
пофайловая гистограмма при включённом и выключенном превью совпадают, а не поместившиеся
превью считаются в `previews_omitted`. Гистограмма — единственный способ обойти `limit`,
и необязательная подпись не может оплачиваться ею. Строки-свидетельства (`actual_line`,
`anchor_sites[].snippet`) выдаются всегда и проходят ту же маскировку и тот же кап: это не
подпись к находке, а обоснование отказа, и бюджетом превью оно не оплачивается.

**Курсора нет.** Оси сужения — `area_root_id`, `area_path_prefix`, `kinds`,
`include_declaration`; `limit` (50, потолок 500) режет ПОКАЗ при точном `total`, а
`max_files` (2000, потолок 10000) режет сам перебор — тогда ответ несёт
`total_is_lower_bound: true` и `narrowing_comparable: false`, и два таких ответа между
собой не сравнимы. Что показ не вместил, видно в `files` — пофайловой гистограмме,
ключ которой пара `(root_id, path)`: сумма её счётчиков равна `total`, пока её саму не
срезал бюджет (тогда `histogram_truncated: true`).

**Адресуются экспортные члены.** Квалифицированное имя `Тип.Объект.Метод` и
`ОбщийМодуль.Метод` доходит до члена, объявленного с `Экспорт`; член без него имени не
имеет — `symbol_info` читает то же написание так же, — и берётся якорем по цитате
`path` + `line_content`. Исключение — методы модуля формы: они адресуются формой
`ОбщаяФорма.<Форма>.<Метод>` и `<Тип>.<Объект>.Форма.<Форма>.<Метод>` независимо от
экспорта, потому что обработчики его не имеют по построению. Одно имя `Тип.Объект.Метод`
достаётся модулю объекта (или набора записей), и лишь когда там его нет — модулю
менеджера; метод при этом старше одноимённой переменной, потому что карточка на тройке
переменных не ищет вовсе. Приоритет действует ВНУТРИ одного объекта: конфигурация и
расширение держат каждая свой, и одноимённые модули в разных корнях по-прежнему дают
`ambiguous`. Два написания одного пути, различающиеся регистром, — тоже два объявления,
а не одно: `symbol_info` выбирает из них первое по таблице модулей, а перебор ссылок
показывает оба, потому что молчаливый выбор здесь и есть та подмена, ради которой
инструмент заведён. Одно расхождение с `symbol_info` названо прямо: неэкспортный член объектного
модуля карточка считает отказом для всей тройки, а перебор ссылок — молчанием, после
которого отвечает модуль менеджера.

**`anchor_root_id` и `area_root_id` — разные вопросы.** Первый говорит, в каком корне
искать ОБЪЯВЛЕНИЕ (выход из `ambiguous`), второй — ссылки из какого корня показывать.
Символ, объявленный в конфигурации и вызываемый из расширения, требует обоих сразу.
Третий, `root_id`, относится только к `path`: рядом с `symbol` он отвергается явной
ошибкой, как и у `symbol_info`, — принятый и отброшенный параметр сузил бы ответ лишь
на словах. `anchor_root_id` отвергается рядом с ЛЮБЫМ якорем по `path`, а не только с
позиционным: файл уже назван, сужать нечего.

Счётчик `total` в теле считает вхождения и только их. Ответ словаря имён лежит под
своим ключом `lookup` — со своими `total`, `total_exact`, `truncated` и `providers`, —
потому что там счёт идёт кандидатам: один ключ с двумя несравнимыми величинами и есть та
путаница, ради которой заведён `outcome`.

Свежесть называет того, чьи данные СОСТАВЛЯЮТ тело: список ссылок и разрешённый символ —
`resident` с непустыми `revision` и `topology_fingerprint`, даже когда якорь нашёл
словарь имён; тело из кандидатов словаря — `name-dictionary` с `null`-идентичностью.

## Места вызова на рёбрах графа

Иерархия вызовов — это `graph` с действиями `callers`/`callees`. Отдельного инструмента
`call_hierarchy` нет и не будет: он отличался бы от них только формой ответа. Чего у
рёбер не хватало — это МЕСТ вызова, и они добавлены на само ребро, а не вторым ответом:
клиенту не приходится склеивать два ответа, и свежесть остаётся честной — у графа она
своя, и подмешивать в один ответ резидентную нельзя.

Спрашивать надо явно: `call_sites: true`. Без него ребро не несёт ни одного ключа про
места, и это не экономия, а различимость — «мест нет» и «никто не спрашивал» обязаны
читаться по-разному.

| Что в запросе | Что на ребре |
|---|---|
| `call_sites` не задан | ни одного ключа `call_site*` |
| задан, места есть | `call_sites` (плита места), `call_sites_total`, при усечении `call_sites_truncated` |
| задан, мест нет | `call_sites_unavailable` — код из того же закрытого словаря, что и `location_unavailable` |

Место — тот же объект, что публикуют `search`, `symbol_info`, `diagnostics`, `outline` и
`references`: `range` — всё выражение вызова, `enclosing_range` — объявление, из которого
он сделан, пара `(root_id, path)` — файл ВЫЗЫВАЮЩЕГО. Для `callers` это файл соседа, для
`callees` — файл корня обхода. У вызова из тела модуля вне процедур `enclosing_range`
отсутствует: объявления, которое его окружало бы, там нет, и выдумывать его нельзя.

Три кода отказа принадлежат именно ребру:

- `no_call_site` — связь выведена из метаданных, а не из кода: `contains`,
  `data_binding`, `subsystem_membership` и прочая структура. Места нет и не будет;
- `call_site_not_recorded` — место в коде ЕСТЬ, но сборка его не хранит. Сегодня это
  `query_ref`: одно ребро стоит за всеми чтениями объекта в модуле;
- `source_drifted` — файл уехал под записанным смещением. Диапазон был бы правдоподобным
  и неверным, а по нему режут текст.

**Что именно подтверждает место.** Срез текста по записанному смещению обязан содержать имя
цели ОТДЕЛЬНЫМ идентификатором, а не подстрокой: `Считать` внутри `СчитатьИное` подтверждал
бы уехавший спан сам собой, и место резало бы чужой вызов. Остаточный случай назван прямо:
правка, после которой спан попал на ДРУГОЙ вызов той же цели, проверку проходит — место
тогда настоящее и ведёт к вызову того же метода, но не к тому вхождению.

**Частичного списка не бывает.** Если проверку не прошло хотя бы одно место ребра, ребро
не отдаёт ни одного и называет `source_drifted`. Иначе список из одного места при
`call_sites_total` два читался бы как усечение, которого никто не объявлял. Поэтому
список короче `call_sites_total` всегда означает ровно одно: сработал `max_call_sites`
(умолчание 20) или общий бюджет вывода — и тогда стоит `call_sites_truncated`, а причина
названа в конверте (`result_cap` либо `output_budget`).

`call_sites_total` считается ДО показа, по тому, что записано в артефакте, — поэтому
урезанный список остаётся сравнимым с целым.

Одно ребро несёт все свои места: два вызова одного метода из одного тела — это одно
ребро с двумя местами, а не два ребра. Счётчик `in_degree`, по которому ранжирует
`overview`, при этом считает МЕСТА вызова, а не вызывающих, — он таким был и остаётся.

## Видимость расширений: что символ вообще может увидеть

Ответ о символе зависит от того, ОТКУДА спрашивают. Файл расширения `E` видит базовую
конфигурацию, транзитивные зависимости `E`, объявленные через `dependsOn`, и само `E`.
Обратной видимости нет: зависимость `A → B` не делает `A` видимым из `B`, независимые
расширения не видят друг друга вовсе, а файл базовой конфигурации не видит ни одного
расширения — метод, добавленный расширением, из кода базы недоступен, потому что
расширение может быть отключено в любой момент.

Из этого следуют две вещи, которые видно в ответах:

- **Позиционный вход уважает видимость, поиск по имени — нет.** `symbol_info` и
  `references`, получив `path` + `line` + `column`, отвечают о том, что видит ИМЕННО ЭТОТ
  файл: вызов общего модуля независимого расширения оттуда не разрешается и приходит
  `not_found`. Тот же символ, спрошенный квалифицированным именем, находится — запрос по
  имени задан о рабочей области целиком и вызывающего не имеет. Это не расхождение
  инструментов, а разные вопросы; выбирать вход стоит по тому, какой из них вы задаёте.
- **Приоритет при поиске имени** — сначала само расширение, затем ближайшая зависимость,
  затем база. Оверлеи метаданных накладываются в обратном порядке (база → зависимости →
  своё расширение), поэтому унаследованные реквизиты сохраняются.

Зависимости объявляются в `bsl-analyzer.toml` структурированной записью расширения
(`dependsOn = ["Имя"]`); граф проверяется при загрузке проекта — неизвестные имена,
самоссылки и циклы отклоняются до анализа. Подробности синтаксиса — в
`docs/configuration/PROJECT_CONFIGURATION.md`.

**У правила есть известное исключение, и оно не покрыто.** Перебор ссылок на метод
менеджерского модуля и модуля объекта сегодня засчитывает вхождения из расширения, которое
объявления не видит: эти два маршрута проверяют видимость объекта метаданных, а тело модуля
берут из индекса, выведенного из путей и топологии не знающего. Для метода общего модуля
правило соблюдается. Модуль набора записей не проверен вовсе. Держатель — github#103.

## Бюджет вывода: `max_output_tokens`

Каждый инструмент принимает `max_output_tokens` — потолок размера ответа в токенах
(~4 символа на токен, по умолчанию 6000; у `graph action=source` — 4000, у `diagnostics`
бюджет применяется только если задан явно). Это защита контекста агента: один вызов не
должен выбивать окно.

Для `diagnostics` минимальное допустимое значение — 256 токенов: меньший конверт не
вмещает обязательную общую сводку и точную идентичность первой ошибки набора baseline.

Как сообщается об усечении:

- JSON-инструменты (`graph`, `diagnostics`, `event_log`) ставят на конверт
  `budget_exhausted: true` и `budget_hint` с подсказкой, чем сузить выборку;
- `outline` помечает усечение иначе — ключом `truncated: true` рядом с `budget_hint`, как
  `symbol_info`; поля `budget_exhausted` у него нет. Отбрасываются целые узлы с хвоста
  документа вместе с поддеревом, поэтому ответ остаётся деревом при любом бюджете, а у
  каждого оставшегося узла родитель на месте;
- текстовые (`metadata`, `query`, `execute`, `its_help`, `debug`)
  режут вывод по границе строки и дописывают в конец пояснение;
- `syntax_help` сохраняет такой же ограниченный Markdown для старых клиентов и
  одновременно возвращает типизированный `structuredContent` версии `2`;
  `kind` различает тип, метод, свойство, глобальную функцию и ключевое слово,
  поэтому машинному потребителю не нужно разбирать Markdown. Бюджет, как и у `search`,
  считается по паре «текст + карточка»: сначала Markdown, затем в остаток
  укладываются перечни карточки — конструкторы прежде методов. Усечение видно по
  двум флагам: `text_truncated` для Markdown и `budget_exhausted` для карточки.
  Перечень `matches` сохраняет одну запись при любом бюджете (пустой читался бы
  как «не найдено»), перечни методов и конструкторов типа могут опустеть —
  нужный метод дешевле запросить точечно через `reference_id` (legacy-вход
  `name` + необязательный `type_name` также сохраняется);
- `search` удаляет целые находки с хвоста, обновляет `shown`, `budget_exhausted`
  и причину `output_budget` в `freshness`. Если исходный текст не помещается,
  он заменяется компактным JSON-зеркалом без потери обязательных полей.
  `hits: []` при `total > 0` означает усечение, а не отсутствие совпадений.
  Для `search_code`, `find_docs`, `search_docs` размер B — UTF-8 байты всех текстовых
  блоков плюс байты компактного `structuredContent`, без протокольного framing;
  соблюдается B <= 4 * max_output_tokens. Сначала резервируется обязательный
  пустой конверт с `indexing`, legacy/detail/degraded/freshness полями.
  Если он не помещается, возвращается MCP invalid_params (-32602),
  `message: "budget_too_small"`, `data: {reason: "budget_too_small",
  minimum_output_tokens: ceil(B/4)}`. JSON и `indexing` не обрезаются.
  Это же правило действует на graph loading для уже бюджетируемых действий
  с исходным кодом. `search status`, `graph status/schema/resolve` сохраняют
  исключения из бюджета. Hard errors и отмена запроса имеют прежний приоритет.
  По умолчанию остаётся 6000 токенов; отказ на слишком маленьком бюджете требует
  machine contract `3.0`.
  Объект `semantic_failure` входит в обязательный конверт целиком: до отбора находок
  учитываются весь объект отказа, текст, `degraded`, `freshness` и `indexing`. Поле отказа
  не обрезается; если без находок конверт с ним не помещается, действует тот же
  `budget_too_small`. У `search action=status` параметра token-бюджета нет.

Где помимо бюджета действует ещё и счётчик (`limit` у `event_log` и `query execute`,
`max_findings` у `diagnostics file`), при срабатывании обоих ограничений подсказка прямо
говорит, что поднятие одного `max_output_tokens` не поможет — поднимать нужно оба.

## Что работает без подключения к базе 1С

Без HTTP-сервиса 1С доступны:

- весь профиль `reference`;
- в `workspace`: `metadata`, `graph`, `diagnostics`, поиск по коду и
  `query(action=validate)` с локальным парсером.

Для `query(action=execute)`, `execute(action=run|eval)`, `event_log` и для
отладки нужно живое подключение к базе через `--onec-url`. `execute(action=check)`
требует выбранное подключение с профилем `native_check`; одно только `--onec-url`
не настраивает нативный компилятор. Для `event_log`
пользователь сервиса дополнительно должен обладать правом `EventLog` (роль
`BSL_ОсновнаяРоль` его выдаёт; при использовании другой роли назначьте право
администрирования журнала регистрации).

## Диагностики и граф: проектный конфиг и резидентная база

`diagnostics` и `graph` — статический анализ, базе 1С они не нужны.

**Единый источник настроек.** `diagnostics` берёт правила и пороги из проектного
`bsl-analyzer.toml` (секция `[diagnostics]`) — ровно так же, как LSP и CLI. Один и тот
же файл управляет диагностиками во всех режимах: отключённые правила
(`ПравилоX = false`) и пороги (`[diagnostics.parameters.LineLength] maxLineLength = 150`)
применяются одинаково в редакторе, в `analyze` и в MCP. Настраивается один раз.

При настроенном `[diagnostics.baseline]` MCP использует тот же снимок и отпечатки,
что CLI и LSP. `file` возвращает частичную сводку, `workspace` — полную только при
завершённом неусечённом обходе. Сводка `baseline` находится рядом с `findings` или
`aggregates` и не удаляется бюджетом ответа. Ошибка файла возвращается обычной
структурированной ветвью с `baseline.state = "error"`, `error_code` и `detail`, без
находок и классификационных счётчиков. Изменение, атомарная замена или удаление
файла перечитываются отдельно от резидентной базы и меняют `result_id`.

В режиме `directory` MCP применяет policy каждого раздела из `include`: enabled
разделы подавляют известные находки, а `unsuppressed` владельцы остаются видимыми и
не читают/не наблюдают свои objects. Контракт `diagnostics` версии 15 всегда
возвращает `selection`, `partitions_enabled`, `partitions_unsuppressed`,
`unsuppressed`, `partitions_total`,
`partitions_returned` и `partitions_truncated`; подробности разделов ограничиваются
бюджетом, а в запросе `file` раздел-владелец идёт первым. Ошибка enabled object
закрывает классификацию и добавляет `errors_total`; повреждение dormant object не
влияет до повторного включения. Изменение `include` меняет `result_id` через штатный
config reload.

**Резидентная база и граф строятся при старте.** Сервер начинает строить резидентную базу по
всем `.bsl` проекта (как у LSP-сервера) и граф вызовов сразу при запуске, не дожидаясь первого
обращения: иначе первый же осмысленный вопрос упирался бы в холодную сборку. На крупной
конфигурации (ERP, ~25 тыс. файлов) резидент занимает ~20 секунд и держит около 2.8 ГБ RAM;
граф на тёплом кэше публикуется с диска, на холодном — собирается заново. После периода
простоя резидент выгружается и при следующем обращении строится заново.

Пока сборка идёт, инструменты отвечают конвертом «не готово», а не ошибкой и не пустым
результатом. Конверт машиночитаемый у всех: в `structuredContent` лежит `status` —
`"loading"` у `metadata`, `symbol_info`, `diagnostics`, `graph` и `references`,
`"not_ready"` у `search`.
Читающие резидент (`metadata`, `symbol_info`, `diagnostics`, `references`) добавляют `detail`, `state`,
`generation` и `elapsed_ms`; `graph` — `detail`; `search` — `retry_after_ms` и `progress`. Проверять
нужно именно поле: у `metadata` рядом с конвертом остаётся человекочитаемая фраза
«Метаданные загружаются…», и распознавание по ней ненадёжно — та же фраза может встретиться
в теле модуля и попасть в вывод инструмента как настоящий результат.

Готовность резидента опрашивается без построения ответа: `metadata action=status` и
`diagnostics action=status` возвращают один и тот же снимок жизненного цикла
(`state`/`generation`/`reload`, плюс `files`/`elapsed_ms`/`error`/`watch` где применимо),
`graph action=status` — свой (`state`, и при `ready` — `files`/`revision`/`stale`/`reload`).

## Карточка символа: структурная выдача `symbol_info`

Инструмент отвечает на вопрос «что это за символ» одним вызовом, чтобы не выстраивать
цепочку «сигнатура → тип → где объявлен → кто вызывает». Основной вход — квалифицированное
имя; позиция нужна только для локальных переменных и параметров, у которых глобального

Правила чтения:

- **`resolved` появляется только при промахе.** Разрешённая карточка этого поля не несёт:
  признак успеха — наличие `symbol` вместе с `kind`, а не `resolved: true`.
- **`id` кандидата — идентификатор графа, а не имя для повторного запроса.** Он адресует узел
  в `graph`, но обратно в `symbol_info` не подставляется: тот ждёт точечное BSL-имя. Либо
  открыть кандидата в `graph`, либо уточнить имя.
- **`match`** — чем совпало: `exact`, `case_insensitive`, `name` (совпал последний сегмент)
  или `substring`.
- **`definitions[]` — все места объявления, а не одно.** Метод, на который расширение
  наложило перехватчик, объявлен больше одного раза, и карточка, печатающая одно место,
  говорит клиенту, что исполняется базовое тело: для `&Вместо` это ложь, для `&Перед` и
  `&После` — половина правды. Каждое место называет свою роль — `base` | `instead` |
  `before` | `after`, — и `source_extension` там, где место пришло из расширения. Базовое
  объявление стоит в списке первым и остаётся в нём при любом числе перехватчиков. Место
  адресуется парой `(root_id, path)` из `location`: именно её принимают `outline` и
  `diagnostics file`.
- **`definition` — то же место в старом виде, и адресом оно не служит.** `path` в нём —
  АБСОЛЮТНЫЙ путь файла на машине сервера, а не относительный путь под корнем; `line` —
  1-based, тогда как `line` на входе 0-based; диапазона нет вовсе — только строка объявления
  и её текст в `snippet`. Поле оставлено для существующих клиентов; всё, что подставляется
  обратно в инструменты, берётся из `definitions[].location`.
- **`usages` — сводка, а не список ссылок.** `count` — полный фан-ин по графу, а `top_modules`
  агрегируются по ограниченной выборке вызывающих; расхождение помечается
  `top_modules_sampled: true`. Полный обход — `graph action=callers` по возвращённому
  `graph_id`.
- **Отсутствие `usages` бывает трёх разных видов, и они не взаимозаменяемы.** Поля нет вовсе —
  у символа нет адресуемого узла графа (объекты метаданных, реквизиты, платформенные члены);
  `usages_unavailable: "graph indexing"` — граф ещё строится, ответ стоит повторить;
  `usages_unavailable: "symbol not in call graph"` — граф готов и символа в нём нет.
- **`semantics_unavailable: true`** — граф знает символ, а резидентная база уже нет
  (устаревший кандидат). Карточка при этом пустая, и содержимое считать достоверным нельзя.
- **`truncated: true` + `budget_hint`** — вывод урезан бюджетом: длинный doc-комментарий,
  сниппет или список `members`. Минимальный корректный конверт сохраняет только
  `schema_version`, `status`, `symbol`, `truncated` и `budget_hint`; повтор одного запроса
  с тем же бюджетом возвращает тот же устойчивый префикс членов.
- **`members` не зависят от `include`.** Их можно сузить точным регистронезависимым
  `member_name` и `member_kind` (`attribute`, `tabular_section`, `method`, `variable`,
  `property`, `form_attribute`, `form_element`, `handler`). Каждый член называет
  `origin`, необязательный `source_extension` и `availability`; типизированный член
  содержит совместимую строку `type` и `type_variants`, вызываемый — `signature`.
  Член, который не описывается ни тем, ни другим — табличная часть, реквизит с
  неразрешённым типом, элемент формы без типа, — приходит без обоих полей: вид
  такого члена называет `member_kind`.
- **`root_id` требует `path`.** Он уточняет, относительно какого корня написан путь, и с
  одним лишь `symbol` смысла не имеет: имя разрешается по всей резидентной базе, и корень
  ему не принадлежит. Такой запрос отвергается явной ошибкой, а не молча.
- **Схема карточки имеет версию `1`.** `tools/list` публикует единый `outputSchema` для
  `ok`, `not_found`, `ambiguous` и усечённого `ok`; ошибки входа и внутренние ошибки
  остаются MCP errors и не являются ветвями успешного `structuredContent`.

## Карта файла: структурная выдача `outline`

Инструмент отвечает на вопрос «как устроен этот модуль», не читая его целиком. От соседей
он отличается тем, что не пользуется ничем построенным: ни резидентной базой, ни графом,
ни индексом поиска. Ответ — один разбор названного файла, поэтому `outline` работает на
холодной рабочей области ровно так же, как на прогретой, и конверта `loading` у него нет
ни в одной ветке.

```json tool=outline
{"schema_version":"1",
 "mode":"full",
 "location":{"root_id":"","path":"CommonModules/РаботаСЗаказами/Ext/Module.bsl",
             "position_encoding":"utf-16","schema_version":"1"},
 "regions":[{"kind":"region","name":"ПрограммныйИнтерфейс",
             "range":{"start_line":4,"start_character":9,"end_line":4,"end_character":29},
             "enclosing_range":{"start_line":4,"start_character":0,"end_line":40,"end_character":14},
             "regions":[],
             "members":[{"kind":"function","name":"СоздатьЗаказ","export":true,
                         "directives":["at_server"],
                         "params":[{"name":"Клиент","by_value":false,"default":{"state":"required"}},
                                   {"name":"Дата","by_value":true,
                                    "default":{"state":"value","text":"Неопределено"}}],
                         "range":{"start_line":6,"start_character":8,"end_line":6,"end_character":20},
                         "enclosing_range":{"start_line":5,"start_character":0,"end_line":9,"end_character":13}}]}],
 "members":[],
 "truncated":false,
 "freshness":{"source":"file-parse","revision":null,"topology_fingerprint":null,"stale":null,
              "completeness":{"status":"complete","reasons":[]}}}
```

Правила чтения:

- **Место названо один раз, в корне.** Ответ всегда про один файл, поэтому пары
  `(root_id, path)` у узлов нет: узел адресуется парой из корня плюс своим диапазоном.
  Там же один раз объявлены `position_encoding` и версия блока места, и это то, что делает
  единицы узловых диапазонов объявленными, а не подразумеваемыми.
- **`range` — имя, `enclosing_range` — всё объявление.** 0-based, конец исключающий,
  колонки в кодовых единицах UTF-16 — как везде в контракте места.
- **Уровень разбит надвое: `regions` и `members`.** Внутри каждого перечня — порядок файла.
  Между перечнями порядка нет: метод, объявленный до области, лежит в `members`, а не перед
  ней.
- **`mode: "regions"` — сужение вопроса, а не усечение ответа.** Ключа `members` в таком
  ответе нет вовсе (пустой перечень читался бы как «методов здесь нет»), а полнота остаётся
  `complete`.
- **`default` — закрытый словарь из трёх состояний.** `{"state":"required"}` — аргумент
  обязателен; `{"state":"value","text":"…"}` — есть умолчание и его текст прочитан;
  `{"state":"unknown"}` — умолчание ЕСТЬ, а текст не прочитан. Последние два — разные
  ответы на вопрос «можно ли не передавать аргумент», и сводить их к одному нельзя.
  Длинный текст режется по своему пределу и помечается `text_truncated: true` рядом с
  `text`, а в конверте — причиной `result_cap`: поднятие `max_output_tokens` этого предела
  не снимает.
- **Тел методов в ответе нет никогда.** Единственная оговорка — невалидное объявление:
  если парсер не смог определить границу выражения умолчания (незакрытый строковый литерал),
  часть тела приезжает в текст умолчания. Это граница парсера, и предел длины ограничивает
  объём такой утечки, но не отменяет её.
- **Область, объявленная внутри тела метода, в карту не попадает.** Карта описывает
  устройство модуля, а не разметку внутри процедур.
- **Ошибка адресации — машинный код в теле ответа**, а не пустая карта: `unknown_root`,
  `absolute_path_under_root`, `path_not_relative_to_root`, `not_in_workspace`, `unreadable`.
  Словарь общий с `diagnostics file`, и на один и тот же вход оба инструмента отвечают
  одинаково.

## Словарь имён

Поиск по имени — один запрос на весь продукт. Им отвечают два входа: `graph action=resolve`
и список кандидатов, который `symbol_info` отдаёт при промахе по неточному имени. Оба
печатают одну и ту же выдачу одним кодом, поэтому на один вопрос дают один ответ.

Отдельного инструмента и отдельного индекса у словаря нет: он складывается из пяти уже
существующих источников. Из этого следует главное — **словарю не нужен граф**. Платформенный
член находится вообще без индексов, объект конфигурации и общий модуль — как только готов
резидент. Поэтому `resolve` отвечает и на несобранном графе, а не конвертом `loading`.

```json tool=graph

 "candidates":[
   {"display":"ЗначениеРеквизитаОбъекта","category":"module_method","match":"substring",

                           "range":{"start_line":5,"start_character":8,
                                    "end_line":5,"end_character":31},
                           "position_encoding":"utf-16","schema_version":"1"}}},
   {"display":"ЗначениеЗаполнено","category":"platform_member","match":"prefix",
    "provider":"platform",
    "address":{"symbol":"ЗначениеЗаполнено","syntax_help":{"name":"ЗначениеЗаполнено"}}}],
 "total":2,"total_exact":true,"truncated":false,
 "providers":[{"provider":"module_index","state":"answered"},
              {"provider":"metadata_listing","state":"answered"},
              {"provider":"platform","state":"answered"},
              {"provider":"module_members","state":"answered"},
              {"provider":"graph","state":"not_ready"}]}
```

Правила чтения:

- **Каждый ключ в `address` принимается тем инструментом, который он называет.** `symbol` —
  параметром `symbol` инструмента `symbol_info`, `graph_id` — действием `graph action=node`,
  `syntax_help` — инструментом `syntax_help`, `location` — парой `(root_id, path)` у
  `outline` и `diagnostics file`. Ключ, который принят не будет, не публикуется вовсе:
  непубликация — это утверждение «сюда нельзя», а не умолчание. Непустых ключей у кандидата
  всегда хотя бы один.
- **`id` сохранён ради совместимости и равен `address.graph_id`.** У кандидата без узла в
  графе ключа `id` нет. Раньше он был у всех и вёл в никуда — с этого дефект и начат.
- **Одна сущность — один кандидат, даже когда её знают двое.** Узел графа и запись
  резидента об одном и том же приходят одной строкой, где есть и `location`, и `graph_id`.
  Сводятся они по ФАЙЛУ, а не по имени: граф называет файл своего узла, поэтому одноимённые
  сущности в разных файлах — модуль конфигурации и одноимённый модуль расширения, экспортный
  метод и его закрытый тёзка в соседнем модуле — остаются разными ответами, и `graph_id`
  каждого указывает туда же, куда его `location`.
  Файл граф называет и для объекта метаданных: справочник, документ, регистр, роль,
  подсистема приходят одной строкой с XML в `location` и `mdo/…` в `graph_id`. У объекта,
  дополненного расширением, `graph_id` привязан к БАЗОВОЙ конфигурации — там он определён, —
  а кандидат расширения остаётся отдельным ответом со своим местом и без `graph_id`.
  Общий модуль, перечисленный в составе подсистемы, приходит категорией `common_module` и с
  `graph_id` вида `module/common/…`: это вызываемое тождество, а не конец ребра
  принадлежности.
- **`category` — единственное поле вида.** Закрытый словарь: `common_module`, `module`,
  `module_method`, `module_variable`, `metadata_object`, `metadata_member`, `form`,
  `platform_member`. `module` — модуль объекта, менеджера или набора записей: адресуется
  целиком, но имени в языке не имеет и открывается только по `graph_id`.
- **`match` — сила совпадения, от сильного к слабому:** `exact`, `case_insensitive`,
  `name`, `prefix`, `substring`. `name` — совпадение с хвостовым сегментом durable-id, то
  есть тоже равенство, поэтому он сильнее `prefix`. Порядок словаря и есть порядок
  ранжирования; при равном тире вперёд идёт более ранняя категория, затем алфавит.
- **`provider` — кто дал этого кандидата:** `module_index`, `metadata_listing`, `platform`,
  `module_members`, `graph`.
- **`providers` — состояние каждого источника, поимённо.** Закрытый словарь: `answered` —
  спрошен и ответил; `not_ready` — существует, но ещё строится, повтор запроса может
  изменить ответ; `not_asked` — не спрошен, потому что вопрос сужен мимо всего, что этот
  источник даёт; `unavailable` — в этой конфигурации отсутствует по построению; `failed` —
  сборка провалилась, и ждать бесполезно.
- **Пустой запрос спрашивает всех и никого.** На пустой строке ни один источник не
  опрашивается, и все пять приходят с `not_asked` — конверт полон, но ни на один источник
  не ссылается, и доказанным нулём это не является.
- **Пустой список сам по себе ничего не доказывает.** Доказанный ноль — это пустой список
  ПРИ всех источниках в `answered`. Если хоть один в `not_ready` или `failed`, конверт несёт
  `index_building`, а `detail` перечисляет, какие именно. `not_asked` и `unavailable`
  полноту не портят: первое — выбор вызывающего, второе — свойство конфигурации.
- **`total` и `total_exact` — про счёт, а не про длину списка.** `total` — сколько нашлось
  до предела. Пока никто не упёрся в свой предел, `total_exact: true` и это точное число.
  Если упёрся, `total_exact: false`: кандидатов, которые источник не отдал, свести с чужими
  было нечем, поэтому число может оказаться завышенным — но никогда не меньше отданного.
- **`truncated: true`** — предел сработал: либо общий, либо у отдельного источника. Ответ
  выдавать за исчерпывающий в этом случае нельзя.

`workspace/symbol` в LSP отвечает из этого же словаря, с одним сужением: только кандидаты,
у которых есть место в файле. Платформенные члены туда поэтому не попадают. Предел выдачи в
протоколе объявить нечем — поля неполноты у `workspace/symbol` нет, — и усечение видно
только в журнале сервера.
Если новое поколение MCP-демона вытеснило прежнее из общего workspace-кэша,
`graph action=status` добавляет `superseded: true`. Старое поколение остаётся только
читающим: оно возвращает `ready + superseded` и обслуживает содержательные действия,
лишь пока в его пуле доступен ранее открытый собственный SQLite-дескриптор. Без такого
дескриптора status возвращает `failed + superseded`, а содержательные действия — ту же
ошибку с указанием переподключиться, никогда не `loading`; статический `schema` доступен
всегда. Краткий параллельный `stdio`/fallback-процесс использует тот же `writer.lease` и,
если старый демон успел его заметить, также необратимо вытесняет старое поколение — после
этого переподключитесь к актуальному backend.

## Переменные окружения и prerequisites

### `EMBEDDING_URL`

Включает семантическую составляющую поиска:

- `search_docs` в профилях `reference` и `workspace`;
- семантическую ветвь `search_code` в `workspace` (лексическая ветвь работает всегда).

Без этой переменной `search_code` возвращает только лексические результаты с пометкой
`-- semantic skipped: … --`; в `reference` остаётся полнотекстовый `find_docs`.

Пока индекс ещё строится, `search_code` отдаёт структурный конверт (как у `graph`):
`{status: "not_ready", detail, retry_after_ms, progress: {active, …}}` в `structuredContent`
плюс зеркало в виде JSON-текста — программный потребитель читает машиночитаемое состояние,
а не разбирает строку. Флаг `progress.active` есть всегда (идёт сборка vs ещё не считает),
а числовые счётчики (`batches`, `chunks`) доступны только для согласованного sample
активной running-фазы; `pct` — только при total > 0. В persistence без счётчиков,
waiting и terminal состояниях устаревшие числа не публикуются. Текст, legacy progress
и `indexing` строятся из одного sample; готовность каждой цели читается из `indexing`.

### Структурная выдача поиска

Список находок приходит дважды: текстом — как его читает человек — и тем же составом в
`structuredContent`. Машинный потребитель читает поля, а не разбирает колонки:

```json tool=search
{"action":"search_code","schema_version":"8",
 "hits":[{"rank":1,"modality":"L","root_id":"","path":"CommonModules/Утилиты/Ext/Module.bsl",
          "line_start":181,"line_end":201,"symbol":"ПроверитьИНН","kind":"procedure",
          "graph_id":"method/common/Утилиты/ПроверитьИНН",
          "location":{"root_id":"","path":"CommonModules/Утилиты/Ext/Module.bsl",
                      "enclosing_range":{"start_line":180,"start_character":0,
                                         "end_line":201,"end_character":0},
                      "position_encoding":"utf-16","schema_version":"1"},
          "snippet":"Процедура ПроверитьИНН(…)\n…","snippet_truncated_lines":16}],
 "shown":1,"total":1,
 "indexing":{"schema_version":"1","targets":[
   {"kind":"lexical","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null},
   {"kind":"semantic","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null}]},
 "freshness":{"source":"search-index","revision":null,"topology_fingerprint":null,
              "stale":null,"drift_watch":"watching",
              "completeness":{"status":"complete","reasons":[]}}}
```

`line_start`/`line_end` (1-based, конец включающий) остаются как были; `location` — общий
объект места (0-based, конец исключающий), см. `docs/mcp/LOCATION_CONTRACT.md`. У поиска нет
своей ревизии, поэтому поля свежести равны `null`, а источник назван явно. `drift_watch`
говорит, следит ли кто-нибудь за исходниками рабочего пространства для индекса
(`starting`/`watching`/`polling`/`unobserved`, см. `docs/mcp/LOCATION_CONTRACT.md`); пока
оверлей догоняет правки или его очередь не обрабатывается, `completeness` становится
`partial` с причинами `index_building` / `modality_degraded` и `detail`. Версия `5` — это
появление этого поля.

Правила чтения:

- **Версионируется `schema_version`.** Меняется форма конверта или полей находки — растёт
  версия. Текстовая раскладка контрактом не является и может быть переформатирована в любом
  релизе; на неё завязываться не нужно.
- **`root_id` — часть тождества находки, а не украшение.** Расширение повторяет структуру
  каталогов конфигурации целиком, поэтому один и тот же `path` существует под несколькими
  корнями, и различает их только `root_id`. Пустой идентификатор — у конфигурации, а также у
  расширения, чей КАНОНИЧЕСКИЙ путь лежит внутри её корня: такое расширение своего корня не
  заводит, и его файлы остаются файлами конфигурации. Решает именно канонический путь, а не
  место объявления: расширение, объявленное ссылкой изнутри конфигурации наружу, корень
  получает, а объявленное снаружи ссылкой внутрь — нет. У расширения под каталогом проекта идентификатор —
  путь относительно этого каталога, у расширения ВНЕ его (объявленного абсолютным путём,
  через `../` или ссылкой) — абсолютное написание: относительным его выразить нечем.
  Сравнивать `root_id` следует на равенство, а не разбирать как путь. В текстовой раскладке непустой идентификатор печатается пометкой перед путём.
  Появление этого поля и подняло версию до `2`.
- **Отсутствие поля — это факт, а не пропуск.** Нет `symbol` — попадание в заголовок файла,
  а не в именованный символ (в тексте на его месте печатается `<header>`); нет `graph_id` —
  у находки нет устойчивого идентификатора, который можно передать в `graph`.
- **`total`** — длина ранжированного списка до усечения бюджетом, уже ограниченная `limit`
  запроса. Это не число совпадений по конфигурации.
- **`snippet`** — ровно те строки, что показаны в тексте (после редактирования секретов),
  плюс `snippet_truncated_lines` со счётчиком отброшенных. За полным телом метода нужно идти
  в `graph action=source` или читать файл.
- **`degraded`** (только `search_code`) — модальность, которая не отработала: семантика
  выключена, индекс ещё строится. Поле выставляется и при пустом списке: «ничего не нашлось»
  и «ничего не нашлось при выключенной половине поиска» — разные ответы.
- **`budget_exhausted`** — выдача урезана бюджетом (см. раздел выше).
- **`reference_id`, `owner`, `name`, `english_name`, `description`** — приписываются
  находке справочного корпуса, когда она узнаётся в каталоге платформы. `reference_id`
  адресует ту же карточку в `syntax_help`, `owner` называет владеющий тип. У находки по
  коду этих полей нет: чанк кода в каталоге платформы не опознаётся.

В справочных действиях обоих профилей (`find_docs` / `search_docs`) конверт тот же, но вместо `modality` и
`graph_id` — `score` ранкера; `root_id` там нет вовсе — справочный корпус не делится на
корни рабочего пространства, и различать его находки нечем и незачем. Он сопоставим внутри одного ответа и бессмысленен между
запросами и бэкендами. Служебные состояния (`not_ready`) остаются структурными и в этом
профиле, поэтому «индекс ещё строится» не выглядит как пустая выдача.

Каждый результат `search_code` помечен модальностью, нашедшей его: `[L+S]` — найден и
лексикой, и семантикой (межмодальное согласие: оба ранкера выдали попадание), `[L]` — только
лексика, `[S]` — только семантика. Тег несёт межмодальный сигнал вместо числового балла. Сниппеты
секрет-редактируются: строковый литерал маскируется как `***`, только если в той же
инструкции ему предшествует чувствительный маркер (идентификатор вроде `Токен` или ключ
`Вставить("Пароль", …)`); структурные литералы и сообщения сохраняются.

### Ошибки эмбеддингов

`semantic_failure` — необязательный объект с обязательным `code` из закрытого
списка ниже. Только локальный отказ по точно измеренному размеру добавляет пару
неотрицательных целых `request_bytes` и `max_request_bytes`. HTTP 413 сам по себе
этих чисел не устанавливает. Других полей, произвольных сообщений, URL, исходного
текста, credentials и raw body провайдера в объекте и embedding-диагностике нет.

| `code` | Причина |
| --- | --- |
| `embedding_invalid_config` | Неверный `EMBEDDING_MAX_REQUEST_BYTES` или нулевой лимит библиотеки |
| `embedding_input_too_large` | Один документ с полным JSON-конвертом превышает лимит |
| `embedding_request_too_large` | Прямой multi-input вызов превышает лимит либо получен HTTP 413 |
| `embedding_response_too_large` | Превышен существующий предел чтения ответа 10 MiB |
| `embedding_timeout` | Истёк таймаут embedding-запроса |
| `embedding_transport_error` | Ошибка соединения, I/O, DNS, TLS или протокола |
| `embedding_provider_error` | Другой ошибочный HTTP status провайдера |
| `embedding_invalid_response` | Невалидный JSON, число/индексы векторов или их форма |
| `embedding_failed` | Прочая embedding-ошибка без безопасной точной классификации |

Предел запроса — по умолчанию 1 MiB; [настройка, разбиение, повторы и откат](README.md#размер-embedding-запросов-и-повторные-попытки)
описаны отдельно. Он не меняет предел чтения ответа.

| Граница ответа | Как виден отказ |
| --- | --- |
| `workspace`: `search action=status` | Текущий отказ workspace/overlay в `structuredContent.semantic_failure`, независимо от `state` лексики |
| `workspace`: `search_code` | Отказ сборки или запроса при лексическом fallback, в том числе при нуле находок; сохраняются `degraded` и `freshness` |
| `reference`: `search action=status` | Отказ семантической сборки справки; `state=ready` может означать готовую лексику |
| Оба профиля: `find_docs` | Лексические результаты или прежний `not_ready` с известным отказом семантической сборки справки; terminal-отказ инициализации справки, вызванный эмбеддингами, — тот же RPC error, что у `search_docs` |
| Оба профиля: `search_docs` | RPC error с фиксированным сообщением и `data.semantic_failure` при известном отказе сборки или запроса |

Отсутствие поля означает отсутствие известного текущего отказа и не доказывает
готовность. Отказ сборки хранит её существующий владелец до начала новой попытки
или успешного завершения; отказ отдельного query остаётся только в его ответе.
Успешный транспортный retry не оставляет предшествующую transient-ошибку.
Если одновременно известны отказы overlay и основной workspace-сборки, выбирается
overlay; состояние другого владельца не сбрасывается. Чтение статуса не вызывает
провайдера и не сканирует хранилище. Отмена и terminal baseline/policy ошибки
сохраняют свой приоритет и прежний формат; `graph` и `list_platform` поля не получают.

Например, сборка справки сохранила лексический корпус, но получила HTTP 413.
Статус `reference` остаётся лексически готовым:

```json tool=search
{"action":"status","schema_version":"4","profile":"reference","state":"ready",
 "indexing":{"schema_version":"1","targets":[
  {"kind":"reference","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null}]},
 "semantic_failure":{"code":"embedding_request_too_large"}}
```

`find_docs` в любом профиле продолжает отвечать, даже если лексических совпадений нет:

```json tool=search
{"action":"find_docs","schema_version":"6","hits":[],"shown":0,"total":0,
 "indexing":{"schema_version":"1","targets":[
  {"kind":"reference","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null}]},
 "semantic_failure":{"code":"embedding_request_too_large"}}
```

Локальный отказ workspace-сборки сообщает измеренные байты:

```json tool=search
{"action":"status","schema_version":"4","profile":"workspace","state":"ready",
 "indexing":{"schema_version":"1","targets":[
  {"kind":"lexical","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null},
  {"kind":"semantic","state":"failed","phase":null,"progress":null,"pass_id":null,
   "reason_code":"native_failure"}]},
 "semantic_failure":{"code":"embedding_input_too_large",
                     "request_bytes":1048577,"max_request_bytes":1048576}}
```

После timeout query `search_code` может вернуть пустой лексический fallback;
этот отказ не меняет состояние уже построенного индекса:

```json tool=search
{"action":"search_code","schema_version":"8","hits":[],"shown":0,"total":0,
 "degraded":"semantic skipped: embedding failed",
 "indexing":{"schema_version":"1","targets":[
  {"kind":"lexical","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null},
  {"kind":"semantic","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null}]},
 "semantic_failure":{"code":"embedding_timeout"},
 "freshness":{"source":"search-index","revision":null,"topology_fingerprint":null,
              "stale":null,"completeness":{"status":"partial",
                "reasons":[{"code":"modality_degraded","detail":"semantic skipped: embedding failed"}]}}}
```

Для `search_docs` в обоих профилях timeout возвращает RPC `error` ниже, а не пустой
успешный результат. Это объект ошибки, не `structuredContent`; его `data` проверяется
отдельно от успешной `outputSchema`. Не связанные с embeddings ошибки сохраняют
свои существующие `reasonCode`.

```json tool=search:error
{"code":-32603,"message":"Semantic embedding failed; use lexical search or retry.",
 "data":{"semantic_failure":{"code":"embedding_timeout"}}}
```

### `EMBEDDING_API_KEY`

Нужен для OpenAI-совместимых embedding API, которые требуют Bearer-авторизацию.

Типовые сценарии:

- локальный Ollama или TEI обычно работают без ключа;
- OpenRouter, OpenAI и похожие сервисы обычно требуют `EMBEDDING_API_KEY`;
- модель при необходимости можно явно задать через `EMBEDDING_MODEL`;
- `Qwen/Qwen3-Embedding-0.6B` — минимальная рекомендуемая модель и текущий
  дефолт;
- `Qwen/Qwen3-Embedding-4B` — усиленный компромиссный вариант;
- `Qwen/Qwen3-Embedding-8B` — более сильный вариант, если ресурс позволяет.

Пример:

```bash
EMBEDDING_URL=https://openrouter.ai/api \
EMBEDDING_API_KEY=your_api_key \
EMBEDDING_MODEL=Qwen/Qwen3-Embedding-0.6B \
bsl-analyzer mcp serve --profile reference
```

Сейчас клиент embedding API добавляет стандартный заголовок
`Authorization: Bearer <ключ>`. Отдельные provider-specific заголовки
автоматически не настраиваются.

### `NAPARNIK_TOKEN`

Нужен только для `its_help`.

Токен можно получить на `https://code.1c.ai/tokens` и передать в MCP-процесс
через `--env NAPARNIK_TOKEN=...` при `mcp install` или обычную переменную
окружения при `mcp serve`.

Если токен не задан, остальные инструменты продолжают работать.

### `--onec-url`, `--onec-user`, `--onec-password`

Нужны для инструментов, которые работают с живой базой 1С:

- `query(action=execute)`;
- `execute(action=run|eval)`;
- `debug`.

`execute(action=check)` использует профиль `native_check` выбранного подключения из
`BSL_ONEC_CONNECTIONS_FILE`. Старое подключение только через `--onec-url` не запускает
HTTP `/check-syntax`: ответ имеет `status="unsupported"`, пока для соединения не
настроен профиль компилятора. Пример полей и локальных лимитов находится в
[`onec-connections.example.json`](onec-connections.example.json).
Пример явно задаёт `source_kind="file"`: `source_connection_env` называет
переменную окружения, значение которой — путь к локальной файловой ИБ. Значение
должно указывать на существующий канонический каталог ИБ; сам путь в JSON не записывают.
Если `source_kind` опустить, выбирается `server`. Для server-профиля эта же переменная
должна содержать `host/base`, а `user_env` обязателен; `password_env` задаётся по
необходимости. Перед компиляцией сервер отправляет фиксированный read-only запрос к
выбранному HTTP-подключению и сверяет фактические `Srvr/Ref` и сборку платформы с
настройкой профиля и локальным Designer.
`designer_path` и обязательный `python_path` задают канонические исполняемые файлы;
`expected_build` должен совпадать с фактической сборкой платформы. На Linux путь Python
можно проверить командой `readlink -f "$(command -v python3)"` и указать полученный
реальный путь. `work_root` нужно заранее создать как канонический каталог, принадлежащий
пользователю MCP-процесса, с правами `0700`; при старте сервер создаёт в нём собственный
каталог заданий. Для headless Linux можно указать канонический путь к `xvfb-run`.
Для `native_check` в file-режиме `user_env` и `password_env` не нужны; поля соединения
верхнего уровня по-прежнему задают доступ к HTTP-сервису. Секреты и значения переменных
окружения в JSON не записывают.

Этот пример документирует file-профиль. Server-профиль получает read-only паспорт выбранной
базы и компилирует указанный metadata owner/origin; порядок расширений в паспорте сеанса не
является гарантией порядка компиляции. Матрица пяти типов модулей проверена с режимами
совместимости `Version8_2_16` и современным режимом; [результаты и ограничения](../architecture/BA-023-MODULE-SYNTAX-CHECK.md#проверки-приёмки).
Внешние файлы EPF/ERF не поддерживаются.
Лимиты профиля по умолчанию — 2 MiB входного текста, 120 секунд и 256 KiB журнала;
верхние границы — 8 MiB, 15 минут и 1 MiB соответственно.

`check` по умолчанию принимает `input_kind="snippet"` и проверяет его в серверном
глобальном контексте временного общего модуля. Полный модуль передаётся с
`input_kind="module"`, явным `module_type` (`object`, `managed_form`,
`ordinary_form`, `common`, `manager`) и `context`:

```json tool=execute direction=input
{"action":"check","code":"Функция Проверка()\nВозврат 1;\nКонецФункции",
 "input_kind":"module","module_type":"common",
 "context":{"kind":"synthetic","module_type":"common"},
 "connection":"test-base"}
```

Это входной запрос `execute`, а не результат вызова. Маркер `direction=input` позволяет
проверять его по опубликованной `inputSchema`; `execute` не публикует общую `outputSchema`,
поскольку `check`, `run` и `eval` возвращают разные формы ответа.

Для модуля конфигурации `context` имеет вид
`{"kind":"metadata","owner":"ОбщийМодуль.МойМодуль","origin":{"kind":"configuration"}}`.
Для модуля расширения указывается его фактический владелец и
`origin":{"kind":"extension","name":"ИмяРасширения"}`; server-профиль сверяет этот target
с read-only паспортом исходной базы. Synthetic-контекст описывает только указанный тип и не
доказывает, что модуль скомпилируется в исходной базе. Объявления процедур и функций во
фрагменте без контекста модуля дают `context_required`.

Результат `check` — `structuredContent` с `schema_version="1"`, статусом,
требуемыми и фактически проверенными контекстами, координатами диагностик и состоянием
очистки. `status` принимает `valid`, `invalid`, `context_required`, `unsupported` или
`error`; `cleanup_status` — `not_started`, `complete` или `pending`. `valid` и
`compilation_status` равны `null`, если компиляция не выполнялась;
`compiler` содержит доступные сведения о сборке, совместимости и fingerprint. Диагностики
возвращают безопасное сообщение и координаты без исходного фрагмента. `context` и
`module_type` отражают запрос, `owner` отдельно дублирует владельца метаданных,
`failure` описывает отказ, а `truncated` отмечает сокращение деталей.

`compiler.compatibility` — сериализованный токен режима из XML применённой конфигурации.
На платформе 8.3.27.1989 runtime-значение `НеИспользовать` представлено в XML токеном
`Version8_3_27`; это не отдельный режим runtime.

У этого действия нет опубликованного tool-wide `outputSchema`: `run` и `eval` сохраняют
текстовые ответы. Бюджет покрывает текст вместе со структурированным JSON; бюджет меньше
512 токенов или вычисленного для запроса минимума отклоняется до запуска компилятора.
Минимум учитывает длину переданных полей контекста.

## Подключение live-инструментов к базе 1С

Для `query`, `execute` и `debug` нужен HTTP-сервис, который предоставляет
встроенное расширение `BSL_Analyzer`.

Один MCP-процесс может работать с несколькими ИБ. Создайте локальный файл по
образцу `docs/mcp/onec-connections.example.json` и передайте путь через
`BSL_ONEC_CONNECTIONS_FILE`. Файл хранит только URL и имена переменных окружения;
учётные данные остаются в окружении. У живых операций укажите `connection`.

Для именованных подключений `execute(action=run|eval)` по умолчанию запрещён.
Для расходуемой тестовой ИБ нужно одновременно установить `allow_execute: true`
в реестре и назначить пользователю роль `BSL_ВыполнениеКода`. Одиночное
подключение через `--onec-url` сохраняет прежнее поведение — выполнение на
стороне MCP разрешено, доступ определяет роль в ИБ. `execute(action=check)` и
операции чтения используют `BSL_ОсновнаяРоль`.

Инструмент `metadata` поддерживает `mode=source|infobase|auto`. В режиме
`infobase` действие `tree` принимает тип коллекции в `meta_type` (и опционально
`name_mask`, `max_items`), а `object` — `object_type` и `object_name`; исходники
конфигурации для этих двух вызовов не требуются.

Форма `object_type` зависит от фактически выбранного источника. Для `mode=source`
и `mode=auto` без `connection` используйте singular-тип анализатора, например
`Справочник`, `Документ` или `ОбщийМодуль`. Для `mode=infobase` и `mode=auto` с
`connection` используйте plural-имя коллекции live-сервиса, например `Справочники`
или `Документы`. MCP передаёт значение без преобразования между singular и plural;
неверная форма возвращает ошибку live-сервиса. Действие `form` доступно только для
source-пути.

Примеры аргументов MCP-вызова `metadata`:

```json tool=none
{"action":"object","mode":"source","object_type":"Справочник","object_name":"Товары"}
```

```json tool=none
{"action":"object","mode":"infobase","connection":"live","object_type":"Справочники","object_name":"Товары","max_output_tokens":700}
```

```json tool=none
{"action":"tree","mode":"infobase","connection":"live","meta_type":"Справочники","max_items":100,"max_output_tokens":700}
```

Первый пример читает workspace source; два остальных передают collection type
как его принимает HTTP producer. Live-бюджет ограничивает сумму сериализованных
`content` и `structuredContent`.

Live-карточка объекта с `schema_version=2` требует HTTP producer не ниже `1.2.0`:
он возвращает варианты типов и реквизиты табличных частей. Проверьте именно
`/version` после публикации; версия HTTP-сервиса отличается от версии расширения
в `Configuration.xml` (для этого producer — `1.1.0`). Со старым producer клиент
сохранит прежние поля и явно пометит недоступные типы или состав табличных частей.

### 1. Экспортируйте расширение

```bash
bsl-analyzer extension export -o ./bsl-extension
```

### 2. Загрузите расширение в конфигуратор

В конфигураторе откройте:

`Конфигурация -> Расширения конфигурации`

Затем добавьте каталог `./bsl-extension` как расширение.

### 3. Опубликуйте HTTP-сервис

В конфигураторе откройте:

`Администрирование -> Публикация на веб-сервере`

Проверьте, что включена публикация HTTP-сервисов и сервис
`BSLAnalyzerService` доступен по пути `/hs/bsl-analyzer`.

### 4. Настройте права

Пользователю 1С, под которым MCP будет обращаться к сервису, должна быть
назначена роль `BSL_ОсновнаяРоль`. Роль включает право `EventLog`, необходимое
инструменту `event_log` для чтения журнала регистрации.

### 5. Проверьте доступность сервиса

```bash
curl http://localhost/base/hs/bsl-analyzer/version
```

Ожидаемый ответ:

```json tool=none
{"version":"1.2.0"}
```

### 6. Запустите `workspace`-профиль с подключением

```bash
bsl-analyzer mcp serve \
  --profile workspace \
  --source-dir ./my-project \
  --onec-url http://localhost/base/hs/bsl-analyzer \
  --onec-user admin \
  --onec-password secret
```

## Rollout и rollback совместимых live-метаданных

Расширение продолжает отдавать legacy-поле `type` и добавляет сырой массив
`typeVariants`; MCP нормализует его в `type_variants` с `technical_name`, `presentation`,
`resolution` и необязательным `reason`. Producer HTTP `1.2.0` также передаёт
`attributes` у каждой табличной части; live object использует `schema_version="2"`
и сообщает причины неполноты. Версия расширения в `Configuration.xml` — `1.1.0`.
Неизвестные будущие поля игнорируются, а
неподдерживаемый технический тип остаётся явным unresolved-вариантом.

Rollout выполняется строго последовательно:

1. Остановить и дождаться завершения всех старых процессов, способных писать derived
   search cache. Одновременные writers разных версий запрещены.
2. Запустить новый бинарник и дождаться публикации его нового engine/cache.
3. Только затем установить новое расширение 1С и проверить `/version` (`1.2.0`),
   raw `typeVariants` и табличные `attributes`, нормализованный `metadata object`,
   BA-007 и BA-010.

Rollback также не смешивает writers:

1. Остановить все новые writers и убедиться, что новый процесс больше не держит cache.
2. Единолично запустить frozen `v0.2.70` и дождаться, пока он откроет и при необходимости
   перестроит derived cache в legacy-формате до публикации engine.
3. Проверить legacy fingerprint/count, отсутствие new-only документов,
   `PRAGMA integrity_check` и FTS consistency; только после этого возвращать старое
   расширение. Не публиковать engine и не обслуживать запросы из частично перестроенного
   cache.

Матрица совместимости: новый бинарник читает старое и новое расширение; legacy
`v0.2.70` читает оба ответа через сохранённое поле `type`, но не использует
`typeVariants`. Derived cache разрешено открывать обеими версиями только
последовательно, никогда одновременно. В доказательствах сохраняют версии и SHA-256
бинарников/расширения, обезличенные fingerprint/count и результаты integrity/FTS;
connection URL и учётные данные не записывают.

### Структурированный прогресс индексации

Machine contract `3.3` публикуется через `bsl-analyzer contract` и ресурс
`bsl-analyzer://contract`; схемы доступны в `tools/list`. Версии: search hits/not-ready
`8` для `search_code` и `6` для docs-действий, search status `4`, graph schema
descriptor `35`, indexing `1`;
`list_platform` остаётся `1`. У legacy graph status/loading нет нового корневого
`schema_version`.

| Успешный ответ | Цели в `indexing.targets` |
| --- | --- |
| Workspace `search status`, `search_code`, включая fallback/not-ready/пустую выдачу | lexical, semantic |
| `find_docs`, `search_docs` обоих профилей; reference `search status` | reference |
| `graph status` и graph loading, включая resolve retry | graph |

Обычные graph data/schema, `list_platform` и ответы других инструментов вне этого
контракта. Hard RPC errors остаются ошибками. Отмена одного запроса не отменяет
общий worker. Ответы не добавляют provider/SQL probes ради telemetry; неизвестное
состояние не запускает восстановление индекса.

Каждая цель содержит ровно шесть ключей `kind`, `state`, `phase`, `progress`,
`pass_id`, `reason_code`, включая явные null. Цели уникальны, порядок
`graph`, `lexical`, `semantic`, `reference`, максимум четыре.

- `state`: `waiting|running|ready|disabled|failed|cancelled|superseded|unknown`.
- `phase`: `initializing|parsing|lexical_indexing|embedding|persisting` или null;
  только native-фаза. У graph/reference phase, counters и pass_id — null.
- `progress`: null либо `{completed: unsigned, total: unsigned|null,
  unit: files|chunks|batches}`. Только согласованные счётчики активного running;
  для embedding предпочтительны chunks, затем batches. Completed не больше total;
  противоречивый sample даёт null. Нет общей процентной шкалы; total=0/null
  не даёт процента. Счётчики монотонны только внутри одного pass/phase/unit.
- `pass_id`: null либо 32 lowercase hex, двоеточие, положительный u64 sequence,
  максимум 53 ASCII байта. Завершённый ID сохраняется до нового begin;
  загруженный с диска ready может иметь null.
- `reason_code`: null либо `initializing`, `pending_work`, `semantic_disabled`,
  `coverage_unverified`, `identity_unverified`, `baseline_unavailable`,
  `overlay_pending`, `stale_generation`, `snapshot_unavailable`, `native_failure`,
  `cancelled`, `superseded`. Raw errors и пути не попадают в это поле.
  Ready и native running имеют null; failed/cancelled/superseded имеют одноимённую
  причину (для failed — native_failure); disabled — semantic_disabled.

Пример: lexical уже готов, semantic ещё считает chunks. Legacy progress и текст
используют тот же sample; counter equality сама по себе не доказывает ready.

```json tool=search
{"action":"search_code","schema_version":"8","status":"not_ready",
 "detail":"semantic indexing","retry_after_ms":1500,
 "progress":{"active":true,"chunks":{"done":12,"total":48},"batches":{"done":1,"total":4},"pct":25},
 "indexing":{"schema_version":"1","targets":[
  {"kind":"lexical","state":"ready","phase":null,"progress":null,"pass_id":null,"reason_code":null},
  {"kind":"semantic","state":"running","phase":"embedding",
   "progress":{"completed":12,"total":48,"unit":"chunks"},
   "pass_id":"0123456789abcdef0123456789abcdef:4","reason_code":null}]}}
```

```json tool=graph
{"status":"loading","indexing":{"schema_version":"1","targets":[
 {"kind":"graph","state":"running","phase":null,"progress":null,"pass_id":null,"reason_code":null}]}}
```

Semantic ready требует текущих coverage и model/dimension identity, успешной
финальной persistence/publication и отсутствия dirty/rerun/overlay debt.
Конфигурация provider, успешная query embedding или равенство счётчиков этого
не доказывают. Непроверенный SQLite BLOB fallback остаётся unknown/identity_unverified;
пустая область готова только после успешной публикации. Ошибка query provider
не отменяет уже доказанную готовность индекса, а сохраняет fallback/degraded semantics.

Remote evidence использует существующий publication marker того же snapshot и
fingerprint, подходящий model/dimension и свежий cache (TTL 60 секунд), плюс
опубликованный overlay без pending/unembedded/unread debt. Истёкший cache,
смена generation и probe in flight дают unknown/stale_generation; отсутствие
coverage/identity — соответствующий unknown. Graph stale — waiting/stale_generation,
reload — running; ошибки и terminal outcomes сохраняются до нового запуска.

Strict consumers квалифицируют `3.3` перед своим развёртыванием. Rollback — предыдущий
квалифицированный binary и соответствующий contract, без конвертации индекса.
Отсутствие `indexing` у старого контракта означает недоступную telemetry, не готовность.
