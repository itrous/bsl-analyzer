# Проверка синтетического серверного модуля через HTTP

Профиль с `epf_module_check: true` разрешает ограниченную проверку целого модуля
через `/check-module`. Значение по умолчанию — `false`; требуется HTTP URL.
Параметр действует только на `execute(action="check")` с
`input_kind="module"` и явным
`context={"kind":"synthetic","module_type":"object"}`.

```json
{
  "connections": {
    "test-base": {
      "url": "http://127.0.0.1/test-base/hs/bsl-analyzer",
      "user_env": "BSL_TEST_BASE_USER",
      "password_env": "BSL_TEST_BASE_PASSWORD",
      "allow_execute": false,
      "epf_module_check": true
    }
  }
}
```

Настроенный `check_executor` сохраняет приоритет и правила `handles_snippet`.
Ошибка выбранного backend не запускает другой backend. Без нового параметра
HTTP-only профиль по-прежнему возвращает `unsupported` для целого модуля;
обычный snippet использует прежний `/check-syntax`. `run` и `eval` сохраняют
прежние разрешения и маршруты.

Rust проверяет полный AST до упаковки и любого HTTP запроса. Поддержаны только
объявления синтетического object-модуля на сервере. Основное тело, в том числе
в препроцессорной ветке, незавершённое дерево, клиентский контекст, настоящий
владелец метаданных и неподтверждённые ссылки на владельца отклоняются с
`valid=null`. Это проверка границы входа в штатном клиенте. Она не заменяет
авторизацию HTTP-сервиса и не вводит серверную ACL для произвольной EPF.

Клиент принимает только `epf_carrier::AdmittedModule`: он сам создаёт бинарный
носитель из внутреннего шаблона, кодирует его и отправляет. Публичного входа
для EPF-пути, EPF-байтов или готового HTTP кадра нет. Producer записывает только
свой временный файл, вызывает `ВнешниеОбработки.Создать(путь, Истина)` и
освобождает объект перед удалением своего файла. Методы входного модуля не
вызываются. Не меняются чужие файлы, процессы и настройки безопасности.

Лимиты: исходный модуль до 1 MiB, EPF до 2 MiB, HTTP JSON до 3 MiB, ответ до
64 KiB. Общий срок проверки — 30 секунд, включая локальную проверку AST,
упаковку и HTTP; запрос получает только оставшийся срок. Повторов и переходов
по redirect нет. Синхронный платформенный `Создать()` нельзя прервать HTTP
таймером: producer проверяет срок до и после него и продолжает очистку своего
файла. Если клиент не получил acknowledgement, `cleanup_status=null` и
`valid=null` сохраняют неизвестность завершения и очистки. Отмена MCP запроса
не выпускает запоздалый ответ `valid`.

Ответ сохраняет check-contract v1. `valid` означает только проверенный
синтетический серверный object-контекст, а не компиляцию настоящего владельца.
`invalid` допускается лишь при нативной ошибке с позицией внутри собственного
фиксированного object-модуля и с допустимыми исходными координатами UTF-16.
Ошибки прав, неподтверждённого контекста или создания без такой позиции дают
`error`, `valid=null`. Ошибка удаления даёт `error` независимо от результата
компиляции; `compilation_status` и `cleanup_status` остаются независимыми.

Шаблон получен на 8.3.27.2130; это происхождение шаблона, не утверждение о версии
платформы сервиса. Применение producer и нативная приёмка нового Rust-носителя
проводятся отдельно: valid → semantic-invalid → valid с тем же шаблоном,
проверка исходных BOM/CRLF/emoji координат, SafeMode и удаления собственного
файла. Unit/fakeHTTP тесты не заменяют эту проверку.
