# Выполнение BSL через HTTP

`execute(action=run)` отправляет код один раз. Настройка именованного подключения
`execute_timeout_ms` задаёт положительный конечный лимит ожидания в миллисекундах.
Если поле отсутствует, действует прежний лимит 30000 мс. Значения 0, отрицательные
числа, дроби и строки недопустимы. Настройка проходит через общий backend и
контекст сеанса; короткие query/check/eval запросы сохраняют лимит 30 секунд.

Транспортный сбой до получения полного ответа даёт `structuredContent` со
`status: "unknown_execution_state"`, `success: null`, `retry_performed: false`
и `isError: true`. `failure.code` различает `timeout` и другой `transport_error`.
Клиент не подтверждает отмену серверной операции. Перед новым
запуском проверьте независимый серверный результат или маркер операции. HTTP
redirect и транспортный сбой не запускают изменяющий код повторно.
Терминальный HTTP 400/500 остаётся HTTP-ошибкой; ответ producer с
`success: false` остаётся ошибкой исполнения BSL.

Успешный ответ HTTP producer `/execute` содержит:

```json
{"success":true,"context":{},"duration_ms":1,"messages":[{"text":"Первое"},{"text":"Второе"}],"messages_truncated":false}
```

`messages` содержит тексты из очереди сообщений платформы в её исходном порядке.
Сбор выполняется после успеха и после исключения. `Сообщить(...)` и
`Новый СообщениеПользователю` используют поддержанный платформой канал; клиент
не переписывает и не перезапускает переданный код. Перед выполнением удаляются
оставшиеся сообщения текущего HTTP-вызова; после выполнения очередь считывается
с удалением полученного. Producer отдаёт не более 256 сообщений и 16384 символов
их текста, сохраняя начало последовательности; `messages_truncated: true`
означает усечение этого канала.

MCP возвращает статус, ошибку и сообщения отдельно в `structuredContent` и
согласованный текстовый блок. Их суммарный размер ограничен
`max_output_tokens` (приблизительно 4 байта на token). Сначала убирается контекст,
затем конец последовательности сообщений и длинный текст; поле `truncated`
и текстовая пометка показывают усечение. Минимальный ответ сохраняет статус
и пометку даже при бюджете меньше размера самой пометки. Ошибка после сообщения
сохраняет `success: false`, `isError: true`, сообщение и описание исключения,
пока они помещаются в бюджет. У старого producer без `messages` MCP возвращает
`messages: null` и пояснение о недоступном канале; `messages: []` подтверждает
поддержанный, но пустой вывод.

Для пустого HTTP 404 клиент сообщает имя выбранного подключения и возможное
отсутствие endpoint или публикации HTTP-сервиса. Это отличается от JSON-ошибки
BSL/SDBL. URL не включается в транспортные ошибки; ссылки и учётные данные удаляются
из HTTP-тела ошибки, ограниченного 4096 байтами с сохранением UTF-8. Проверка
публикации выполняется оператором, без автоматической установки или смены профиля.
Имя подключения также очищается от URL и настроенных учётных данных. Непустой
ответ HTTP 404 сохраняет обычную ошибку запроса без предположения об отсутствии сервиса.

`query(action=execute)` отправляет пакет `SELECT` одним HTTP-запросом. Если
платформа отклоняет пакет, MCP возвращает ошибку `-32603` с текстом ответа
платформы в пределах лимита выше. Например, `РАЗРЕШЕННЫЕ` во вложенном запросе
может привести к ошибке «Ключевое слово РАЗРЕШЕННЫЕ доступно только у первого
запроса». Таймаут HTTP или отмена MCP завершают ожидание клиента. Сервер может
ещё обрабатывать запрос. Автоматического повторного запроса нет.

Очередь сообщений описана в [документации платформы](https://1c-dn.com/library/messages_displayed_to_users/).
Стандарт [418](https://its.1c.ru/db/v8std#content:418) рекомендует прикладному коду
`СообщениеПользователю`; совместимость HTTP run с существующим `Сообщить` сохраняется.

## Проверка на тестовой 1С

Эти сценарии требуют отдельно разрешённой существующей тестовой ИБ. Локальный
HTTP stub проверяет клиентский контракт, но не заменяет выполнение платформой.
Перед проверкой зафиксируйте source/binary/extension hashes и выбранный профиль
без URL, пароля и других секретов.

1. При лимите 45000 мс выполнить безопасную операцию длительностью 31 секунду.
   Отдельный наблюдатель должен подтвердить один запуск и один итоговый маркер.
   Повторить короткий успех и серверную ошибку.
2. Установить лимит меньше времени операции. После `unknown_execution_state`
   наблюдать появление итогового маркера на сервере, не повторяя run. Число запусков
   остаётся равным одному.
3. Последовательно выполнить `Сообщить("Первое")`, сформировать и отправить
   `СообщениеПользователю` с текстом `Второе`, затем `Сообщить("Третье")`.
   Сравнить точный порядок в HTTP JSON и MCP. Повторить с исключением после
   второго сообщения, пустым выводом и превышением обоих лимитов producer/MCP.
   Повторить короткий успех со старым producer без поля сообщений.
4. Для проверки схемы после apply сохранить прежний HTTP-сеанс S1 и отдельно
   создать новый S2 той же тестовой ИБ. Зафиксировать идентификаторы сеансов,
   платформу, конфигурацию и hash read-only SELECT существующего поля. Выполнить
   штатное разрешённое добавление тестового поля и apply; сохранить hashes до/после.
   В S1, S2 и новом обычном клиенте сравнить карточку метаданных, eval наличия поля
   и одинаковый read-only SELECT нового поля. HTTP-заголовок `Connection: close`
   сам по себе не доказывает новый сеанс платформы. Готовая карточка не подтверждает
   готовность запросов. При расхождении записать владельца состояния и точную
   ошибку; поддержанный способ обновить только S1 выбирать после установления
   причины. До такой проверки автоматическое обновление сеанса не реализуется.
   Не перезапускать кластер и не повторять изменяющий run. Удалить только свои
   тестовые объекты штатным rollback после снятия результатов.

### Ограничение после изменения структуры расширения

Успешный apply, карточка метаданных, `eval` и новый TCP-клиент не являются
подтверждением готовности запросов в HTTP-сеансе. Поэтому live `metadata` для
`tree` и `object` явно возвращает `query_schema_readiness="not_checked"` в
структурированном ответе; полнота самой карточки этого не меняет. Обычные
карточки и дерево повторяют поле в текстовом JSON. При выборе
`predefined_code` текст представляет краткую карточку, а поле сохраняется в
структурированном ответе, в том числе после бюджетного усечения. На платформе 8.3.27.2130
после добавления строкового ресурса собственного регистра один HTTP-обработчик
продолжал видеть прежний набор полей и отвергал SELECT нового ресурса. Другой
параллельный HTTP-запрос вернул HTTP 500 с ошибкой SDBL «Таблица или поле
Fld67236 не содержится в разделе FROM». Хотя HTTP-ответ не содержал SID,
сохранённый технологический журнал связал этот отказ с новым серверным
`SessionID=2`, соединением `4909` и `WebServerExtension`: совпали целевая ИБ,
время и точная ошибка; до запроса RAC содержал только прежний SID1. RAC UUID
второго сеанса не восстановлен, успешного результата его metadata/SELECT нет.
Новый обычный клиент той же ИБ затем подтвердил и metadata нового ресурса,
и успешный SELECT нового поля. Это локализует наблюдаемое расхождение до
серверного HTTP/runtime-пути против обычного клиента, но не доказывает, что
запуск обычного клиента обновляет HTTP-сеанс. Точный внутренний cache и момент
отказа относительно выполнения диагностического BSL не установлены.

Эти наблюдения не устанавливают конкретный cache или рабочий процесс как
причину отказа. Клиент не поддерживает доказанный способ обновить состояние
только одного устаревшего сеанса и не выполняет скрытый reset, restart или
повтор кода. При таком расхождении готовность новой схемы **не подтверждена**:
сохраните исходную ошибку и проверьте то же поле отдельным read-only SELECT
внутри нужного сеанса. Связывайте результат с actual SID и, если доступен RAC,
UUID и временем начала сеанса. Успех другого сеанса не исправляет результат
первого и не разрешает повторить изменяющую операцию.

Отсутствующее поле само по себе также не доказывает устаревание: это может быть
ошибка имени или неприменённое изменение. Сначала сопоставьте ожидаемую схему
с фактически применённой и результатом обычного нового клиента. Если
расхождение не устранено, оператор должен считать HTTP-выполнение с новой
структурой недоступным, а не принимать частичную проверку метаданных за успех.
