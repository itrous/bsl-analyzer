# Руководство по логированию и профилированию

Этот документ описывает, как использовать инфраструктуру логирования и
профилирования в `bsl-analyzer`.

## Переменные окружения

| Переменная | Назначение | Пример |
|------------|------------|--------|
| `BSL_LOG` | фильтрация логов через targets syntax | `hir_def=debug,cfg=warn` |
| `BSL_PROFILE` | иерархическое профилирование | `*@3>10` |
| `BSL_PROFILE_JSON` | выгрузка профиля в JSON | `*` |
| `BSL_LOG_FILE` | запись логов в файл | `/tmp/bsl.log` |
| `BSL_MCP_DAEMON_LOG` | opt-in файл лога daemon: `1`/`true` в каталоге кеша состава либо явный путь | `true` |

Для workspace каталог daemon log определяется после проверки Project и состава
источников: `<base>/workspaces/v1/<digest>/bsl-analyzer-daemon.log`. База выбирается
по `--cache-dir`, затем `BSL_CACHE_DIR`, затем системному cache dir; пути описаны
в [MCP README](../mcp/README.md#каталог-кеша-workspace). Явный filename остаётся
пользовательским выходом. Ошибка opt-in file log сообщает причину и сохраняет
stderr logging без отказа запуска. Невалидный source-set или запрещённое
расположение кэша отклоняется до создания каталога/лога. Stdout stdio остаётся
за MCP-протоколом.

## Уровни логирования

Используйте уровень логирования в зависимости от сценария:

| Уровень | Когда использовать |
|---------|--------------------|
| `error` | невосстановимые ошибки, влияющие на работоспособность |
| `warn` | восстановимые ошибки и деградация функциональности |
| `info` | крупные этапы выполнения: загрузка, завершение анализа, запуск сервера |
| `debug` | подробности для отладки обычного выполнения |
| `trace` | очень подробная трассировка: отдельные узлы AST, итерации, низкоуровневые шаги |

## Использование `tracing` в коде

### Базовое логирование

```rust
use tracing::{trace, debug, info, warn, error};

// Простые сообщения
info!("Analysis started");
debug!("Processing file");

// Структурированные поля
info!(file_count = files.len(), "Loading files");
debug!(file_id = ?file_id, method = %method_name, "Lowering method");
```

### Спаны для профилирования

Для измерения длительности операций используйте `span`:

```rust
pub fn expensive_operation(input: &str) -> Result {
    let _span = tracing::info_span!("expensive_operation", len = input.len()).entered();
    // ... код операции
}
```

Если задан `BSL_PROFILE`, время выполнения спанов измеряется автоматически.

### Правила именования спанов

- используйте `snake_case`
- передавайте важный контекст через поля спана
- выбирайте короткие, но понятные имена

```rust
// Хорошо
let _span = tracing::info_span!("lower_method", method_id = ?id).entered();
let _span = tracing::info_span!("parse_file", file_id = ?file_id, len = input.len()).entered();

// Плохо: слишком многословно
let _span = tracing::info_span!("lowering_method_body_to_hir_representation").entered();
```

## Постоянный журнал жизненного цикла векторов

При создании MCP-сервера CLI автоматически подключает отдельный JSONL-журнал
`bsl_vector_lifecycle` до открытия поисковых хранилищ. Это относится к stdio,
HTTP и backend daemon; broker-прокси, который только пересылает сообщения,
журнал не создаёт. Неверные аргументы `mcp serve` отклоняются до его подключения.
При использовании `bsl-search` как библиотеки события получает subscriber
вызывающей программы: библиотека не устанавливает глобальное логирование.

Журнал по умолчанию принимает INFO независимо от общего `BSL_LOG=warn`.
Точное указание target переопределяет этот уровень:

```bash
BSL_LOG='warn,bsl_vector_lifecycle=debug'  # также транзакционные детали отдельных файлов
BSL_LOG='warn,bsl_vector_lifecycle=off'    # отключить события этого target
```

Обычный диагностический вывод и `BSL_LOG_FILE` сохраняют свою настройку.
Журнал не пишет в stdout: этот поток остаётся за MCP-протоколом.

### Расположение и ограничения

Каталог: `<state>/bsl-analyzer/vector-journal/<workspace-key>/`.
Корень выбирается через `dirs::state_dir().or_else(dirs::data_local_dir)`:

| Платформа | Корень `<state>` |
|-----------|------------------|
| Linux | `$XDG_STATE_HOME`, иначе `$HOME/.local/state` |
| Windows | `%LOCALAPPDATA%` |
| macOS | `$HOME/Library/Application Support` |

`workspace-key` — BLAKE3 от байтов канонического пути исходного workspace
(`Path::canonicalize`, затем `OsStr::as_encoded_bytes`); без исходного каталога
используется BLAKE3 от литерала `reference-only`. Разные поколения процесса
разделяют каталог, а конкретный SQLite-файл различается полями `store_id`,
`store_path` и `store_role`. В ключ не входят URL, пароль или broker token.
Путь store приводится к абсолютному написанию без открытия файла и разрешения
symlink; `..` сохраняется, чтобы не приписать путь через symlink другой базе.
Встроенные workspace, reference и временные baseline stores имеют разные роли.
При недоступном state-каталоге запасного пути в репозитории, `.build` или `/tmp` нет.
Если автоматически выбранный journal path пересекается с workspace или
declared source roots, журнал отключается с диагностикой до создания файлов;
остальные MCP-возможности продолжают работать. Перенос workspace cache не
меняет расположение и формат этого журнала.

Кольцо содержит до восьми сегментов `0.jsonl`…`7.jsonl`, каждый не более
4 МиБ вместе с заголовком, и пустой постоянный `journal.lock`: максимум
32 МиБ полезных файлов и девять файлов на workspace, включая параллельные
процессы. Каждый сегмент начинается заголовком
`{"journal_version":1,"generation":0}` с возрастающим логическим `generation`.
Восстановление выбирает максимальное корректное поколение; номер файла и mtime
не задают хронологический порядок. Писатели сериализуют полные записи и ротацию
через неблокирующий OS lock; файл блокировки нельзя удалять или заменять во время работы.

Одна запись занимает не более 8 КиБ. Слишком длинные разрешённые строковые поля
сокращаются с `truncated=true`; числа и идентификаторы операций сохраняются.
Обычные операции дают сводку через 128 обработанных файлов либо одну секунду
и заключительную частичную сводку; примеров файлов не более десяти.
В процессе работает один writer thread: очередь на 511 записей плюс одна
ожидающая запись, до 4 МиБ payload. Заполнение очереди не задерживает индексатор.
При штатном выходе ожидание сброса ограничено двумя секундами.

Unix-каталоги `vector-journal` и workspace имеют режим 0700, файлы — 0600.
Уже существующий общий каталог `bsl-analyzer` может иметь 0755: он должен
принадлежать текущему пользователю и не разрешать запись группе или остальным.
В частности, 0775 отключает журнал; его исправляют отдельно при настройке
установки, сам журнал не меняет права общего каталога. Windows создаёт приватные
каталоги с protected DACL текущего пользователя; доступ SYSTEM и администраторов
находится вне границы конфиденциальности. Общий родитель может иметь безопасную
унаследованную DACL с теми же доверенными субъектами. Symlink/reparse,
чужой владелец, небезопасные права и посторонние файлы отключают запись, не
изменяя чужие данные. Журнал может содержать пути; исходный текст, векторы,
секреты, endpoint URL, lease token и произвольный текст ошибок в него не входят.

### Чтение и атрибуция

Для согласованного снимка копируйте сегменты после выхода всех писателей этого
workspace, сохраняя приватные права. Копирование живого кольца не атомарно:
во время сбора слот может сменить поколение. Не смешивайте сегменты разных сборов.
В копии прочитайте заголовок каждого сегмента, отсортируйте по числовому
`generation` и обрабатывайте последующие полные JSONL-строки в порядке записи.
Повреждённый заголовок и незавершённую последнюю строку считайте отсутствующим
свидетельством; не пытайтесь дополнять их предполагаемыми событиями.

| Поля | Интерпретация |
|------|---------------|
| `process_id`, `pid`, `event_seq`, `timestamp_ms` | UUID поколения процесса, PID, порядок внутри процесса и UTC Unix-время в миллисекундах |
| `operation_id`, `parent_operation_id` | Связь операций внутри одного `process_id`; объединяйте по паре process/operation |
| `snapshot` | Наблюдение до миграций: версии, начальные счётчики и качество идентичности; это не предобраз последующей мутации |
| `reason`, `reasons`, `outcome`, `outcomes` | Причина решения и исход отдельной операции либо сводки |
| `counts`, `committed_totals`, `count_quality` | Раздельные эффекты и подтверждённые итоги; недоступные векторные счётчики имеют `null`, а не вымышленный ноль |
| `kind=journal_gap`, `dropped`, `gap_reason` | Потерянные записи при `queue_overflow` либо восстановление `partial_record` / `corrupt_segment`; число повреждений не является числом потерянных векторов |

`sqlite_vectors_removed` означает удаление ненулевых SQLite-векторов;
`overlay_vectors_removed` и `overlay_cache_entries_removed` считаются отдельно.
`hashes_cleared` — изменение метаданных, `embeddings_written` — прогресс записи.
Обнуление хеша само по себе не доказывает потерю вектора: её может вызвать
последующая переиндексация. Пустой хеш без более ранней записи не объясняет,
кто и почему его очистил. Удаление или перестроение HNSW/sidecar-артефакта
не означает потерю SQLite-векторов. Только подтверждённый commit даёт
подтверждённые потери; откат или отмена не отменяет уже завершённые дочерние commit.
Публикация index и sidecar записывается отдельно: успешный первый rename остаётся
успешным, даже если второй завершился ошибкой. Отказ публикации из-за изменившегося
generation не означает удаления векторов из SQLite.

`pending` в embedding-pass означает остаток выбранного в начале прохода набора
после подтверждённых записей этого прохода; это не новый подсчёт живой базы при
конкурирующих изменениях. `committed_totals` — накопленные эффекты дочерних
транзакций, `counts` — эффекты текущей сводки. `files`, `reasons` и `outcomes`
тоже относятся только к текущей сводке: итог операции — их сумма по всем её
сводкам. Событие `embedding_orchestration`
описывает запуск worker и не дублирует SQL-счётчики дочернего `embedding_pass`.
Версии миграций доступны как `version_kind`, `from_version`, `to_version`;
неизвестная исходная версия остаётся null.

### Пробелы и отказоустойчивость

При переполнении очереди следующий успешный writer сначала записывает gap.
Незавершённый хвост обрезается до последней полной строки под блокировкой;
повреждённый слот заменяется только при его очереди ротации, с отметкой gap.
Ошибка открытия, прав или записи выдаёт диагностическое предупреждение
`vector journal unavailable` не чаще раза в минуту на класс ошибки. В нём нет
исходной ошибки или содержимого записи; оно не возвращается в очередь журнала.
Если обычный диагностический канал тоже недоступен, наблюдение недоступно,
но поисковая операция продолжается. Занятую другим процессом блокировку writer
ждёт короткими повторами; после любой другой ошибки пауза между попытками
удваивается до одной секунды, а при выходе процесса двухсекундный сброс не ждёт
такую запись.

Это диагностический след, а не транзакционный audit ledger. Обычный перезапуск
процесса или ОС сохраняет файлы, но per-record fsync не выполняется. Сбой питания,
авария процесса, последняя несброшенная сводка, очередь, disk error и ротация
могут удалить свидетельства. Между SQLite commit и доставкой события остаётся
окно: отсутствие записи о commit не доказывает откат. Старый эпизод без журнала
нельзя объявлять объяснённым по одному нынешнему состоянию индекса.

Проверки sink: `cargo test -p bsl-analyzer --bin bsl-analyzer-app cli::logging`.
Изолированный CLI/protocol-тест для Unix, кроме macOS (там корень берётся не из XDG):
`cargo test -p bsl-analyzer --test vector_journal_cli`.
Windows DACL/junction-проверка входит в unit tests под `cfg(windows)`;
Linux-прогон не подтверждает её выполнение на Windows.

## Профилирование

### Иерархическое профилирование (`BSL_PROFILE`)

Синтаксис фильтра: `pattern@depth>threshold_ms`

Примеры:

```bash
# Профилировать все операции
BSL_PROFILE='*' cargo run -- analyze ~/project

# Только операции дольше 50ms, глубина 2
BSL_PROFILE='*@2>50' cargo run -- analyze ~/project

# Профилировать только выбранные операции
BSL_PROFILE='parse|analyze' cargo run -- analyze ~/project
```

Пример вывода:

```text
  112ms  cli_analyze
    45ms  load_files
    67ms  run_diagnostics
      23ms  check_file (×6540)
```

### JSON-профилирование (`BSL_PROFILE_JSON`)

Для инструментальной обработки можно писать профиль в JSONL:

```bash
BSL_PROFILE_JSON='*' cargo run -- analyze ~/project 2>timing.jsonl
```

Пример вывода:

```json
{"name":"cli_analyze","elapsed_ms":112}
{"name":"load_files","elapsed_ms":45}
```

## Фильтрация по компонентам

Логи можно фильтровать по crate/module через targets syntax:

```bash
# Только debug-логи из hir-def
BSL_LOG=hir_def=debug cargo run

# Несколько фильтров сразу
BSL_LOG=hir_def=debug,cfg=warn,dataflow=info cargo run

# Общий debug + trace для конкретного модуля
BSL_LOG=debug,hir_def::body::lower=trace cargo run
```

## Практические рекомендации

### Делайте

- ставьте `span` вокруг потенциально дорогих операций (>1ms)
- добавляйте в поля спана полезный контекст: идентификаторы, размеры, счётчики
- используйте `debug!` для штатных технических деталей
- используйте `info!` экономно, только для крупных этапов

### Не делайте

- не используйте `println!` / `eprintln!` для отладки — вместо этого используйте `tracing`
- не создавайте `span` для тривиальных операций (<100μs)
- не логируйте чувствительные данные: содержимое файлов, токены, пароли, креды
- не ставьте `info!` на каждый элемент в больших циклах

## Профилирование памяти и CPU

Для более детальных измерений можно использовать `StopWatch` из crate
`profile`:

```rust
use profile::StopWatch;

let sw = StopWatch::start();
// ... операция
let span = sw.elapsed();
println!("{}", span); // "123ms, 456ki, 789kb"
                      // время, инструкции CPU, изменение памяти
```

Что умеет `StopWatch`:

- CPU instructions (только Linux, через `perf_event`)
- изменение памяти (Linux glibc, Windows или при включённом `jemalloc`)
- время выполнения (все платформы)
