# Базовая линия диагностик: устройство

Пользовательская сторона — команды, настройки и обещания — описана в
`docs/configuration/DIAGNOSTICS.md`. Здесь зафиксировано внутреннее устройство:
где что лежит, какие инварианты держатся и какие свойства приняты сознательно.

## Слои

| Слой | Что owns |
|------|----------|
| `ide::diagnostics_baseline` | модель файла версии 1, отпечаток, классификация, сводка |
| `ide::partitioned_diagnostics_baseline` | набор партиций, манифест, покрытие по партициям |
| `ide-host-core::diagnostics_baseline` | снапшот в памяти, наблюдение за файлами, эпоха |
| `project-model` | настройка, план партиций, файловая граница каталога |
| `bsl-analyzer` | команды CLI, транзакция публикации, применение в LSP |
| `mcp-server` | применение в резидентном состоянии и в ответах инструмента |

Классификация ничего не знает ни о LSP, ни о MCP: она принимает кандидатов и
покрытие, возвращает разложение и сводку. Адаптеры своей логики не имеют.

## Отпечаток

`diagnostic_fingerprint` = BLAKE3 от относительного пути, кода правила,
нормализованной по пробелам строки исходника и порядкового номера одинакового
срабатывания. Номера строк в ключ не входят — подавление переживает сдвиг кода.

Не переживают: правку самой строки, переименование файла, изменение кода правила.
Это цена устойчивости к сдвигам, а не недосмотр.

**Порядковый номер (`occurrence`) — известное слабое место.** Появление ещё
одного одинакового срабатывания выше по файлу сдвигает номера, и подавление
переезжает на соседнее срабатывание того же вида.

`UnknownSuppressionCode` и `SuppressionWithoutCode` защищённые: они сообщают о
сломанной директиве подавления, поэтому не подавляются и **не записываются** в
файл. Правило живёт в одном месте — `is_protected_diagnostic`; каждый путь записи
фильтрует через него, потому что валидатор такую запись отвергает и уронил бы
всю команду.

## Форматы хранения

Версия 1 — один JSON-файл: область проекта и плоский список записей.

Версия 2 — каталог: `manifest.json` плюс content-addressed объекты партиций в
`objects/<партиция>/<хэш>.json`. Манифест хранит отпечаток области проекта,
поколение и по записи на партицию (идентификатор, путь объекта, BLAKE3).

**Объект партиции пишут двое:** потоковый `PartitionFileWriter` (миграция
большого набора, память не растёт с числом записей) и `diagnostics_partition_json`
(обычный путь). Их байты обязаны совпадать: `repair_object` восстанавливает
объект регенерацией и сверяет BLAKE3 с манифестом. Поэтому оба пишут компактный
JSON плюс завершающий перевод строки. Манифест, в отличие от объектов, остаётся
pretty — он мал и его читают люди.

## Публикация

`publish_set` — единственная точка записи набора:

1. блокировка `.baseline.lock` через `try_lock` (занято → отказ, а не ожидание);
2. объекты пишутся во временные имена и переименовываются, файлы и каталог
   синхронизируются;
3. манифест заменяется последним — до этого момента старое поколение цело;
4. временные файлы снимаются guard'ом на `Drop`.

После смены манифеста удаляются объекты, которых в нём больше нет, **но только
при неизменном отпечатке области проекта**. Отсюда правило: перестройка набора
обязана нести спящие партиции (`carry_dormant`), иначе восстановление одного
повреждённого объекта унесёт с диска партиции вне `include`. При изменившейся
топологии спящие записи вычищаются из манифеста намеренно, а их объекты остаются
на диске.

## Классификация и покрытие

Разложение кандидатов: `new` (активные), `known` (подавлённые), `resolved`
(записи линии, которых больше нет), `unsuppressed` (партиции вне `include` —
их записи не подавляют).

Покрытие бывает `Full` и `Partial { completed_files }`. Партиция повышается до
`Full`, только когда все принадлежащие ей файлы проекта попали в проанализированные.
**Знаменатель обязан включать нечитаемые файлы**: иначе записи файла, на который
не смотрели, будут объявлены исправленными.

`ResolvedPolicy` управляет тем, считается ли `resolved`. Подсчёт обходит все
записи всех включённых партиций — верная форма для прогона по проекту, который
делает это один раз, и чистая трата для классификации одного файла в редакторе,
где результат выбрасывается. Публикация диагностик документа идёт со `Skip`;
пропущенный счётчик отсутствует в сводке, а не равен нулю.

## Перезагрузка вне Salsa

Снапшот базовой линии не является входом Salsa: линия не участвует в вычислении
диагностик, а отбирает готовые — `active_for_file` получает уже посчитанный набор
и снимает записанное. Дверь для входа здесь одна, интернированный
`DiagnosticsConfigId`, по которому ключуется `file_diagnostics_query`: положить
линию туда значит давать новый ключ на каждую публикацию и заново исполнять
запрос диагностик для каждого файла проекта. Сейчас же кеш запроса переживает
смену линии, а заново отрабатывает только проверка принадлежности множеству.

Свежесть определяется наблюдением (`observe`) — длина, время изменения, а на Unix
ещё устройство и inode каждого файла набора. Смена эпохи наблюдения поднимает
`affects_open_documents`, и открытые документы публикуются заново. В идентификатор
результата эпоха входит по-разному: MCP дописывает её к `result_id` явно, а LSP
считает `result_id` по уже отфильтрованному набору — правка линии, не изменившая
в файле ничего видимого, оставляет прежний идентификатор, и `Unchanged` здесь
верный ответ.

Известные свойства наблюдения: на Windows нет `dev`/`ino`, остаются длина и
время; перезапись равным по длине содержимым в пределах разрешения таймера
файловой системы останется незамеченной до следующей полной загрузки.

Автономный LSP (`lsp --mode stdio`) наблюдает точный список файлов линии —
манифест и объекты включённых партиций; объекты спящих партиций в список не
входят. Публикация меняет имена объектов, и сервер передаёт новый список
загрузчику операцией `set_watch_only_files`: рабочая область не
пересканируется, финализация загрузки не повторяется. Принятое ограничение:
регистрация наблюдателя на каталоге вне корней исходников, из которого ушли
все наблюдаемые имена, остаётся до следующей полной конфигурации загрузчика
(правка конфигурации проекта) или до исчезновения каталога. Снимать её при
публикации дороже: на FSEvents `unwatch` перестраивает поток событий.

## Отмена

Обход рабочей области в MCP идёт двумя параллельными проходами: сбор кандидатов
и, отдельно, фильтр по авторам. **Оба** обязаны регистрировать salsa-токен своей
копии базы в `RequestCancel`, проверять отмену между файлами и держать раскрутку
внутри воркера: иначе второй проход неостановим, а раскрутка отмены переходит
через rayon в блокировку состояния как паника.

## Принятые ограничения

- Файловый путь MCP считает `resolved` полным обходом линии: это одиночный запрос
  агента, а не публикация на каждое нажатие клавиши.
- Сводку партиций в ответах MCP урезает бюджетный шейпер ответа, а не сама карточка:
  при заданном `max_output_tokens` сводки партиций снимаются ПЕРВЫМИ, раньше
  ошибок и находок, и тогда ответ несёт `partitions_truncated: true` с
  `partitions_returned` меньше `partitions_total`.
- Наблюдение за набором делает `stat` манифеста и каждого объекта под мьютексом
  резидентного состояния при каждом чтении.
- `max_output_tokens` меньше 256 инструмент диагностик отвергает.
