# Windows native acceptance stand

Runs the native check matrix (fixtures L and M) against the real 1C platform
in the libvirt guest `win10`, through the public MCP `execute` tool.

Copy `stand.example.json` to `stand.local.json` (not committed) and fill in
the VM name, the virtiofs share and the guest paths.

```bash
python3 scripts/win-acceptance/win_accept.py build            # build HEAD in the guest
python3 scripts/win-acceptance/win_accept.py run              # all L and M rows
python3 scripts/win-acceptance/win_accept.py run --rows windows-M-snippet,windows-L-snippet
python3 scripts/win-acceptance/win_accept.py run --fixtures L --rows none \
    --lifecycle active-cancel,active-timeout,queue-cancel   # lifecycle scenarios only
python3 -m pytest scripts/win-acceptance                       # oracle unit tests
```

Results: `<share>/wa/runs/<run-id>/out/{results.jsonl,summary.json}`.

## What a row proves

A row passes when all of the following hold:

- the MCP answer matches the expected status, and for `valid`/`invalid`
  also `valid` flag, `cleanup_status=complete`, all required contexts checked,
  the fixture compatibility mode and the expected original UTF-16 position;
- every file of the source infobase has the same path, size and SHA-256 after
  the row as before it (a file created or deleted by the platform shows up as
  added/removed);
- no `1cv8`/`1cv8c`/`ibcmd` process, no new `owned-jobs` entry in the executor
  work root and no execution sentinel marker remain.

The stand deliberately does not watch file events in real time:
`FileSystemWatcher` drops events under bursts, which made earlier runs fail
for reasons unrelated to the product. The executor's own guarantees (private
snapshot, share-mode reader) are covered by its Rust tests.

## Layout

- `win_accept.py` — host driver: exports the revision to the virtiofs share
  (guest `Z:`), starts one PowerShell process per command through the QEMU
  guest agent, prints row results as they appear.
- `guest_run.py` — guest runner (stdlib only, run from `C:` because Python
  path resolution fails on virtiofs).
- `windows-matrix.json` — rows generated by `make_matrix.py` from the
  prepared request manifest. Lifecycle rows are listed separately.

## Lifecycle scenarios (`--lifecycle`, fixture L)

The runner suspends the Designer started for the request (`NtSuspendProcess`)
instead of patching the product, then:

- `active-cancel` — sends `notifications/cancelled`; no response may arrive;
- `active-timeout` — waits for the 30 s connection deadline; the answer must be
  `error` with `transport_timeout` or `deadline_exceeded`;
- `queue-cancel` — while the active request is held, submits a peer
  (`max_concurrent = 1`), checks that no second executor starts, cancels the
  peer, resumes the Designer and expects the active request to be `valid`.

After each scenario no platform process or new owned job may remain, the
follow-up row must pass and the source must be byte-identical.
Not run here: the queue-deadline row (the queue wait counts against the same
per-connection deadline, so a held active request also times out; covered by
the Rust test `queue_deadline_and_cancellation_do_not_spawn_executor`) and
crash recovery (accepted separately).

## Binaries

`build` takes the executables from `target\...\debug\deps`: on the virtiofs
share Cargo does not reliably refresh the copies in `debug\`, which once made
a run use a ten-day-old executor.

Guest prerequisites: QEMU guest agent, a virtiofs share mounted as `Z:`,
Rust 1.98 MSVC toolchain, VS 2022 Build Tools, platform 8.3.27.1989 and the
executor profiles/fixtures named in `stand.local.json`.
